## 3. Fail-Closed Runtime & Prevention of Silent Restarts (Phase B)

Previously, systemd units or operators could restart background collectors against terminal campaigns if service files or registries were not tightly coupled. In v0.3.21:
1. **Dynamic Registry Resolution**:
   - `quantctl derivatives collect-once --require-active-epoch`: Dynamically resolves `resolve_active_derivatives_epoch()`. If all registered epochs are terminal, it refuses collection with `REFUSED_NO_ACTIVE_EPOCH` and exits cleanly.
   - `quantctl opportunity-forward collect-once --registry <path>`: Dynamically resolves `resolve_active_opportunity_campaign()`. If all registered campaigns are terminal, it refuses collection with `REFUSED_NO_ACTIVE_CAMPAIGN` and exits cleanly.
2. **Preregistration Boundary Protection**:
   - Both collectors verify whether wall-clock slot time has reached the campaign's frozen `start_ms`.
   - If invoked before start time, they log `REFUSED_PREREGISTERED_PENDING` and exit cleanly (exit code 0), preventing premature execution or SQLite state pollution.
3. **Automated Verification**:
   - Empirical validation in WSL confirmed that invoking `systemctl --user start btc-quant-forward-derivatives.service` and `btc-quant-opportunity-forward.service` resulted in zero appends and explicit refusal logs in `journalctl`.

## 4. Opportunity Collector / Resolver Parity Repair (Phase C)

An audit of the existing deployment configuration revealed a critical structural bug:
- `btc-quant-opportunity-forward.service` hardcoded `--campaign configs/forward/v0.3.20_opportunity_successor_campaign.json`.
- `btc-quant-opportunity-resolve.service` hardcoded `--campaign configs/forward/v0.3.17_opportunity_successor_campaign.json`.

This configuration mismatch caused the resolver to query a different campaign from the one being collected. In v0.3.21:
- Hardcoded campaign paths have been eliminated from both service unit templates.
- Both units now pass `--registry /root/workspace/project/Quant-agent/configs/forward/opportunity_forward_campaigns.json`.
- Both collector and resolver call `resolve_active_opportunity_campaign()` through the identical resolution code path, mathematically guaranteeing parity.
- `forward_doctor` now includes `check_collector_resolver_parity()`, which parses systemd unit `ExecStart` parameters and flags any discrepancy as `CONFIGURATION_INCONSISTENT`.
