## 2. B01 — independent trust root before any candidate import

The future implementation commit alone, or an implementer-edited checksum dictionary in that commit, is **not** the R4 acceptance authority. After a candidate is frozen, ChatGPT-1 independently enumerates and rehashes its complete R4 code/assets/tests, every repository transitive import reachable by the selected R4 entrypoint and test suite, the original 13 files, and the unchanged V1 sidecar closure. The Controller, outside the implementer's write scope, pins an exact candidate commit, independently constructed path-to-SHA-256 manifest blob, and exact trusted launcher/verifier artifact hash in a separate immutable acceptance record. Those R4 hashes and artifacts are **future identities**; none is invented or approved in this document. The manifest includes file type, path, size, hash and import-closure result; the trusted Python interpreter, standard library and test-tool environment are separately version/hash pinned. The reviewer independently compares the Controller's record to bytes and reports results; the Controller owns gate execution/acceptance. No candidate process can replace its own expected digest.

The trusted launcher/verifier runs **before** importing R4 or opening/creating its persistence root. It checks the exact commit/tree and external manifest; exact allowlisted file set with no missing or extra R4 source/asset/test files; all 13 old hashes; every regular file's bytes; no symlink, hardlink, path traversal, case-fold collision, mount/root redirection or writable import shadow; and the full static import graph including relative and transitive imports. R4's import policy allows only its pinned modules and pinned standard library; third-party imports, V1 modules, broker/order clients, network clients, importlib, dynamic loaders, eval/exec, and runtime path mutation fail. It AST-checks all R4 Python and all reachable repository dependencies for forbidden calls and protected paths, then executes from a newly sealed, private, read-only verified tree with import origins checked against that tree. It installs the trusted no-network/no-order runtime boundary before candidate import. Any verification failure is a HARD STOP, including an altered legacy guard, an edited candidate manifest, a mutable-guard bypass attempt, an extra import/file, and a root swapped between check and run. Runtime storage uses held directory descriptors and no-follow opens so its root cannot be swapped after validation. The author may add local defensive checks, but they cannot serve as trust authority.

The independent acceptance record must cover the trusted launcher/verifier and trusted receiver with its fsynced ingress-evidence log, as well as any other explicitly permitted external integration component; those components are owned and pinned by Controller/reviewer, **outside** the implementer's path allowlist. At present no external integration modification is permitted. A new external dependency, interpreter, test tool, or shared-sidecar change invalidates the trust root and needs a new exact-SHA review. This gate is a required future procedure, not a claim of mathematically zero regression risk.

## 4. B03 — append, crash recovery, checkpoint, and ACK durability

R4 uses a single-writer, append-only WAL as the **authoritative** record. On first creation, the trusted launcher validates the storage parent, creates root and checkpoints directories with no-follow exclusive operations, fsyncs created directories and their parents, writes/fsyncs the WAL header file, then fsyncs its parent directory before any receipt. Existing roots must match their immutable header; no header recreation. All writes check short writes/errors. A funding transition is prepared from a verified state, then its complete newline-terminated POST record is appended; after_append_before_fsync is a fault hook **before** file fsync. File fsync succeeds before memory state advances. A valid record surviving an earlier pre-fsync crash is replayed and fsynced on restart before any ACK. A missing pre-fsync record is retried from authenticated receipt, producing one economic effect. Neither path may ACK before durable POST, any transport alias, and ACK_READY.

Recovery verifies the complete WAL from header through last byte: UTF-8 and strict JSON, exact version fields, newline termination, contiguous sequence, previous chain, record/event/state hashes, immutable event IDs, replayed state, journal uniqueness and settlement/transport/ACK cross-links. Any torn/corrupt tail, hash-valid but wrong state, mismatch or unexpected record causes quarantine of the **unaltered full original bytes**, durable quarantine copy where possible, and HARD STOP. If quarantine copying fails, the original WAL remains untouched and operation still stops. There is no automatic truncation, last-good-prefix resume, or financial repair without separately authorized repair. A checkpoint ahead of WAL or inconsistent with its WAL anchor likewise stops.

A checkpoint is optional acceleration and never overrides WAL. Its immutable name binds run_id, manifest_id, seq and state hash. Write a same-directory pending file exclusively, write all bytes, fsync file, close, perform atomic no-clobber rename to final name, then fsync checkpoint directory; fsync any newly created parent directory. The final checkpoint must match the WAL sequence/chain/state hash, genesis and manifest, and verify its own checkpoint_hash. Existing final name with different bytes stops. A pending temp is never an authoritative checkpoint: on restart, preserve/quarantine its bytes, compare any final counterpart, and replay WAL. If final and pending disagree, STOP; if final is absent, ignore the temp for recovery and rebuild only from valid WAL. Rename visibility before directory fsync is uncertain after a crash; either absent or valid final is acceptable, but an ahead/corrupt final stops. An orphan temp alone does not invent a cash effect. A checkpoint I/O error stops this transaction before ACK, then restart recovers from WAL. File fsync without parent-directory fsync does not establish a newly created name's durability under the relevant filesystem contract; see [Python os.fsync](https://docs.python.org/3.12/library/os.html#os.fsync) and [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html). A platform/filesystem adapter unable to prove required file and directory sync, atomic no-clobber promotion, and no-follow semantics is **unsupported** for R4 durability and must fail closed; it cannot silently fall back.

| After ACK_READY fsync, before ACK send | Resend exactly the persisted receipt on retry/restart; no new cash. |
| After ACK send, before or after ACK_EMITTED fsync | Remote delivery is uncertain; retry may resend identical receipt_id and original POST anchor. ACK_EMITTED is audit evidence only; no cash or new receipt identity. |
| Any process restart or duplicate transport | Verify full WAL and all checkpoint/ledger anchors first; only then accept retry. |

The table describes process crashes and required filesystem operations; it does not claim hardware power-loss fidelity on every filesystem. Future fault tests must distinguish process death from simulated loss of unfsynced bytes and verify both survivor and missing cases. A cash effect is either exactly one WAL-recoverable posting or an explicit fail-closed stop; no ACK is emitted for unverified or unfsynced economic state.

## 5. B04 — settlement evidence, signed cash, transport, and durable ACK

The economic key is the canonical tuple **(venue, contract, settlement_at_utc_ms, source_version)**. Venue and contract are exact registered uppercase ASCII identifiers; unknown spellings, aliases and whitespace are rejected. Its human settlement_id uses exactly VENUE:CONTRACT:YYYYMMDDTHHMMSSmmmZ, with uppercase registered identifiers and three UTC millisecond digits; parsing it must yield the same venue, contract and integer settlement_at_utc_ms. A **source-version-independent anchor** (venue, contract, settlement_at_utc_ms) maps to exactly one accepted settlement_id, source_version, economic key and fingerprint in the WAL economic ledger. Thus changing source_version or settlement_id at the same settlement is a conflict rather than a second debit. Neither transport event_id, connection epoch, retry count, arrival clock nor ACK time is in the economic key or economic fingerprint.

The economic fingerprint is a domain-separated canonical digest of the key, settlement_id, immutable authenticated synthetic Mark value and its source/version/effective_at/first-known-at provenance, settled rate value and corresponding provenance, and the **as-known** executed-fill ledger snapshot/coverage proof at settlement. The fill proof binds ordered fill IDs, signed sides/actions/sizes, execution times, first-known times, source versions, the immutable fill-ledger prefix anchor closing that window, and coverage through the settlement and uncertainty window. Later fills beyond that closed window cannot change the frozen proof; retries compare against the WAL-persisted original proof rather than recomputing it from a later ledger tail. The source witness is an authenticated synthetic fixture assertion bound to a Controller/reviewer-pinned test issuer and exact fixture bytes. The issuer's signature/attestation over the fixture blob is held outside the implementer's tree and delivered by the trusted launcher, so an author-written fixture cannot attest itself; literal strings such as SYNTHETIC_SETTLEMENT_MARK and caller-supplied known_at are not authentication. The trusted launcher verifies the external attestation and fixture identity before import; the R4 engine binds the resulting sealed evidence digest to matching WAL fill anchors. This design makes **no claim of venue-authenticated live Mark, rate or fills**. Missing, stale, unverifiable, incomplete or contradictory witness means COST_INCOMPLETE, zero cash posting and no ACK. A Mark must be positive and at most 10^12 with at most 8 fractional digits; absolute signed quantity must be at most 10^6 with at most 8 fractional digits; rate must be finite Decimal with absolute value at most 0.10 and at most 12 fractional digits. No float arithmetic. InvalidOperation, Overflow, nonfinite input, exponent/scale/magnitude violation, or failed quantization is COST_INCOMPLETE with no cash or ACK.

Each executed fill has absolute quantity greater than zero and a derived signed delta: LONG entry positive, LONG exit negative, SHORT entry negative, SHORT exit positive. Opposite-sign supplied quantity, duplicate/missing fill ID, missing TP1 or EXIT, incomplete interval coverage, or mismatch between complete fill ledger and current position fails closed. For settlement exposure, sum signed deltas with executed_at strictly before settlement_at. Any fill whose executed_at satisfies **abs(executed_at − settlement_at) ≤ 15000 ms** yields AMBIGUOUS_SETTLEMENT_BOUNDARY; exactly −15000 and +15000 fail. Completeness of the entire window must be witnessed before accepting a zero or nonzero exposure. A later CLOSED or FLAT phase does not erase pre-settlement exposure; a position fully closed before settlement has signed quantity zero. A TP1 before settlement reduces exposure; a TP1 after it does not. Zero rate still requires complete authenticated Mark, rate and fill witnesses and creates one zero-cash settlement journal row. Apply cash only at forward receipt/commit time: **cash_delta = −signed_quantity_at_settlement × mark_price × rate_fraction**, computed in a local Decimal context with precision 128 and quantized to 0.00000001 using ROUND_HALF_EVEN. Precision 128 here is a Python calculation setting, not an IEEE Decimal128 representation; invalid/overflow/quantization failures and nonzero raw cash rounded to zero are COST_INCOMPLETE. Persisted Decimal strings use the canonical trailing-zero-free form, while examples below display eight fractional cash places. This sign convention makes LONG-positive/SHORT-negative quantity explicit.

For each synthetic settlement the trusted receiver/fixture authority creates one immutable original-ingress token with exact fields ingress_schema=G1_R4_INGRESS_V2, transport_event_id, normalized_payload_hash, first_receiver_known_at_ms, receiver_id, nonce, attestation. The Controller-pinned synthetic fixture and trusted receiver's append-only ingress log retain that token outside the candidate tree; the log is file-fsynced and its parent directory synced on creation **before** forwarding to R4. The external launcher validates the attestation and exact source binding. R4 cannot mint or update the token. New transport aliases carry the same original token plus their own attempt identity and clock; the token's transport_event_id remains bound to the original POST. Its **first_receiver_known_at_ms** is copied into the first funding POST and later ACK receipt. Settled Mark and rate witnesses must have effective_at equal to settlement_at and first-known-at in the closed interval from settlement_at through first_receiver_known_at_ms. Executed-fill first-known times and a coverage attestation through the entire ±15000 ms window must be no later than first_receiver_known_at_ms; settlement_at itself must be no later than first receipt. If the R4 process dies before POST, retry must recover the same original-ingress token from that independent trusted evidence. If the original token or its trusted provenance is unavailable or its timestamp changes, COST_INCOMPLETE, no cash post and no ACK; a later retry clock cannot silently become the first receiver clock. Subsequent retries carry separate transport_received_at_ms and connection epoch, which cannot change the original first-known time or economic identity. A new funding event is sequenced at the current forward commit clock, at least max(first_receiver_known_at_ms, last_event_at); its historical settlement_at is data for exposure only. A Funding receipt after later BARs adjusts cash forward and does not insert before, recompute, or reorder those BARs or prior decisions.

The funding POST WAL record atomically persists the economic fingerprint, one cash journal row, first receipt evidence, and the first transport mapping. The WAL economic ledger maps source-independent anchor and economic key to fingerprint and original POST sequence; the original record hash is verified by storage/recovery and retained in the WAL index. The WAL transport ledger maps transport event_id to its exact normalized payload hash, economic key and fingerprint. Normalization excludes attempt-specific retry clock and connection epoch but includes the authenticated source envelope and every economic value/provenance field; a changed signed source payload under one transport ID still conflicts. Port memory is only a cache. Processing stages are **RECEIVED** (original ingress token externally authenticated and durably retained, no G1 cash or ACK), **WAL_PERSISTED** (POST or TRANSPORT_ALIAS file-fsynced), **ACK_READY** (receipt persisted and file-fsynced), then **ACK_EMITTED** (at-least-once send, optional WAL audit marker). A transport alias is **always WAL-fsynced before ACK**. Same transport ID with changed normalized payload/economics stops. Same economic key with new transport ID and identical fingerprint fsyncs a TRANSPORT_ALIAS mapping, adds no cash, and returns the same settled receipt after ACK_READY verification. Same source-independent anchor with changed Mark, rate, source version, fill proof or source-witness first-known provenance stops as FUNDING_SETTLEMENT_CONFLICT. A duplicate with the same transport ID and byte-identical normalized payload recovers the same receipt. Lost ACK, restart, replayed ACK and multiple transport epochs cannot create another journal row or change original POST sequence/chain.

The ACK_READY WAL event contains the exact immutable receipt fields from §3 and references the original POST's seq/record_hash. Recovery of a durable POST without ACK_READY appends exactly one ACK_READY before emission, without reposting cash. Its original POST anchor is fixed; issued_at_ms is taken from the trusted recovery clock before ACK_READY append, then persisted once, and receipt_id is thereafter deterministic from the complete immutable receipt. A complete valid pre-fsync ACK_READY survivor is fsynced/reused; a missing one is regenerated before any emission. Its state_hash is computed from the state *after* ACK_READY; the earlier POST state_hash never depends on later ACK or its own record_hash. ACK_EMITTED may increment administrative WAL sequence, as may TRANSPORT_ALIAS, but they do not change economic cash, journal row count, original POST sequence, original POST record hash, or receipt_id. The receipt binds the accepted original economic POST, not the latest administrative tail. The exact ACK delivery envelope reports COMMITTED only for the call that first durably creates the POST, and IDEMPOTENT_DUPLICATE for a retry/alias that finds the original POST; it also carries that attempt's transport clock and ACK_READY anchor, while the persisted inner receipt and receipt_id remain identical after ACK_READY durability. A receiver must verify receipt identity/anchors against its own expected R4 context; an unsupported or conflicting ACK is rejected.
