### 3. Stage planning

Plan the smallest number of meaningful stages.

Default rule:

`merge mechanical stages; preserve epistemic gates`

Combine:

### 3A. Bounded investigations and evidence novelty

Do not allow an unresolved audit/repair stage to recurse indefinitely.

Before authorizing a follow-up repair, provenance investigation, repeated audit or
feasibility pass, explicitly identify:

- what materially new evidence/authority is available compared with the prior pass;
- what previously unresolved question that new evidence can answer;
- the bounded scope of the new pass;
- the early-stop condition;
- the terminal route if the question remains unresolved.

Default rule:

`same question + same evidence set != another repair stage`

If no materially new evidence authority exists, prefer a terminal disposition,
alternative route or explicit fail-closed state over repeating repository archaeology.

A repair/investigation should normally be one bounded pass. Additional passes require
genuinely new evidence, a newly discovered authority surface, or a materially changed
scientific question.

Every bounded repair should have a route stop-loss:

```text
repair succeeds       -> next scientific stage
repair proves no path -> fallback/terminate
repair remains unknowable with available authority -> fail closed and change route
```

Do not optimize for completeness of governance documentation when route determination
has already become possible.

### 3B. Causal materiality and contamination scope

Scientific contamination and provenance requirements must be scoped to the actual
claim, candidate family and scientific change rights.

Do not treat generic market awareness, unrelated research, operational monitoring or
mere existence of data/results as contamination by default.

Where contamination is material, reconstruct the causal route:

```text
candidate / hypothesis family
-> outcome or candidate-aligned information
-> protected interval
-> disclosure or accessibility
-> recipient/principal
-> scientific change rights
-> plausible influence on frozen semantics
```

When historical work may overlap a new campaign, classify the relationship where useful:

- `EXACT`
- `SUBSTANTIALLY_EQUIVALENT`
- `RELATED_BUT_NON_ALIGNED`
- `UNRELATED`
- `UNKNOWN`

Unknowns fail closed only when they are material to the protected claim or gate.
Do not convert all activity in the same market, symbol or broad strategy class into
automatic contamination.

Avoid impossible universal-negative standards such as proving that no person ever saw
any related market information. Require closure of material causal exposure routes,
not proof of total historical ignorance.

### 3C. Failure taxonomy and interpretation

Always distinguish a scientific result from an inability to test or certify the result.

Useful failure classes include:

- `SCIENTIFIC_NO_GO` — a valid frozen test did not support the hypothesis;
- `TESTABILITY_FAILURE` — support/power/candidate population was insufficient;
- `PROVENANCE_AUTHORITY_FAILURE` — required source/exposure authority cannot be established;
- `PROTECTED_GATE_FAILURE` — masking, independence or lifecycle conditions are not valid;
- `IMPLEMENTATION_VALIDATION_FAILURE` — code/evidence does not satisfy the frozen semantics;
- `OPERATIONAL_INFRASTRUCTURE_FAILURE` — environment/runtime/CI prevented execution.

Do not translate governance or authority failure into a claim that alpha is absent.
Do not rescue a scientific NO_GO by relabeling it as an engineering issue after outcomes
are exposed.

### 3D. Route stop-loss and decision compression

Every long or uncertain route must define:

- why the route is worth attempting;
- the maximum number of repair/feasibility loops allowed without new evidence;
- the condition for abandoning it;
- the fallback route.

Prefer one compressed authority package when several mechanical documents answer the
same decision question.

Do not split a stage merely because separate files can be produced. Split only when
there is a genuinely separate epistemic gate, independent authority boundary or
protected-information transition.

## Authority hydration and verification budget

Binding authority is mandatory; repeatedly re-reading unchanged authority is not.

Controller Prompts should minimize executor startup cost by separating:

- identity verification;
- binding summary;
- semantic source material.

Default rule:

`verify identity cheaply; hydrate semantics only when the task actually depends on them`.

### Dispatch manifest

Every substantial executor Prompt should prefer one compact `DISPATCH_MANIFEST`
over a long list of documents to fetch.

The manifest should include only material bindings such as:

```text
repository
task_branch
dispatch_start_sha
accepted_code_sha
authority_refs:
  - path
  - blob_sha or commit_sha
  - access_mode
protected_fences
allowed_scope
forbidden_scope
expected_outputs
terminal_state
```

For each authority reference, set exactly one access mode:

- `IDENTITY_ONLY` — verify path/hash/commit identity; do not read the full file;
- `BINDING_FIELDS_ONLY` — consume only explicitly listed fields supplied in the Prompt/manifest;
- `MUST_READ` — full semantic content is necessary to execute the task correctly.

Default to `IDENTITY_ONLY` or `BINDING_FIELDS_ONLY`.
Use `MUST_READ` only when formulas, lifecycle semantics, statistical rules,
source contracts or other task behavior depend on the source text.

### Verification tiers

Use the cheapest tier that preserves correctness.

#### Tier 0 — mechanical/docs-only work

Required startup verification normally consists of:

- repository identity;
- assigned branch;
- `git rev-parse HEAD == dispatch_start_sha`;
- clean/expected worktree state.

Do not require the executor to open historical acceptance reports or evidence files
unless the task edits or reasons about their contents.

#### Tier 1 — implementation / exact-SHA validation

Additionally verify:

- accepted implementation SHA;
- expected parent/lineage where material;
- changed-file scope;
- one current Controller authority manifest.

Historical reports should be read only when a current binding field cannot be
expressed unambiguously in the dispatch manifest.

#### Tier 2 — scientific/protected gate

Require exact immutable authority for the scientific semantics that govern the gate.

Full reads are justified only for the minimal set of documents containing binding:

- candidate equations;
- source/PIT contract;
- endpoint/cost semantics;
- inference/multiplicity;
- partition/protected-access rules;
- lifecycle authorization.

Do not require unrelated handover, CI history, prior Controller prose or stale reports
merely because they exist.

### No recursive authority hydration

Executors should not recursively chase references unless the Prompt marks them
`MUST_READ` or a required binding field is missing/inconsistent.

If a referenced acceptance JSON is used only to establish lifecycle state, the
Controller should inline the necessary fields, for example:

```text
accepted_implementation_sha = <sha>
next_lifecycle_state = <state>
authorized = true
authority_ref = <path>@<blob_sha>
```

The executor verifies the identity and proceeds.

### Prefer immutable summaries over repeated full-file reads

For already accepted authority, the Controller should publish or reuse a compact
machine-readable authority manifest rather than requiring every downstream executor
to rehydrate multiple historical Markdown/JSON artifacts.

A downstream Prompt should carry forward the small subset of binding fields it
actually needs and reference the immutable source by hash for auditability.

### Fail-closed behavior

A startup mismatch in repository, branch or exact dispatch SHA remains fail-closed.

A missing optional/context-only historical document is not a reason to stop if all
binding fields and immutable identities required by the task are already present.

If a `MUST_READ` authority is missing, hash-mismatched or semantically inconsistent,
stop and report the exact missing authority instead of opening unrelated files.



## Current authority manifest contract

When several downstream tasks repeatedly depend on the same accepted lifecycle state,
prefer a compact current-authority manifest over repeatedly hydrating historical
Controller reviews, acceptance JSON, handovers and validation reports.

Recommended paths:

```text
evidence/v0.5.5/controller/A_LINE_CURRENT_AUTHORITY.json
evidence/v0.5.5/controller/B_LINE_CURRENT_AUTHORITY.json
```

Create or refresh such a manifest only when it materially reduces repeated downstream
authority hydration. Do not create manifest churn for every docs-only commit.

A current-authority manifest should contain only the fields needed to start downstream
work safely, for example:

```json
{
  "line": "A_LINE | B_LINE",
  "stage": "<current lifecycle stage>",
  "code_branch": "<branch>",
  "accepted_code_sha": "<sha>",
  "docs_authority_commit": "<sha>",
  "current_controller_authority": {
    "path": "<path>",
    "blob_sha": "<blob sha>"
  },
  "protected_state": "<state>",
  "authorized_next_stage": "<state>",
  "binding_fields": {},
  "must_read": []
}
```

The manifest is a cache of already accepted authority, not a new scientific authority
source. It must point back to immutable underlying authority by exact path/hash.

If the manifest conflicts with an immutable underlying authority artifact, the immutable
artifact wins and the manifest must be repaired.

### Downstream Prompt slimming

For routine downstream tasks, the Controller should normally provide:

1. repo;
2. task branch;
3. dispatch/start SHA;
4. accepted code SHA if relevant;
5. one current-authority manifest reference;
6. inline binding fields actually needed by the task;
7. only the minimal `MUST_READ` semantic sources;
8. allowed/forbidden scope;
9. expected outputs and terminal state.

Do not append historical links merely for completeness.

A historical authority should be included only when at least one is true:

- it contains semantics the executor must apply;
- it is required to resolve a known conflict;
- the task explicitly audits that historical authority;
- the current manifest cannot safely summarize the required binding.

### Controller verification vs executor verification

The Controller owns broad historical reconciliation.

The executor owns only the verification needed to prove that it is executing the
assigned task against the intended immutable state.

Therefore:

- Controller may inspect many historical artifacts during adjudication;
- downstream executors should not repeat that work by default;
- exact branch/SHA verification remains mandatory because it is cheap and prevents
  authority drift;
- expensive semantic re-hydration should be paid only once unless the downstream task
  genuinely depends on it.

### Context-budget principle

Treat executor context as a bounded engineering resource.

Prompt material that does not affect:

- code behavior;
- scientific semantics;
- authorization;
- fail-closed behavior;
- required evidence;
- terminal decision

should normally be omitted from the executor context and retained only by reference for
auditability.



## B-line development fast path

B-line routine implementation is an engineering workflow, not a protected scientific
authority gate. Do not impose A-line scientific exact-authority startup cost on normal
continuous B-line development.

Default binding mode for ordinary B-line implementation is:

```text
START_BINDING_MODE = CURRENT_BRANCH_HEAD
```

### Fast-path startup contract

For routine B-line implementation, startup verification is normally limited to:

1. repository identity;
2. assigned task branch;
3. clean or explicitly understood worktree state;
4. record the actual current `START_SHA`;
5. verify the accepted predecessor implementation is the current HEAD or an ancestor of
   current HEAD when a predecessor binding is material.

Preferred ancestry check:

```text
git merge-base --is-ancestor <ACCEPTED_PREDECESSOR_SHA> HEAD
```

If these checks pass, begin implementation immediately.

Do not block routine implementation merely because:

- `CONTROLLER_DISPATCH_SHA` is absent, stale or still a placeholder;
- docs HEAD advanced after the Prompt was authored;
- an immutable historical authority document was not re-read;
- current HEAD is a descendant rather than exact equality with the accepted predecessor;
- a remote branch/ref has not been fetched again after already being verified in the
  same execution session.

A missing Controller dispatch SHA in this class of task should normally be recorded as:

```text
NON_BLOCKING_DISPATCH_METADATA_MISSING
```

not as a fail-closed implementation blocker.

### Binding modes

Use one of three explicit binding modes.

#### 1. CURRENT_BRANCH_HEAD

Default for:

- ordinary B-line implementation;
- sequential B3/B4-style feature development;
- routine repairs;
- adapters;
- tests;
- non-authority documentation;
- performance work that does not alter accepted semantics.

Requirements:

- correct branch;
- acceptable worktree;
- predecessor ancestry when relevant;
- record actual start SHA.

Exact docs/controller-dispatch equality is not required.

#### 2. EXACT_CODE_SHA

Use for tasks whose purpose is to validate, audit or accept an already sealed
implementation, including:

- independent exact-SHA validation;
- security/safety review;
- release acceptance;
- performance validation of a fixed implementation;
- B-line pre-live validation;
- first enablement of real exchange mutation against a fixed implementation.

Requirement:

```text
HEAD == TARGET_IMPLEMENTATION_SHA
```

or use an equivalent detached/worktree checkout that proves the exact code identity.

#### 3. EXACT_AUTHORITY_SHA

Reserve for tasks whose correctness depends on immutable scientific or governance
semantics, including:

- A-line protected scientific gates;
- formal scientific audits;
- candidate/inference/source authority materialization;
- protected unseal operations;
- any task where using a different authority version would invalidate the scientific
  claim.

Do not promote ordinary B-line implementation to `EXACT_AUTHORITY_SHA` merely because
a Controller Prompt or acceptance artifact exists.

### Remote verification budget

Within one executor run, successful verification of an immutable commit/blob identity
is cached for that run.

Do not repeatedly fetch the same remote branch, commit or blob unless a cache-invalidating
event occurs.

Cache-invalidating events include:

- `git push`;
- `git pull`, `git fetch` when remote movement matters, or rebase;
- branch switch;
- new Controller dispatch;
- user reports an external push;
- detected authority mismatch;
- an operation intentionally mutates the remote state.

For ordinary B-line implementation, the normal remote budget is:

```text
START:
  local branch/worktree/HEAD checks
  optional one remote-head check only when remote freshness is material

DURING IMPLEMENTATION:
  no repeated remote identity checks

END:
  push
  verify final remote HEAD/final commit once
```

Do not perform remote GitHub fetches after every local exploration, test, file read or
implementation step.

### Authority consumption in fast-path tasks

Use the existing authority access modes:

- `IDENTITY_ONLY`;
- `BINDING_FIELDS_ONLY`;
- `MUST_READ`.

For routine B-line continuation, Controller should inline the few accepted predecessor
facts actually required, for example:

```text
accepted_predecessor_sha = <sha>
predecessor_accepted = true
next_stage_authorized = true
```

The executor should not rehydrate the full acceptance/review/evidence chain unless the
task semantics actually depend on it.

### Development seal occurs at the end, not the beginning

Routine development should follow:

```text
correct branch
-> record START_SHA
-> implement
-> test
-> commit
-> FINAL_SHA
-> push
-> independent validation / Controller acceptance binds FINAL_SHA
```

The strongest exact-code verification belongs at the validation/acceptance boundary
after implementation has produced a sealed candidate SHA.

Do not spend implementation time repeatedly proving a docs dispatch SHA that does not
affect the code being written.

### Fast-path fail-closed conditions

Routine B-line implementation should still stop before coding when any of these are
true:

- wrong repository or wrong task branch;
- worktree contains unexplained changes that could contaminate the task;
- accepted predecessor is not in current ancestry when ancestry is required;
- a task-critical `MUST_READ` semantic authority is missing or conflicting;
- the Prompt requests a protected scientific action or real-exchange mutation that is
  not authorized;
- current code state materially contradicts the task assumptions.

These are substantive blockers. Missing redundant dispatch metadata is not.



## Content-visibility and safety-compatible prompt authoring

Controller Prompts must make legitimate defensive engineering intent explicit and keep
operational scope narrow enough that downstream models do not have to infer whether the
task is authorized.

This rule is about clarity and safe execution, not weakening engineering rigor.

### Default project scope

For implementation, review and validation tasks, state the scope in concrete terms:

```text
AUTHORIZED_SCOPE =
repository-bounded software engineering for EXASHXE/btc-quant-agent-public
```

Prefer named repository paths, branches, modules, fixtures, test environments and
documented APIs over broad instructions such as "inspect the machine", "scan the
environment", "search all credentials", or "enumerate the network".

### Credentials and secrets

Prompts must never ask an executor to discover, print, recover, exfiltrate or inspect
real secrets, including:

- API keys;
- access tokens;
- private keys;
- wallet seed material;
- cookies/session tokens;
- browser credential stores;
- SSH credentials;
- cloud credentials;
- exchange secrets.

Use environment-variable names or placeholders only, for example:

```text
BINANCE_API_KEY=<provided at runtime>
OPENAI_API_KEY=<provided at runtime>
```

Tests should use mocks, fixtures, redacted values or dedicated testnet credentials
provided outside the Prompt.

Do not include secret values in reports, evidence, commits, logs or model context.

### Exchange and other side-effecting integrations

For ordinary development and review, default to:

```text
DRY_RUN
TESTNET
MOCK
READ_ONLY
```

unless the task has a separate explicit authorization for a real side effect.

When real exchange mutation is in scope, the Prompt must describe it as an
approval-gated application flow with deterministic risk checks. Do not ask the model
to improvise credentials, bypass confirmations or perform unrestricted account actions.

Keep the execution boundary narrow, for example:

```text
approved_intent_id
-> deterministic revalidation
-> authorized execution adapter
```

rather than granting a general-purpose agent unrestricted exchange control.

### Defensive review wording

When reviewing authentication, order execution, approval handling, idempotency,
permissions or secret handling, phrase the task as defensive application engineering.

Preferred wording includes:

- defensive code review;
- authorization-boundary review;
- permission and credential-handling review;
- replay/idempotency review;
- fail-closed behavior review;
- stale-approval and duplicate-action prevention;
- testnet verification;
- configuration-hardening review.

Do not ask for offensive exploitation, credential extraction, persistence, lateral
movement, evasion, destructive testing, or access to systems outside the explicitly
authorized project/test environment.

### Repository-bounded tool use

Unless a task explicitly requires otherwise, executor tool use should remain inside:

- the assigned repository/worktree;
- named documentation URLs;
- official vendor API documentation;
- local tests and project fixtures;
- approved testnet/sandbox endpoints.

Avoid broad host, filesystem, process, network or account enumeration that is not
needed to complete the code task.

### Prompt decomposition

Do not combine many unrelated high-impact concerns into one broad instruction.

Prefer bounded task descriptions such as:

```text
implement Feishu approval callback state transitions
```

or:

```text
review duplicate-order prevention in execution/intents.py
```

instead of a single omnibus task that mixes secret handling, remote system access,
security testing, live trading and infrastructure administration.

Planning, implementation, validation and live enablement should remain separate when
they involve materially different permissions.

### If a downstream response is not displayable

If a downstream model returns a content-visibility or safety-interruption message for a
legitimate project task:

1. do not repeatedly resend the same broad Prompt;
2. narrow the task to the exact repository/module/test objective;
3. remove any unnecessary request for credentials, host/network discovery or broad
   system access;
4. use mock/testnet/read-only inputs where possible;
5. separate defensive review from live side-effect enablement;
6. preserve the original engineering acceptance criteria.

Do not attempt to evade safety controls. Rewrite the task so its legitimate defensive
scope and authorized boundaries are explicit.

The stable role document should carry only durable safety and governance principles.

- live account permissions;

## Validation output hygiene and safe reporting

Independent validation must remain technically strong, but the user-visible response should report
results as bounded defensive software-engineering evidence rather than replaying a raw forensic
transcript.

This is a reporting rule, not a test-weakening rule.

### Two-layer evidence model

Keep two distinct layers:

```text
LAYER 1 — detailed machine/repository evidence
  exact tests
  fixture/state-transition details
  mock call counts
  temporary SQLite evidence
  hashes / JSON receipts
  failure reproduction details

LAYER 2 — user-visible summary
  validation identity
  PASS/FAIL
  test counts
  material findings
  affected invariant
  evidence artifact path / commit
  next lifecycle action
```

Layer 1 may remain detailed inside repository evidence, validator reports and machine-readable JSON.
Layer 2 should be concise and should not paste large low-level execution transcripts unless the user
explicitly asks for a specific diagnostic detail.

### Preferred validation terminology

For legitimate negative/boundary testing, prefer precise engineering language in Prompts and final
responses:

- `negative-case validation` instead of broad `attack` wording;
- `fixture state change` or `concurrent authority change` instead of generic `mutation attack`;
- `validation harness` instead of `probe` when describing a local test helper;
- `mock exchange side-effect call count` instead of `fake POST`;
- `credential inputs unset / not used` instead of discussing credential removal mechanics;
- `authorization-boundary validation` instead of broad offensive-security phrasing;
- `temporary disposable SQLite fixture` when database state is intentionally changed for testing.

Do not change established finding IDs merely for wording. Stable machine identifiers such as
`HIGH_RUNTIME_AUTHORITY_ASYNC_HANDOFF_STALE` may remain in evidence and authority artifacts.

### User-visible validator response

A validator's normal chat response should NOT paste:

- long shell transcripts;
- temporary `/tmp`, `/root` or executor-private filesystem paths unless needed to retrieve evidence;
- generated helper-script bodies;
- exhaustive lists of every field changed in a negative-case matrix;
- environment-variable manipulation details;
- raw HTTP request/response payloads when a mock call count is sufficient;
- repetitive low-level database update statements.

Instead summarize, for example:

```text
F02 PASS — 8 bounded runtime-authority scenarios passed.
Invalid-authority cases produced zero mock entry side effects; the valid control produced one.

Outbox authority validation: 69 checks passed across lifecycle boundaries.
Concurrent state-change cases failed closed before external analysis where required.

Evidence:
<repository evidence path / validation commit>
```

If a material finding exists, include the minimum reproduction semantics necessary to understand the
bug, but do not dump the entire validation harness into chat.

### Validation task decomposition

Prefer three bounded phases:

```text
A. repository/static/regression validation
B. bounded negative-case / concurrency / lifecycle validation using mocks and disposable fixtures
C. evidence publication and concise final adjudication
```

Phase B remains fully authorized defensive engineering inside the repository/test environment. It
must not expand into real credentials, unrelated host inspection, third-party systems or real-money
exchange actions.

### Detailed evidence preservation

Do not omit or destroy detailed evidence merely to keep the chat concise.

Where detailed reproduction evidence is necessary, store it in the designated validation artifact,
for example:

```text
evidence/.../*.json
reviews/.../*.md
validation/...@<sha>
```

Then cite the artifact identity in the final response.

Machine evidence should contain enough detail for Controller review and future reproduction while
remaining free of secrets.

### Handling a content-visibility interruption

If a legitimate repository-bounded validator completes work but the chat response encounters a
content-visibility interruption:

1. preserve the completed test/evidence results;
2. do not weaken, skip or rerun tests solely to change wording;
3. do not repeatedly emit the same raw transcript;
4. return a concise defensive-engineering summary using the Layer-2 format;
5. reference the repository evidence/validation publication for full technical detail;
6. continue to obey all authorization and safety boundaries.

Do not attempt to bypass safety controls. The goal is to report legitimate software correctness work
at the appropriate abstraction level.

### Controller prompt requirement

For independent B-line validators, Controller Prompts should explicitly state:

```text
REPORTING_MODE = CONCISE_DEFENSIVE_ENGINEERING_SUMMARY
DETAILED_EVIDENCE = REPOSITORY_ARTIFACTS
REAL_CREDENTIAL_ACCESS = FORBIDDEN
REAL_FUNDS_SIDE_EFFECTS = FORBIDDEN
NEGATIVE_TEST_SCOPE = MOCKS + DISPOSABLE_FIXTURES + AUTHORIZED_REPOSITORY_CODE
```

The executor may internally retain detailed machine evidence, but its normal final chat answer should
focus on lifecycle decision, findings, counts and evidence identity.
