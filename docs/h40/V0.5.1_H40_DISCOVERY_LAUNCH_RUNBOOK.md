## 2. Authorization preflight

The independent authorizer must require all of the following:

1. Publication validation for `0131a977...` is independently accepted, not
   merely asserted by its executor report.
2. The candidate artifact still has
   `authorization_status = PENDING_PUBLICATION_VALIDATION` until that acceptance
   is issued; it is never treated as a receipt.
3. The accepted implementation-authority V1 object reconstructs to
   `6d61054a...` and binds tested commit `d0e1fe0...`.
4. All five scientific/lifecycle identities above naturally recompute.
5. `CURRENT_EXECUTION_POLICY == RESEARCH_DISABLED_V1` and
   `ACCEPTED_EXECUTION_WRITE_AUTHORITY is None`.
6. A separately accepted, non-synthetic production implementation of
   `H40LifecycleEvidenceVerifier` is available for candidate-lock/NO-GO
   adjudication. Without it, do not authorize an end-to-end Discovery run.
7. Confirmation/F02, H39 and Final Holdout guards remain sealed.

Any failure ends preflight with no receipt and no outcome access.

## 4. Durable Discovery authorization

Construct the production service only from the exact accepted implementation
authority object and the separately accepted production scientific verifier:

```python
service = H40LifecycleAuthorityService.production(

    evidence_verifier=accepted_production_evidence_verifier,
)
discovery_authority = service.authorize_discovery(
    implementation_authority=accepted_implementation_authority,

    seal=seal,

store = H40LifecycleArtifactStore(REPO_ROOT)

    discovery_authority.receipt_hash,
    discovery_authority,
    service=service,
```

`CANONICAL_AUDIT_TIMESTAMP` must be exactly `YYYY-MM-DDTHH:MM:SSZ`. It is
hash-bound audit metadata, not freshness authority. There is no run nonce and
no caller-selected run ID.

Before reading any outcome, restore/reverify the committed current head using
the production persistence context, then advance an
`H40LifecycleStateMachine` with that reverified
`VerifiedLifecycleAuthorization`. The durable head—not the caller's in-memory
object—is the commit point.

## 5. First outcome-bearing read

Only after Section 4 succeeds may the Discovery engine read the accepted
`WF1_CALIBRATION` outcome-bearing inputs. It must evaluate exactly the sealed
18-row REGISTERED universe. No source, slot, family, parameter or metric may be
added after the read starts.

Discovery must emit one canonical `H40_DISCOVERY_RESULT_EVIDENCE_V1` whose
candidate entries exactly equal the sealed roster, ordered by ascending
structural configuration hash. Every entry binds:

- run, roster, source/split and authorization lineage;
- slot hash/index and structural configuration hash;
- accepted family and complexity;
- complete hard-gate input evidence;
- separate Precision and Net Expectancy correction input evidence;
- complete candidate-result scientific input evidence.

The correction manifest must bind the complete roster and accepted
`DISCOVERY_SELECTION_V1` content hash.

## 6. Deterministic selection and termination

The production verifier must recompute, never trust caller claims:

1. complete evidence and exact roster membership;
2. every accepted hard gate;
3. within-family max-stat correction over REGISTERED rows of that family,
   separately for Precision and Net Expectancy;
4. cross-family Holm over family representatives;
5. the final order:
   - pass every hard gate;
   - highest adjusted LCB Net Expectancy;
   - highest adjusted LCB Precision;
   - lower complexity;
   - ascending structural configuration hash/configuration ID.

If exactly one winner is derived, issue and durably commit
`H40_RECEIPT_CANDIDATE_LOCK_V2`, producing `H40_CANDIDATE_LOCKED`.

If no candidate passes, evidence is incomplete/misbound, or an accepted gate
fails in a way requiring termination, issue the accepted
`H40_RECEIPT_TERMINATION_V2` and commit `H40_NO_GO` or `NOT_TESTABLE` as
appropriate. Both states are absorbing.

There is no runner-up promotion. A selected candidate that later fails cannot
be replaced under the same run.

## 7. Later WF and Confirmation boundary

If and only if a candidate is durably locked, later WF authority uses exactly:

```text
WF1 -> WF1_VALIDATION
WF2 -> WF2_VALIDATION
WF3 -> WF3_VALIDATION
WF4 -> WF4_VALIDATION
```

Each fold must remain bound to the same candidate, run, split and attestation.
Confirmation is not a fifth fold.

```text

```

remains prohibited by F02. This runbook grants no Confirmation, H39, Final
Holdout or execution capability.

## 8. Abort and rollback rules

Before the first outcome read, any mismatch means delete no evidence and issue
no receipt; stop fail-closed. If a receipt was fully published but its durable
head did not commit, it is an uncommitted orphan and grants no authority.

After the durable Discovery head commits, do not mutate or reuse its run
authority. If current active-source truth disappears, revalidation fails and
the run cannot advance. A later accepted source snapshot requires a new seal
and new deterministic run authority; it cannot expand the old run.

After Discovery begins, preserve all canonical evidence. Terminate through the
accepted receipt path. Never rewrite results, unlock slots, change thresholds,
promote a runner-up, or fall back to a legacy receipt mirror.
