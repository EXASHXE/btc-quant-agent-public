# Quant-Agent v0.5.5 — B-Line Gemini Execution Standard

## 0. Purpose

This document defines the default execution discipline for the Tactical Policy B-line when the implementation executor is Gemini.

The B-line uses Gemini for most implementation and validation work because execution quota is normally allocated there. Therefore Controller prompts must compensate for model variability by making the contract explicit, mechanically checkable, fail-closed, and narrow in scope.

This standard applies to B-line work only. It does not change A-line model routing or scientific authority.

## 1. Roles

Controller / Reviewer:

`ChatGPT-0 Primary Controller + Reviewer`

Default B-line executor:

`Gemini 3.8 Flash`

Independent high-value audit, only when justified:

`Astra`

Operating rule:

`Controller freezes semantics; Gemini implements exactly; Controller verifies remote state; executor prose is never authority.`

## 2. Mandatory Prompt Shape

Every substantive B-line Gemini Prompt must explicitly contain all of the following:

1. exact repository;
2. exact target branch;
3. exact start SHA;
4. expected parent or ancestry invariant where relevant;
5. Controller dispatch SHA for docs work;
6. objective in one sentence;
7. authority precedence;
8. allowed files;
9. forbidden files;
10. frozen semantics;
11. required implementation steps in order;
12. adversarial tests;
13. regression tests;
14. static/type gates;
15. full-suite gate when practical;
16. scientific/A-line isolation fence;
17. execution-safety fence;
18. machine-evidence schema;
19. commit/push rules;
20. fail-closed conditions;
21. exact terminal lifecycle state;
22. exact final-response schema.

A Prompt missing any material item above is not considered dispatch-ready.

## 3. Execution Discipline

Gemini must execute in ordered phases and may not collapse them:

```text
PHASE 0  PRECHECK
PHASE 1  READ/FREEZE
PHASE 2  IMPLEMENT OR VALIDATE
PHASE 3  FOCUSED TESTS
PHASE 4  REGRESSION / STATIC / TYPE
PHASE 5  FULL SUITE
PHASE 6  FENCES
PHASE 7  EVIDENCE
PHASE 8  COMMIT/PUSH
PHASE 9  REMOTE SELF-VERIFY
PHASE 10 FINAL REPORT
```

If a phase fails, later authority-producing phases must not proceed unless the Prompt explicitly defines a repair loop.

Do not infer permission from the next-stage roadmap.

## 4. Precheck Requirements

Before any edit or validation, record:

- `pwd`;
- repository remote;
- current branch;
- `git rev-parse HEAD`;
- `git show -s --format='%H %P %s' HEAD`;
- `git status --porcelain`;
- Python executable and version;
- resolved `btc_quant_agent` import path;
- relevant tool versions, at minimum `pytest`, `ruff`, and `mypy` when used.

Fail closed if:

- HEAD differs from the exact Prompt SHA;
- worktree is dirty when a clean worktree is required;
- runtime imports resolve outside the intended checkout;
- repository or branch differs;
- a required dependency/gate cannot be executed.

Do not substitute a nearby SHA or live branch HEAD for a frozen SHA.

## 5. Scope Discipline

Prompts must use explicit allowlists.

Gemini may modify only listed implementation/test/docs files plus mechanically necessary adjacent files that the Prompt explicitly authorizes.

Any need to modify an unlisted semantic file is a blocker. Report it; do not expand scope autonomously.

Never modify in B-line work unless explicitly authorized by a separate Controller decision:

- `src/btc_quant_agent/h40/**`;
- A-line H41/successor protocol authority;
- protected outcome artifacts;
- execution safety authority;
- unrelated performance infrastructure.

## 6. Semantic Freeze Rule

The Prompt must distinguish:

```text
FROZEN SEMANTICS
IMPLEMENTATION FREEDOM
DIAGNOSTICS ONLY
FORBIDDEN CHANGES
```

Gemini must not reinterpret ambiguous prose to invent new semantics.

When code and Prompt conflict:

1. stop;
2. identify the exact conflict;
3. cite file/function/line or symbol;
4. propose the smallest disposition;
5. end in a blocker state unless the Prompt already defines precedence.

## 7. Validation and Repair Separation

Default B-line rule:

`validation tasks are read-only on implementation code`.

If exact-SHA validation fails:

- do not edit implementation code in the same validation task;
- publish failure evidence only if the Prompt authorizes docs output;
- return the exact failing command/test and root-cause hypothesis;
- Controller decides whether to issue a separate repair Prompt.

This prevents an executor from validating SHA A, modifying to SHA B, and accidentally reporting A as accepted.

Implementation tasks may contain an internal test/fix loop only when the Prompt explicitly authorizes it before the implementation SHA is sealed.

## 8. Test Requirements

For each implementation task, require three layers where applicable:

### 8.1 Adversarial tests

Tests aimed directly at semantic failure modes, including:

- temporal boundary conditions;
- stale or missing data;
- malformed identities;
- duplicate/idempotent persistence;
- conflicting natural keys;
- wrong version/profile;
- incomplete coverage;
- same-bar ambiguity;
- restart/replay behavior;
- precision/rounding edges;
- unavailable upstream endpoints.

### 8.2 Focused regression

Run all B-line suites whose semantics may be touched, not only new tests.

### 8.3 Repository regression

Run the full suite unless the Prompt explicitly documents why it is impractical.

No test may be deleted, weakened, skipped, xfailed, or rewritten merely to make the stage pass unless the Controller contract explicitly requires that semantic change.

## 9. Shell and Gate Integrity

Use commands that preserve failure codes.

Recommended:

```bash
set -euo pipefail
```

Forbidden for authority-producing gates:

- `|| true`;
- swallowing stderr;
- piping through commands that lose the original exit status without `pipefail`;
- reporting only the final line while omitting a non-zero exit;
- rerunning until green without recording the first failure and repair;
- using cached/generated evidence from another SHA as if reproduced.

Every gate in machine evidence records:

```text
command
working_directory
start_head
exit_code
summary
duration_if_available
```

## 10. Machine Evidence

Every material B-line implementation/validation stage must publish machine-readable evidence.

Minimum fields:

```json
{
  "stage": "...",
  "decision": "...",
  "repository": "...",
  "branch": "...",
  "validated_or_implemented_sha": "...",
  "parent_sha": "...",
  "controller_dispatch_sha": "...",
  "workspace": {
    "pwd": "...",
    "clean": true,
    "runtime_import_path": "...",
    "python_version": "..."
  },
  "changed_files": [],
  "frozen_identities": {},
  "gates": [],
  "focused_tests": {},
  "full_suite": {},
  "a_line_fence": "...",
  "execution_fence": "...",
  "blockers": [],
  "next_lifecycle_state": "..."
}
```

Counts in prose must match machine evidence exactly.

## 11. Evidence Provenance

Evidence must bind to immutable Git identities.

Never manually type a commit SHA from memory when it can be obtained from Git.

Before publishing evidence:

```bash
git rev-parse HEAD
git show -s --format='%H %P %s' HEAD
```

The exact output must populate the evidence.

After pushing, verify the remote branch points to the expected commit.

A locally created but unpushed commit is not remote authority.

## 12. Commit Discipline

Implementation commits:

- minimal;
- stage-specific;
- no unrelated formatting churn;
- no drive-by refactor unless required;
- no generated caches, databases, credentials, local paths, or secrets.

Docs/evidence commits:

- do not mutate unrelated A-line sections;
- do not rewrite historical evidence except when explicitly repairing a documented authority error;
- preserve historical incorrect value with a correction note when auditability requires it.

## 13. Remote Self-Verification

After push, Gemini must verify:

- branch HEAD;
- commit SHA;
- parent;
- changed files;
- docs artifacts exist at expected paths.

The executor final response must distinguish:

```text
LOCAL_RESULT
REMOTE_VERIFIED_RESULT
CONTROLLER_ACCEPTANCE
```

Gemini may report only the first two.

It must never self-declare Controller acceptance.

## 14. Review Standard for ChatGPT-0

Controller review of Gemini output must independently inspect, as applicable:

1. live branch HEAD;
2. parent/lineage;
3. exact changed files;
4. diff scope;
5. frozen semantic invariants;
6. new/changed tests;
7. evidence JSON consistency;
8. report ↔ evidence ↔ Git SHA consistency;
9. CI/workflow status;
10. A-line/H40 fence;
11. execution-safety fence;
12. lifecycle transition.

High-risk claims such as test counts, exact SHAs, protected-data status, and no-execution fences are never accepted from executor prose alone.

## 15. Severity Model

Controller findings:

- `BLOCKER`: cannot accept or proceed;
- `HIGH`: must be dispositioned before next semantic stage;
- `MEDIUM`: may defer with explicit rationale;
- `LOW`: non-blocking quality improvement.

Exact-SHA mismatch, protected-scope mutation, hidden live execution, and evidence/code identity mismatch are always at least `BLOCKER`.

## 16. B-Line Model Routing

Default:

- architecture / frozen semantic contract / Controller acceptance: ChatGPT-0;
- implementation / tests / long validation / evidence production: Gemini 3.8 Flash;
- Astra: only for major statistical methodology, promotion gates, or an unresolved high-risk semantic dispute;
- Codex/GPT-6.1 Sol: optional exception when available, not assumed by the B-line operating plan.

The Prompt must remain sufficiently complete that Gemini can execute without relying on unstated Controller intent.

## 17. Governing Principle

```text
Make the task narrow enough that correctness is mechanically checkable.
Make the evidence strong enough that Controller acceptance does not depend on trust in executor prose.
```
