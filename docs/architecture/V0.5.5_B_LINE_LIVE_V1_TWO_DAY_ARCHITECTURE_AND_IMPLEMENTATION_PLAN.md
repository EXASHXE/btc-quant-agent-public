Protocol:

### ResponsesBackend — production primary

Use `AsyncOpenAI.responses.parse` or equivalent current Responses structured-output
API with Pydantic `AnalysisResultV1`.

Model ID is configuration:

`OPENAI_ANALYSIS_MODEL`

The user target is GPT-6.1 Sol where the account/API exposes that model. Do not
hard-code or silently substitute an unavailable model ID. Startup must report the
configured model identity.

One CasePackage -> one Responses request.

No model tool loop.

### CodexExecBackend — secondary

Use non-interactive:

`codex exec`

Use `--output-schema` to constrain the final result to the same AnalysisResultV1
JSON Schema.

Run with least privilege/restricted sandbox. Do not use `--full-auto`.

Codex receives:

- CasePackage;
- analysis mode;
- optionally explicitly allowlisted read-only quant evidence paths.

Codex must never receive:

- Binance API secret;
- signing credentials;
- Feishu app secret;
- order-submit capability.

### Secondary-review triggers

At minimum:

- high account exposure;
- ADD;
- REVERSE_POSITION;
- EMERGENCY_CLOSE;
- strategy/data disagreement;
- primary low confidence;
- manual Codex-review request.

## DECISION FUSION

Primary Responses result is authoritative only as an analysis input.

If no secondary review is required:

`primary_result -> RiskCompiler`

If Codex review is required:

`primary + secondary -> DecisionFusion`

Hard disagreement examples:

- opposite OPEN direction;
- OPEN vs CLOSE/REDUCE;
- ADD vs CLOSE;
- one backend emits emergency/risk invalidation and the other ignores it.

Result:

`MODEL_DISAGREEMENT -> MANUAL_REVIEW_REQUIRED`

No majority vote.

No model averaging for size/leverage.

## RISK_AND_APPROVAL_PLAN

### RiskCompilerV1

Inputs:

- CasePackageV1;
- AnalysisResultV1 / fused result;
- current AccountSnapshotV1;
- RiskPolicyV1.

Output:

`TradeProposalV1`

Risk policy includes:

- max risk USDT and max risk % equity;
- max symbol exposure;
- max portfolio gross exposure;
- max leverage;
- configured default leverage;
- max margin utilization;
- max simultaneous positions;
- daily loss limit;
- drawdown kill switch;
- staleness/spread/liquidity thresholds;
- duplicate-order prevention;
- proposal/approval TTL.

Sizing:

```text
risk_budget =
min(
  configured_trade_risk_usdt,
  equity * risk_per_trade,
  remaining_daily_loss_budget
)

loss_fraction =
stop_distance_fraction
+ estimated_fee_fraction
+ adverse_slippage_fraction
+ adverse_funding_fraction

raw_notional = risk_budget / loss_fraction

recommended_notional =
min(raw_notional,
    symbol_exposure_headroom,
    portfolio_exposure_headroom,
    configured_notional_cap)

leverage = configured deterministic leverage capped by max_leverage

if required margin exceeds margin headroom:
    reduce notional
    do not increase leverage to rescue the proposal
```

ADD_POSITION requires:

- distinct fresh CasePackage;
- distinct fresh signal/evidence identity;
- current position reconciliation;
- all portfolio risk gates;
- no loss-based averaging rule.

### TradeProposalV1

Contains:

- proposal_id/hash;
- case_id/hash;
- analysis IDs/hashes;
- risk_policy_hash;
- entry_low/high;
- stop_loss;
- TP1/TP2;
- risk_budget_usdt;
- recommended_notional;
- margin_required;
- leverage;
- estimated fees/slippage/funding;
- max_loss_usdt;
- valid_until_ms;
- allowed_price_drift_bps;
- manual_review state.

Existing webhook remains for informational notifications.

Interactive approval uses:

- Feishu Custom App;
- Bot;
- Interactive Card;
- FastAPI callback endpoint.

Card:

- symbol/direction;
- strategy;
- primary analysis;
- Codex review when present;
- entry/SL/TP;
- deterministic notional/margin/leverage/max loss;
- market/risk/data-quality evidence;
- expiry.

Actions:

- APPROVE;
- REJECT;
- MANUAL;
- REQUEST_CODEX_REVIEW.

Local SQLite is the approval authority.

Callback must bind:

- case_id;
- proposal_id;
- proposal_hash;
- callback/event ID;
- approver identity;
- decision timestamp;
- nonce/idempotency key.

Replay callback is idempotent and cannot approve a different proposal hash.
