## BLOCKER 1 — placement-time authorization/account authority is staleable

Current `submit_authorized(authorization_id, now_ms)` checks receipt expiry using the caller-supplied
`now_ms`. The caller captures that timestamp before the asynchronous/threaded submission boundary,
so a delayed call may validate against an earlier time.

The backend also compares the stored latest account snapshot hash with the receipt-bound snapshot,
but does not force a fresh account reconciliation immediately at the placement boundary.

Required invariant:

```text
actual placement-time clock
+ fresh current account authority
+ current risk/headroom
+ still-valid authorization
-> only then risk-increasing side effect
```

Classification:

`BLOCKER_PLACEMENT_GATE_USES_STALEABLE_TIME_AND_ACCOUNT_AUTHORITY`

## BLOCKER 2 — protective-stop ownership is inferred from a short prefix

Protective reconciliation currently derives/matches exchange protection using a truncated prefix:

`bqa-stop-{intent.client_order_id[:12]}`

and selects an exchange protective order with `startswith(prefix)`.

This is not a complete immutable ownership proof. Multiple intents/history on the same symbol/side
can collide semantically even if the normal case is unlikely.

Required invariant:

```text
protective exchange order
<-> exact persisted owner identity
<-> exact intent / position-side authority
```

Classification:

`BLOCKER_PROTECTIVE_ORDER_OWNERSHIP_NOT_EXACT_INTENT_BOUND`

## BLOCKER 3 — risk gate checks cap breach, not remaining loss/drawdown headroom

The validator computes current daily-loss and drawdown caps and rejects when those caps are already
breached. It also computes the proposed trade worst-case loss.

But the proposed new worst-case loss is not fully bounded by the *remaining* daily-loss and
drawdown headroom.

Required invariant:

```text
projected worst-case state after this new risk
must remain within:
  remaining daily-loss budget
  remaining drawdown budget
```

Classification:

`BLOCKER_NEW_RISK_NOT_BOUNDED_BY_REMAINING_ACCOUNT_LOSS_HEADROOM`

## HIGH 1 — runtime enable flags have multiple interpretation paths

`LiveV1Config.from_env()` parses `BTC_QUANT_LIVE_V1_ENABLED` and
`BTC_QUANT_LIVE_V1_RUNTIME_ENABLED`, while `api.create_app()` separately reads runtime flags
to decide mode/precedence.

The same runtime authority should be normalized once and consumed everywhere.

Classification:

`HIGH_RUNTIME_ENABLE_AUTHORITY_NOT_SINGLE_SOURCE`

## HIGH 2 — flat transition persistence is insufficient for reopen semantics

The runtime/supervisor maintains position-open state across observations, but a durable, explicit
flat transition must be authoritative across restart/reopen cycles.

A close-to-flat must persist the closed/flat state so a later 0 -> nonzero position is guaranteed
to emit a new `POSITION_OPENED`.

Classification:

`HIGH_FLAT_POSITION_TRANSITION_NOT_DURABLY_AUTHORITATIVE`

## HIGH 3 — market freshness is composite rather than component-specific

The Live V1 market observation combines mark, best bid/ask and 1m-kline information under one
observation freshness boundary.

Risk-increasing execution must not treat a fresh mark update as proof that book or kline data is
also fresh.

Classification:

`HIGH_MARK_BOOK_KLINE_FRESHNESS_NOT_SEPARATELY_PROVEN`

## HIGH 4 — deterministic identifiers are generated but not fully canonical-verified

The builder derives deterministic `intent_id`, `idempotency_key`, and `client_order_id`, but
the immutable model validation primarily verifies the overall intent hash.

A locally supplied noncanonical identity can therefore be structurally valid if the whole payload
is self-consistent.

Classification:

`HIGH_EXECUTION_IDENTITIES_NOT_CANONICAL_RECOMPUTED_ON_VERIFY`

## HIGH 5 — already-submitted reconciliation can be blocked by new-entry rules

Reconciliation of an already claimed/submitted intent must discover and reconcile exchange state
before applying rules that only govern *new* risk entry.

Current reconciliation authority paths still reuse checks that can reject stale/expired approval
or executable conditions before querying the existing exchange order.

Classification:

`HIGH_ACTIVE_ORDER_RECONCILIATION_ORDERING_CAN_DROP_STATE_RECOVERY`
