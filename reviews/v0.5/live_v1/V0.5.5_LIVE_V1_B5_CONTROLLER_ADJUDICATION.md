## Reproduced BLOCKER 1 — executable TradeIntent can diverge from approved proposal

`PreExecutionValidator` verifies:

- intent self hash;
- proposal/case identity;
- approval identity/hash;
- account/risk/environment gates.

However it does not recompute the deterministic approved executable fields and compare them to
the submitted intent.

A caller can construct a new internally self-consistent TradeIntent whose:

- quantity;
- price;
- leverage;
- order_type;
- stop_loss;
- take_profit fields

diverge from the approved proposal while retaining the approved proposal/case/approval hashes.

Re-hashing the forged intent makes its own `intent_hash` valid, and the current validator does
not prove that those executable fields are the deterministic compilation of the approved proposal.

Classification:

`BLOCKER_APPROVAL_EXECUTABLE_SEMANTICS_NOT_BOUND_TO_INTENT`

This is a risk-cap / approval-authority bypass.

## Reproduced BLOCKER 2 — TESTNET backend accepts unproven raw intent authority

`TestnetExecutionBackend.submit_intent(intent, now_ms)` accepts a TradeIntent object directly.

The backend validates client TESTNET capability and local clientOrderId idempotency, but does not
load the intent from `IntentStore`, does not require a persisted approval-derived execution
authorization, and does not prove that the supplied object passed the current PreExecutionValidator.

Therefore a syntactically valid forged intent can reach:

- margin-type mutation;
- leverage mutation;
- order submission path

without persisted approval authority.

Classification:

`BLOCKER_BACKEND_SIDE_EFFECT_BOUNDARY_ACCEPTS_UNAUTHORIZED_INTENT_OBJECT`

The public/coordinator entrypoint correctly accepts `intent_id`, but the actual exchange-mutation
backend remains directly reachable with a raw intent object. The side-effect boundary itself must
be fail-closed.

## Reproduced HIGH — stale outbox lease owner can continue after failed guarded freeze

R1.2 correctly added frozen PositionCase JSON/hash before external analysis.

However the guarded UPDATE that freezes the PositionCase uses `event_id + lease_token` but does
not check `cursor.rowcount == 1`.

If the lease expires and another worker claims the row, the stale worker can:

1. attempt the guarded freeze;
2. update zero rows;
3. continue anyway;
4. call `analysis_service.analyze_case(pos_case)`.

Classification:

`HIGH_STALE_OUTBOX_LEASE_OWNER_CAN_CROSS_EXTERNAL_ANALYSIS_BOUNDARY`

A stale worker must prove current lease ownership immediately before any external/downstream call.

## Reproduced HIGH — B4 operational services are not wired into application lifecycle

The repository contains B4 component implementations for:

- AccountWatch / user stream;
- REST reconciliation;
- MarketStreamService;
- LiveExecutionService;
- PositionSupervisor.

But the actual Live V1 application startup in `api.py` only constructs the Day-1
`TacticalLiveService`, Feishu callback app and decision router.

No production-like application lifecycle starts/stops the B4 account stream, account reconciliation
loop, live market stream, execution coordinator, or supervisor recovery/drain loop.

The CLI/legacy QuantService also do not provide a separate B4 runtime entrypoint.

Classification:

`HIGH_B4_OPERATIONAL_RUNTIME_LIFECYCLE_NOT_WIRED`

Component tests/E2E harness do not substitute for runtime service ownership, clean shutdown,
restart recovery, and explicit TESTNET opt-in wiring.
