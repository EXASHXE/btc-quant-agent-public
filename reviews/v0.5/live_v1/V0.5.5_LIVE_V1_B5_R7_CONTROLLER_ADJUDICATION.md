## Accepted material finding

`R7-V5-REPLACE_COMPLETION_FABRICATION` — BLOCKER

The finding is accepted as a real durable-authority bypass.

R7 protects `analysis_completed` with an UPDATE-specific trigger and protects dispatch DELETEs, but the shared SQLite connection does not enable `PRAGMA recursive_triggers=ON`. Under SQLite REPLACE semantics, an `INSERT OR REPLACE` can delete the conflicting row implicitly without firing the delete trigger when recursive triggers are disabled, then insert a replacement row. The validator reproduced `state=DONE` and `analysis_completed=1` with no admission, no provider call, and blank authority fields.

This is not merely a test-harness artifact. The completion marker is intended to be durable authority and must not be fabricable through an alternate SQLite write form.

## R8 scope

Authorize one bounded repair:

`LIVE_V1_B4_B5_FINDINGS_REPAIR_R8_COMPLETION_FABRICATION_SEAL`

Required invariant:

> No SQL write form available through the project SQLite connection may create, replace, or mutate a dispatch into `analysis_completed=1` / `DONE` unless the protected terminal authority transition authorizes it.

R8 must close both:
1. direct terminal/completion fabrication on INSERT;
2. REPLACE-style implicit deletion/reinsertion of an existing authoritative dispatch row.

Preferred defense-in-depth direction:
- shared Live V1 SQLite connections explicitly enable and verify `PRAGMA recursive_triggers=ON`, so REPLACE implicit deletes are subject to existing delete guards;
- add a dispatch INSERT guard that rejects terminal/completed/admitted authority state on initial insert, while preserving the legitimate blank `PENDING` creation path;
- retain the existing UPDATE completion capability/terminal transaction.

Equivalent narrower mechanisms are allowed if they prove the same invariant.

Do not redesign R7 admission, provider, terminal, runtime, execution, REST, or scientific semantics.
