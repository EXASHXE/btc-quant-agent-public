## Findings

### B5R4-01 — BLOCKER: PENDING recovery promotes protection without exact-ID confirmation

Protective POST returns owned-stop; exact-ID query fails; owner is PENDING_CONFIRMATION. Restart with an otherwise matching openAlgoOrders listing while exact-ID query remains unavailable. Recovery returns owned-stop and writes ACTIVE without retrying query_protective_order. A listing with algoStatus omitted is also accepted via implicit NEW.

Violates the mandatory authoritative exact-ID query before atomic ACTIVE invariant. Aggregate listing becomes installation authority after an uncertain placement.

Evidence: test_independent_protection_contract.py::test_pending_restart_requires_successful_exact_id_query (2 failing safety assertions); protection/test_independent_protection_probe.py::test_pending_restart_promotes_from_open_list_without_exact_query (2 observed-behavior cases).

Limit: No duplicate placement was observed, and the kill switch remains latched from the initial uncertainty. No network or real-money write was exercised.

### B5R4-02 — HIGH: Confirmation ignores explicitly different protective execution settings

POST requests workingType=MARK_PRICE, priceProtect=TRUE, closePosition=false, algoType=CONDITIONAL. Exact-ID query returning CONTRACT_PRICE, priceProtect=false, closePosition=true, or algoType=OTHER is accepted and persisted ACTIVE.

Matching numeric trigger price alone does not establish the requested stop trigger source or full execution contract.

Evidence: test_independent_protection_contract.py::test_exact_confirmation_must_preserve_submitted_stop_semantics (4 failing safety assertions).

Limit: Fake responses demonstrate missing validation, not that Binance normally changes submitted fields.

### B5R4-03 — HIGH: Flat reconciliation discards unresolved remote stop identity

After POST success/query uncertainty leaves PENDING_CONFIRMATION with exchange_id, a flat position and empty aggregate listing cause RELEASED and exchange_id=NULL without exact-ID absence or cancellation confirmation.

Durable exact stop authority is lost under uncertainty; later reconciliation ignores the RELEASED owner.

Evidence: test_independent_protection_contract.py::test_flat_position_must_retain_unresolved_exact_stop_identity.

Limit: The position is flat, kill remains latched, and orphan-stop impact requires a stale/inconsistent listing plus later risk reenablement. No immediate excess exposure or duplicate submit was proved.

### B5R4-04 — HIGH: Runtime startup/readiness admits wrong or invalid account snapshot

A hash-valid TESTNET snapshot for OTHER_ACCOUNT is accepted at startup and sets accepting_risk=true. Readiness also accepts a failed snapshot.verify(), and execute_intent delegates before poll_positions applies the authority check.

Runtime readiness/status and task admission do not consistently use verified configured account authority; REST loop may reenable risk.

Evidence: position/test_independent_position_probe.py (4 failing runtime safety assertions).

Limit: Actual validator verifies the snapshot and matches intent account/environment; backend obtains fresh matching REST authority before placement. Wrong-account exchange placement was not established.

### B5R4-05 — HIGH: Outbox dispatch symbol is not bound to verified position event

Change only pending dispatch row symbol BTCUSDT to ETHUSDT, preserving the valid BTCUSDT event payload/hash. A symbol-aware fresh case provider returns ETHUSDT; dispatch analyzes an ETHUSDT PositionCase linked to the BTCUSDT event hash and marks DONE.

A corrupted persisted dispatch row can break event-to-case frozen symbol identity.

Evidence: position/test_independent_position_probe.py::test_dispatch_rejects_symbol_mismatch_between_event_and_outbox.

Limit: Requires corrupt/modified SQLite row. Ordinary supervisor writes matching symbols. Wrong-symbol analysis is proved; exchange placement is not.
