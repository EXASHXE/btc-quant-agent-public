## 4. R2-F04 — service authority lifetime

Production service authority configuration is write-once after construction. More importantly, every authoritative operation independently rechecks stored production authority against the current in-process accepted constants.

At minimum this applies to Discovery authorization, predecessor use, revalidation, persistence and cold restore.

A service created under a superseded implementation authority fails new authoritative operations.

Hot authority republication inside a running authoritative process is unsupported. A publication represents a new executable governance identity and requires process/service recreation.

Synthetic service construction remains explicitly isolated.

## 5. R2-F02 — exact source bytes to economic values

The verifier re-extracts economic rows from the exact source bytes already bound by source record, validation receipt, runtime source/split authority and runtime seal.

New canonical provenance identity:

```text

```

It contains `H40_SOURCE_VALUE_EXTRACTION_V1` and `H40_CAUSAL_PREFIT_RECONSTRUCTION_V1`.

For every source required by the sealed REGISTERED roster:

1. require canonical source record and verified receipt;
2. recheck exact file SHA-256;
3. use the receipt's verified timestamp field;
4. require unique sorted 1h UTC rows;
5. extract `open/high/low/close`;
6. accept only finite IEEE-754 binary64 economic values;
7. use canonical `repr(float_value)` decimal strings for row hashing;
8. enforce positivity and OHLC geometry;
9. hash ordered canonical economic rows;
10. compare the derived identity with source-derivation evidence.

Current H40 V1's sealed roster is ETH_ONLY D1/D2/D3. Any active source without an accepted economic adapter is `NOT_TESTABLE`.

## 10. Required regression plan

F01:
- no accepted controller authority => Discovery refuses;
- economic/outcome reads occur only after controller/run-grant validation;
- matching authority+grant is limited to exact run/source/split and WF1 Training/Calibration;
- absent/foreign/superseded grant refuses;
- cold restore rechecks authority and grant.

F04:
- fresh service accepts only current implementation authority;
- historical implementation authority refuses at every authoritative boundary;
- long-lived service rechecks current in-process accepted anchor;
- persistence/restore cannot revive stale authority;
- synthetic authority remains isolated.

F02:
- canonical synthetic parquet bytes independently reproduce exact economic-row identity;
- non-derived economic identity refuses;
- stale source/extraction pair refuses;
- cold replay yields identical extraction identity;
- source without accepted adapter is NOT_TESTABLE.

F03:
- active D1/D2/D3, R_VOL and O_RANGE outputs match R3R2;
- later observations cannot alter earlier prefit rows;
- `close_time == decision_t` is unavailable;
- 720-hour lookback reserve supports early decisions without joining the denominator;
- derivative cache invalidates on causal-input identity change;
- retrospective calibration remains regression-equivalent.

All six P3B closure suites, verifier behavior/identity seals, durable lifecycle tests, protected-surface tests, execution tests, static gates and full pytest remain required.

## 11. Implementation staging

Use two implementation stages.

### Stage A — F01 + F04 authority/lifecycle

Implements lifecycle V5, controller authority/run-grant typed objects, Discovery receipt V3, persistence context V2, service lifetime revalidation and synthetic isolation.

During Stage A both production acceptance constants remain `None`, so no real Discovery can become authorized.

### Stage B — F02 + F03 provenance/PIT

Implements:

```text
H40_SOURCE_VALUE_EXTRACTION_V1
H40_P3B_SOURCE_DERIVATION_V2
H40_CAUSAL_PREFIT_RECONSTRUCTION_V1
H40_P3B_RAW_DECISIONS_V2
```

and direct verifier reconstruction from sealed source bytes using accepted R3R2 formulas.

Do not republish implementation authority after Stage A alone.

After A+B:

```text
combined exact-SHA validation
-> content-addressed evidence
-> controller implementation acceptance
-> new lifecycle implementation authority publication
-> focused Astra re-audit
```

Only after Astra closes F01-F04 may a real `H40_P3_CONTROLLER_AUTHORITY_V1` be issued and published.
