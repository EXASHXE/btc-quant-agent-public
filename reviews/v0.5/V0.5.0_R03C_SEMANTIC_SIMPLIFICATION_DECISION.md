## C1 — Retain historical directional rejection

### Producers, consumers and classification

Current facts at this exact HEAD:

- `configs/research_registry.json:27-68` contains two components,
  `trend_pullback_opportunity` and `breakout_retest_opportunity`, each with
  `role=OPPORTUNITY`, `research_status=SUPPORTED_MOVEMENT`,
  `runtime_eligibility=ANALYSIS_ONLY`, and `legacy_directional_role=REJECTED`.
- Producer: the versioned, curated component registry JSON. No current code
  synthesizes a rejected directional conclusion from movement support.
- `research_registry.py:56,80,83-97` admits the optional field and preserves it in
  `RegistryComponent`. It is not an enum-validated input or a separate admission
  guard in `validate()`.
- `cli.py:406-410` serializes the full component with `asdict` for the component
  lookup command: an actual current public consumer of the historical field.
  `ResearchRegistry.status()` deliberately exposes a smaller view and does not
  include it. Omitting it from that view does not make the underlying field dead.
- `engine.py:218-234` admits movement detectors through present role/status/
  eligibility; `execution/service.py:62-94` independently requires a qualified
  direction engine. Neither uses the legacy field as a formal promotion token.

| Relevant fields | Classification and owner |
| --- | --- |
| `legacy_directional_role` | `LEGACY_HISTORICAL_SEMANTIC`; also a `PERSISTED_REPRODUCIBILITY_COPY` of the rejected interpretation. Not a current runtime admission check. |
| `component_id`, `component_type`, `feature_family`, `role`, `version` | `AUTHORITATIVE_INPUT` within operational component selection; not formal experiment identity or P5 authority. |
| `research_status`, `runtime_eligibility` | `AUTHORITATIVE_INPUT` for operational actionability, with validation constraints. Movement support does not imply directional support. |
| `state`, `reason`, hypothesis/version/dataset lists, development window/reuse count, `last_updated` | `LEGACY_HISTORICAL_SEMANTIC` / `PERSISTED_REPRODUCIBILITY_COPY`; provenance and descriptive state, not immutable formal attestations. |
| `stopped_family`, `eligible_for_reuse` | Historical reuse restrictions/metadata; not an authorization to qualify or trade. |
| `final_holdout_accessed`, registry `final_holdout` | `AUTHORITATIVE_INPUT` to fail-closed isolation checks: accessed components and non-sealed registry are rejected. |
| `evidence_paths` | `PERSISTED_REPRODUCIBILITY_COPY` of references; `validate()` independently checks existence, not content-qualified directional evidence. |
| `actionable`, qualified direction count | `DERIVED_RECONSTRUCTION` of current role/eligibility, not of the rejected historical side. |

The two `reason` strings also describe directional rejection, and protected
historical report references remain. They are useful human evidence, but no
current parser establishes a lossless machine-readable equivalence between that
prose and `legacy_directional_role`. Moving the assertion to a new history table
would relocate rather than remove semantics and introduce a mapping/migration.

### Reproducibility and attack result

The in-memory probe loaded each current component via `RegistryComponent.from_dict`,
removed only `legacy_directional_role` from a copy, and parsed again. Both versions
had the same opportunity role and `actionable=False`; the first retained
`REJECTED`, the second had `None`. The optional schema accepts the missing field.
Therefore deletion loses a specific historical assertion without buying a new
safety property. A future reader of the typed component could incorrectly infer
that preserved opportunity evidence also preserved the prior directional claim.

Do not overstate this field: it is currently optional metadata, not an independent
B04 producer-binding or execution gate. Its removal alone does **not** make a
rejected strategy actionable or bypass formal replay. Those protections are
different authorities. Keeping it protects historical interpretation, not a
fictional enforcement check.

### Complexity/disposition

`KEEP_AS_IS`. Proposed removal saves one dataclass field declaration and a term in
the optional-key set (two touched production lines, roughly one net line removed),
plus two JSON occurrences; zero types or algorithms are retired. There is one
external production serializer directly exposing the field and no direct named
test-field assertion. Existing runtime-registry/P5/R01 test modules consume the
registry more broadly. A responsible deletion would need new historical-loss
tests and a lossless replacement representation or API migration; it removes no
current independent enforcement comparison. Runtime registry bytes and component
lookup payloads would change, although formal run hashes do not currently consume
this field. The saving does not justify that semantic/API loss.

## C2 — Keep governance separate from operational component actionability

### Two concepts, not duplicate persisted state

| Dimension | Formal P5 `ResearchContractRegistry` | Operational `ResearchRegistry` |
| --- | --- | --- |
| Producer | Explicit protocol/evidence registration and legal append-only decisions | Curated `configs/research_registry.json` component records |
| Identity unit | Content-addressed immutable `ExperimentMetadata` revision, typed evidence IDs, hash-chained `DecisionEvent` | Named component, historical version, role/status/runtime eligibility |
| Persisted state | Versioned envelope: protocols, evidence, ordered events, generation and whole-state hash | Versioned component JSON; sealed flag and maximum runtime stage |
| Mutation | Advisory lock, generation CAS, canonical bytes, atomic publication and uncertainty reconciliation | `load()`/`validate()` are readers; no corresponding append-only decision writer |
| Decision | Reconstruct lifecycle from immutable event history; dedicated artifact-bound economic qualification | Derive operational actionability and qualified direction count |
| Qualification source | Frozen protocol, local complete evidence, verified P6 run/suite/result and attestation | Not a source of formal qualification or promotion |

Exact producers/consumers:

- Formal class: `research_contract/registry.py:77-1099`; registration at 109 and
  184; transitions at 208; economic qualification at 277; reconstruction at 384;
  publication at 417; envelope/read validation at 472-562. Exported through
  `research_contract/__init__.py`. Its external production caller is
  `formal_research.py:227-300` (and the loader in the same module), which checks
  existing protocol authority, performs cold verification, and records a decision
  only when explicitly requested. Five current test modules directly reference it.
- Operational class: `research_registry.py:110-221`, loader at 224. Five external
  production caller modules: `engine.py`, `cli.py`, `service.py`,
  `execution/service.py`, `opportunity_forward.py:1013-1015`. The last checks
  campaign registry-version consistency; it does not append a P5 decision.
  Three current test modules directly reference the class. These counts exclude
  each defining module, package re-export and transitive callers.
- `research_contract/registry.py:969+` requires complete registered economic
  evidence; `_validate_economic_attestation` checks protocol/revision/code/product/
  terminal/comparison binding and cold qualification semantics. A raw generic
  `update_decision_status(...ECONOMICALLY_QUALIFIED...)` is explicitly forbidden;
  only the dedicated P6 path can produce that event.

| Relevant fields | Classification |
| --- | --- |
| Frozen protocol semantic payload: input, feature, prediction target, evaluation, policy/cost/execution/benchmark identities, product scope, code revision, terminal policy, producer contract | `AUTHORITATIVE_INPUT` for formal revision/qualification; not operational component eligibility. |
| Evidence reference: content hash, type/schema, producing revision/code, completeness, local location and identity | `PERSISTED_REPRODUCIBILITY_COPY` with `INDEPENDENT_CROSS_CHECK` against referenced immutable bytes/provenance; complete required evidence supplies authoritative inputs. The synthetic probe created an in-memory formal registry, registered a current
synthetic protocol, captured generation/hash/state, loaded the runtime registry
with zero qualified direction engines, then cold-validated the synthetic formal
qualification. Formal state remained unchanged. This is a positive separation
control, not a proof that every possible future merge is safe. Static callers and
the current P5/P6/C-lite tests establish the absence of a runtime-to-P5 promotion
bridge today.

### Options and authority risk

1. **Keep both; clarify terminology.** Say “formal protocol/evidence/decision
   registry” for `ResearchContractRegistry`, and “operational component
   actionability registry” for `ResearchRegistry`. Keep current public names.
   The name overlap is the main superficial complexity, not duplicate state.
2. **Public rename:** no semantic benefit demonstrated; at least five runtime
   caller modules and three direct test modules, or one formal caller and five
   direct test modules plus a package export, would move. Compatibility aliases
   and import churn outweigh removing zero types/fields/comparisons.
3. **Common leaf:** no genuinely equivalent duplicated status/identity/evidence
   type was found. `ResearchStatus` is not `DecisionStatus`; a shared enum would
   erase distinctions. Canonical/publication leaves already have their own owners.
   No new generic-registry base class or adapter is justified.
4. **Merge persistence/authority:** forbidden under the evidence available here.
   In particular, mapping `VALIDATED_FORWARD`, `LIVE_ELIGIBLE`, movement support,
   or the operational qualified count to a P5 economic decision would let editable
   operational state influence promotion without immutable attestation/replay.
   Co-location that preserves every branch, type, CAS and evidence check is not
   necessarily exploitable, but is not semantic equivalence or a useful reduction;
   it adds dispatch/migration coupling rather than removing it.

### Complexity/disposition and exact documentation-only boundary

`DOC_OR_NAMING_ONLY`. Actual production LOC/fields/types/comparisons changed:
**zero**. The classes are 111 and 1,023 AST lines respectively; these are footprint
measurements, not removable LOC. A merge cannot responsibly retire either state
machine or substitute one persisted schema for the other. Both use `1.0.0` schema
labels, but their envelopes are incompatible; equal version text is not authority
equivalence. A shared-container adapter would introduce a new version, conversion,
backward-compatibility and failure/transaction matrix. No defensible net LOC saving
was established, and pretending otherwise would be an unbounded architecture task.

Allowed now: this report on the docs branch only, including the terminology above.
Forbidden: public imports/names, either registry implementation, persisted records,
`src/`, `tests/`, `configs/`, workflows, goldens and protected evidence/state.
Schema/hash impact and migration policy: none; no adapter, alias or migration.
No changed tests are necessary for documentation. The fast existing CI is sufficient
for this output; no implementation worker/model is required. Any future code rename
or common-type extraction needs a new bounded prompt, preserved separation tests,
and evaluation of the full 3.11/3.12/3.13 gate; it is **not** authorized by R03C.

## C3 — Retain persisted round-trip attribution and verification

### Exact derivation, serialization, consumers and identity

- `economic/metrics.py:662-738::attribute_round_trips` attributes ordered
  `TradeEvent`s per asset/open lot, allocates entry/exit fees and funding to matched
  quantities, derives net economics and holding duration. `summarize_ledger:804+`
  calls it and computes trade counts, win/loss totals and profit-factor status.
- `SimulationSummary:237+` stores the tuple at 287, normalizes it at 296, compares
  it to re-attribution at 510-512, validates counts and net economics at 499-583,
  and serializes the array at 642 with accounting `schema_version=2.0.0`.
- `RoundTripAttribution:136+` validates timestamps, costs and net PnL and serializes
  entry/exit IDs/times, side, quantity/notionals, gross/net/fees/funding, duration,
  MAE/MFE/status and `round_trip_id`. Its content ID binds event IDs, matched
  quantity and economics; not every serialized field is in this per-trip ID.
  The containing result hash additionally binds the full serialized accounting.
- `acceptance_verifier.py:785-840::verify_formal_accounting` parses atomic events,
  derives curve/notional/drawdown from the ledger/candles, calls `summarize_ledger`,
  and requires every replay field, recursively comparing `round_trips` too. This
  is input-to-persisted-output comparison using canonical accounting arithmetic,
  **not a second independently implemented attribution algorithm**.
- `qualification.py:1755-1756,1836-1840` reads candidate/trial durations to match
  random holding distributions; `acceptance_verifier.py:1276-1320` recomputes
  matching diagnostics independently of submitted diagnostic claims.
- `qualification.py:514-542` includes the accounting in `EconomicRunResult`
  semantic payload/hash; benchmark result, random distribution, suite and
  qualification identities transitively bind those bytes. Result artifact evidence
  hashes and P5 attestations bind the published outputs too. The input run identity
  need not change merely because serialization changes, but **output identities do**.
- `execution_replay.py:56-117` reconstructs the canonical engine from bound protocol,
  dataset, decision bundle, policy/cost/execution/funding inputs, enforces expected
  candidate role and compares the full result using canonical SHA-256 equality.
  `verify_benchmark_replay:120-155` reconstructs CASH and random experiments as well.
  `formal_research.py:254-295` publishes and cold-verifies these bound artifacts.

There are two explicit external production field-reader modules (`qualification`,
`acceptance_verifier`) plus the `metrics` owner. Opaque whole-summary/result
propagation in simulator, execution replay and formal consumers is additional
real use, not zero consumers because it lacks a `.round_trips` expression.
One current test module explicitly names the field; B05/B06/B07/C-lite tests also
exercise it through full semantic payloads and persistently rehashed attacks.

| Relevant fields/layers | Classification |
| --- | --- |
| Atomic `TradeEvent` action/asset/time/price/quantity/fee/funding and ledger order | `AUTHORITATIVE_INPUT` to attribution once reconstructed by the engine; submitted event copies alone are not independent execution truth. |
| Frozen protocol, canonical candles/availability, verified signals/bundle, policy/fee/execution/funding models and terminal rules | Root `AUTHORITATIVE_INPUT` for cold execution/benchmark reconstruction. |
| In-memory `round_trips`: matched IDs/times/side/quantity/notionals/gross/net/cost allocations/duration | `DERIVED_RECONSTRUCTION` from atomic events. Not a second source of economic truth or a user-editable forecast. |
| Serialized `round_trips`, ledger/event IDs, trade events and equity curve | `PERSISTED_REPRODUCIBILITY_COPY`; compared with regenerated values as `INDEPENDENT_CROSS_CHECK`. Their derivability does not make the equality check redundant. |
| Final cash/equity/position/mark/PnL; fills/completed/win/loss/flat counts, win rate and PF/status; exposures/drawdown/return/slippage metrics | `DERIVED_RECONSTRUCTION`, persisted and reconciled against ledger/cold execution. Remove no authority merely because multiple projections describe the same economic path. |
| `round_trip_id`, accounting/result/suite/qualification IDs, evidence hashes, run/model/bundle identities | `INDEPENDENT_CROSS_CHECK` / persisted reproducibility binding. Different scopes; synchronized rehashing still must face frozen-root replay. |

PF and win/loss classification directly rely on attributed net trade economics.
Holding duration directly influences qualification comparability. Current code
does **not** implement a separate expectancy metric/gate or available MAE/MFE
series; this audit does not invent either requirement. MAE/MFE's explicit
unavailability is nevertheless part of accepted serialized bytes and replay.
A future available path metric requires its own evidence/protocol, not a field cut.

### Mutation controls and their limits

On the unchanged synthetic fixture, baseline accounting and qualification both
verified. The probe then changed only a deep copy of the accounting:

| Mutation | Current rejection |
| --- | --- |
| Remove array | `formal accounting is missing replay field: round_trips` |
| Holding duration +1 ms | `accounting.round_trips[0].holding_duration_ms disagrees with independent replay` |
| Funding allocation +1 | `accounting.round_trips[0].funding_usdt disagrees with independent replay` |
| Fabricate available path metrics | `accounting.round_trips[0].path_metrics_status disagrees with independent replay` |

All four mutated accounting hashes differed from baseline. These failures do not
depend on trusting an unchanged outer wrapper/hash. Existing B05/B06/B07/P6 tests
add the stronger fully rehashed, internally coherent forged-ledger/random/CASH
controls. No proposed new schema or compatibility adapter was implemented.

Removing the persisted array would delete at least its persisted-vs-recomputed
attribution comparison. It does not automatically eliminate canonical engine
replay of atomic events, nor prove that all forged ledgers would suddenly pass;
those remaining checks must not be conflated with the lost comparison. A fully
redesigned reconstruction-only schema could in principle retain root execution
security, but would change accepted bytes, matching readers, exact replay payloads
and artifact identities. That is precisely the unbounded migration excluded here.

### Options, complexity and disposition

1. **Persist and verify:** keep the accepted contract. Zero production LOC,
   fields/types/comparisons or migrations changed.
2. **Persist but centralize derivation/validation:** attribution is already a
   shared 77-line function, used by production summarization and verification.
   Summarization itself is shared. The small holding-mean readers are at different
   submission/verification boundaries; a helper does not retire duplicated
   authority or persisted state. No consequential net simplification established.
3. **Remove serialization and reconstruct:** one persisted array could be removed,
   but four schema-facing sites (field, normalization, serialization, summary
   construction) and downstream comparisons/metrics readers must be handled.
   The 101-line attribution type and 77-line algorithm remain necessary for
   quantities, net PF and holding matching, so counting them as deleted LOC is
   false. At least P6 explicit field/count/reproducibility tests and the full-payload
   A04/B05/B06/B07/C-lite/registry controls require examination. Schema `2.0.0`
   cannot silently lose a required replay field. Keeping old artifacts verifiable
   requires explicit version handling and old-byte/hash preservation; rewriting
   historical artifacts/attestations is forbidden. Migration cost exceeds a key.

`KEEP_AS_IS`. No current-schema deletion, attribution-type retirement, public
property replacement or verifier adapter is authorized.
