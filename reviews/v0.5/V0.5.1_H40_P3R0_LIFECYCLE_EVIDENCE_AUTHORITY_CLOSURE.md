## 3. Typed Evidence Receipts Architecture

Under this amendment, `H40LifecycleStateMachine` transitions are **evidence-gated**. State adjacency alone in `VALID_TRANSITIONS` is a necessary condition, but **never a sufficient condition**.

Every transition from state $S_A$ to $S_B$ requires a cryptographically verified, typed evidence receipt $R_{A \to B}$.

### 3.1 Standard Receipt Contract Invariants

Every receipt object adheres to the following structural requirements:
1. **Typed Schema ID**: Uniquely identifies the receipt version (e.g., `H40_RECEIPT_DISCOVERY_AUTH_V1`).
2. **Deterministic Run Scope**: Explicitly binds a `run_id` string matching the execution session.
3. **Cryptographic Lineage**: Contains `upstream_receipt_hash` referencing its immediate parent receipt in the lifecycle chain. The root receipt references `upstream_receipt_hash = None`.
4. **Canonical Preimage**: The receipt's content hash `receipt_sha256` is calculated over the canonical JSON of all required receipt fields (excluding `receipt_sha256` itself).
5. **Content-Addressable Verification**: Receipts are verified from their serialized byte contents, never from filename or directory existence alone.
6. **Strict Immutability**: Receipts are write-once. Mutation of any byte changes the content hash, breaking the lineage check of all subsequent downstream transitions.
7. **No In-Memory Bypass**: An in-memory boolean, string token, caller flag, or unverified path cannot satisfy the evidence requirement.

### 4.2 Runtime Authority Snapshot Sealing Semantics

1. **Pre-Outcome Sealing Boundary**: The runtime authority snapshot is sealed at discovery authorization time, **strictly before** any discovery runner loads features, labels, or price series.
2. **Frozen Testable Universe**: Under the sealed P1 authority snapshot (`P1_ACCEPTED_3fc89541`), exactly 18 slots have all required sources `VERIFIED` and derive status `REGISTERED`. Exactly 150 slots have at least one unverified source and derive status `NOT_TESTABLE`.

   - However, **no post-seal source promotion can retroactively alter or expand the candidate universe of an active discovery run**.
   - An active run is permanently restricted to the slots registered under its sealed `materialized_run_authority_hash`.
4. **Separation from Structural Identity**: A change in source verification state changes the runtime authority snapshot hash and the materialized run authority hash, but **never** modifies the immutable `structural_ledger_hash` or `structural_configuration_hash`.

### 5.2 Single Candidate and No-Runner-Up Rules

1. **Exactly One Candidate**: The state machine allows locking at most one candidate per run. Attempting to lock a second candidate or overwrite the lock receipt fails closed.
2. **Strict Multiplicity Control**: The selected candidate must be evaluated under the full family-wise multiple testing correction over the entire sealed discovery universe ($M = 18$ under P1), using the lexicographic tie-break:
   $$\text{Complexity} = \text{len}(\text{family\_combination}) \quad (1 \text{ before } 2), \quad \text{ascending slot\_index final tie}.$$
3. **No Runner-Up Promotion**: If the locked candidate later fails walk-forward validation or confirmation, no runner-up candidate may be promoted or substituted. The pipeline must terminate immediately in `H40_NO_GO`.

## 10. Persistence, Serialization, and Replay Defense Protocol

### 10.1 Deterministic Persistence Hierarchy

Receipts are persisted as durable artifacts on disk to prevent in-memory state manipulation and ensure auditable replayability:

```text
artifacts/h40/lifecycle/runs/<run_id>/receipts/
├── 01_discovery_authorization_receipt.json
├── 02_candidate_lock_receipt.json
├── 03_wf_validation_receipt.json
├── 04_confirmation_ready_receipt.json
└── [optional] termination_receipt.json
```

### 10.2 Content-Addressable Integrity Verification

When the lifecycle state machine restores or verifies state from disk:
1. **Schema Check**: Validates the presence and types of all required fields.
2. **Byte-Level Hash Check**: The canonical JSON of the receipt payload is re-hashed. The calculated `canonical_sha256` must equal `receipt_sha256`.
3. **Cryptographic Lineage Re-Verification**: The `upstream_receipt_hash` must match the re-computed content hash of the predecessor receipt on disk.
4. **No Trust in Paths**: Filenames and paths are informational locators. The state machine never relies on filename or directory presence alone to determine validity.

### 10.3 Replay and Anti-Tamper Invariants

1. **Idempotence**: Providing the identical valid receipt for an already-achieved state is idempotent and re-confirms the state.
2. **Replacement Prohibition (Write-Once)**: Once a receipt file is written for a given transition in a `run_id`, attempting to overwrite it with different contents raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT)`.
3. **Cross-Run Replay Defense**: Receipts bind `run_id` and `materialized_run_authority_hash`. Presenting a receipt from `run_001` to authorize a transition in `run_002` raises `CONFIG_IDENTITY_CONFLICT`.
4. **Cross-Candidate Replay Defense**: Validation receipts bind `locked_structural_configuration_hash` and `locked_slot_index`. A validation receipt created for Candidate A cannot be presented to authorize Candidate B.
5. **Fail-Closed on Stale Receipts**: Any receipt whose timestamp is in the future, whose upstream receipt hash fails lineage matching, or whose commit SHAs do not match the environment fails closed immediately.

## 11. Adversarial Implementation Acceptance Criteria

When `H40-FSA-F01` is implemented in Python, the test suite must prove immunity against adversarial bypasses via the following 12 synthetic/governance tests:

1. **Adjacency Alone Cannot Enter Discovery**:
   - Calling `transition_to(H40_DISCOVERY)` without presenting a valid `H40DiscoveryAuthorizationReceipt` raises `H40GuardError(H40ReasonCode.NOT_TESTABLE)`.
2. **Forged Protocol/Ledger Hashes Fail Discovery Entry**:
   - Presenting an authorization receipt with an altered `structural_ledger_hash` or `protocol_authority_hash` raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT)`.
3. **P2 Acceptance Mismatch Fails Discovery Entry**:
   - Presenting a receipt referencing an unapproved P2 acceptance commit or mismatched P2 artifact SHA raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT)`.
4. **Runtime Source Mutation Preserves Structural Identity**:
   - Simulating promotion of a source from `NOT_TESTABLE` to `VERIFIED` generates a different `materialized_run_authority_hash` but leaves `structural_ledger_hash` and `semantic_root_hash` byte-for-byte identical.
5. **Post-Seal Source Promotion Cannot Unlock Candidates**:
   - In an active run with a sealed snapshot, mutating global source state after the seal timestamp does not expand the testable candidate slots beyond the sealed 18 REGISTERED slots.
6. **Candidate Lock Rejects Foreign Run or Altered Configuration**:
   - Presenting a candidate lock receipt with a mismatched `run_id` or an altered `selected_structural_configuration_hash` raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT)`.
7. **Validation Receipt From Another Candidate Fails Transition**:
   - Attempting to authorize `H40_WALK_FORWARD_VALIDATED` using a receipt corresponding to a different candidate slot or foreign split manifest raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT)`.
8. **Confirmation-Ready Strictly Denies Outcome Access**:
   - In state `H40_CONFIRMATION_READY`, invoking `H40ConfirmationGuard.assert_outcomes_accessible()` strictly raises `H40GuardError(H40ReasonCode.CONFIRMATION_NOT_READY)`.
9. **Caller Primitive Token Cannot Satisfy Evidence Gate**:
   - Passing `True`, `"AUTHORIZED"`, a dummy dictionary, or a path string to `transition_to()` raises `H40GuardError` / `TypeError`.
10. **Receipt Mutation Breaks Lineage Verification**:
    - Mutating a single character in `01_discovery_authorization_receipt.json` invalidates `upstream_receipt_hash` checks in `02_candidate_lock_receipt.json`, halting lifecycle verification.
11. **Stale / Cross-Run Replayed Receipts Fail Closed**:
    - Copying a valid receipt from a previous run directory into a new run directory is detected as a foreign `run_id` and fails closed.
12. **Scientific P2 Hashes Remain Byte-for-Byte Unchanged**:
    - A dedicated test verifies that `protocol_authority_hash`, `semantic_root_hash`, and `structural_ledger_hash` match their published expected values exactly.
