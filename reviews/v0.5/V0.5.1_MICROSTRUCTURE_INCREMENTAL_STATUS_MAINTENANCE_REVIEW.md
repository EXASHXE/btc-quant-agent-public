## 3. Blocking finding — warm cache can bypass active deep audit

The production cache-hit condition allows an active partition to reuse cached stats during deep_integrity=True because the condition contains `not deep_integrity or not is_finalized or cached integrity is True`. For an active partition, `not is_finalized` is True, so a cache populated by ordinary status can be accepted by a later explicit audit.

Real operational sequence affected:

ordinary status -> cache populated -> explicit audit

In that sequence, active PRAGMA quick_check can be skipped.

The current P05 test covers only deep audit against a cold cache, so it misses this path.

There is also an observability defect: status_performance.active_quick_check_executed is currently assigned from the requested deep_integrity flag rather than from whether a quick_check actually executed. A warm-cache audit can therefore report True without doing the verification.

This is an acceptance blocker.

Required repair: deep audit must bypass the ordinary active-partition stats-cache fast path (or otherwise prove an actual active quick_check), track actual quick-check execution, and add a warm-status -> deep-audit regression test with SQLite trace evidence.

## 5. Pytest runtime regression

The new test file adds roughly 900 lines. Static hotspots include: P01 doing 100,000 Python-level SQLite execute calls; the independent reference helper enumerating one-second buckets over full synthetic days; P11-P15 repeatedly rebuilding/finalizing partitions and running brute-force equivalence; and cold finalized-summary construction enumerating 86,400 one-second buckets per full finalized day.

These are plausible contributors to the reported >8 minute suite time, but optimization must be profile-driven.

Capture before changes:

- /usr/bin/time -v python -m pytest -q --durations=50 --durations-min=0.25
- python -m pytest -q tests/test_microstructure_status_incremental_performance.py --durations=0

Where practical, time the parent b653a2e... suite on the same host/interpreter to attribute the regression.

Preferred optimizations: bulk/streaming SQLite insertion for the 100k test; shorter synthetic observation windows where a full day is not part of the asserted contract; campaign starts near day boundaries for cross-midnight/partial-day semantics; removal of redundant cold-cache rebuilds while preserving independent assertions; no sleeps where deterministic fingerprint changes suffice.

Do not gain speed by deleting assertions, xfail, globally skipping the semantic suite, weakening integrity/audit semantics, or touching H40 science.

A dedicated slow/scale tier is acceptable only if the default suite retains a bounded semantic equivalent and the scale test remains an explicit acceptance gate.

Performance target: at least 40% wall-time reduction from the captured current baseline, with preferred full pytest wall time below 5 minutes on the same host. If the baseline is dominated by pre-existing tests, report attribution honestly and optimize only the maintenance regression.
