## 2. Same-type verifier behavior seal

The reviewed implementation closes the previously identified exact-type substitution path using multiple independent barriers.

### 2.1 Instance behavior shadowing

`H40ProductionDiscoveryEvidenceVerifier` now uses `__slots__` and has no normal instance `__dict__`.

Instance-level replacement of reviewed entry points such as:

```text
verify_discovery_manifest
verify_candidate
verify_wf_fold
```

therefore cannot be installed as arbitrary per-instance attributes.

### 2.2 Write-once authority-bearing state

The following fields are write-once through normal assignment:

```text
_resolver
_seal
_receipt
_split
```

The evidence resolver separately makes its approved evidence root write-once.

### 2.3 Constructor-completion binding

Normal construction records an out-of-object binding in a `WeakKeyDictionary` containing the exact resolver/root, seal and seal context, Discovery receipt identity, split authority and split content hash.

An `object.__new__(H40ProductionDiscoveryEvidenceVerifier)` object or a partially initialized object is absent from that constructor binding and therefore fails closed.

### 2.4 Transitive authority-state integrity

`assert_runtime_integrity()` checks not only direct field identity but also:

- resolver exact type and approved root;
- runtime seal authority-context hash;
- hashes and identities of runtime seal source/split/attestation contexts;
- runtime seal repo-root context;
- Discovery receipt identity/hash;
- split object identity and canonical content hash;
- split hash equality to the runtime seal;
- optional lifecycle-provided seal/receipt binding.

This covers the previously identified risk where class-bound method dispatch alone would still trust substituted collaborators.

### 2.5 Reviewed class method dispatch

Production candidate lock no longer invokes the verifier through arbitrary instance lookup.

The lifecycle path dispatches through the import-time captured reviewed method mapping for:

```text
assert_runtime_integrity
verify_discovery_manifest
verify_candidate
```

The integrity validator also verifies that the current verifier and resolver class methods still equal the captured implementations.

### 2.6 Scientific result cache binding

After a successful Discovery manifest verification, a canonical binding of the scientific result state is stored out-of-object.

Before each candidate result is consumed, the verifier recomputes and compares the binding over:

- manifest/evidence identity;
- candidate verification outputs;
- candidate entries;
- evidence dependency list.

Mutation of the in-memory scientific result cache therefore cannot silently promote a candidate.

### 2.7 Evidence dependency replay

Candidate verification continues to reload all content-addressed scientific dependencies from the sealed resolver before returning the bound candidate result.

This retains fail-closed behavior if evidence bytes disappear or no longer match their digest/schema.

## 4. Test-fixture restructuring / small performance repair

The prior lifecycle tests relied on a forged exact-type production verifier implemented with `object.__new__` plus replaced methods.

That fixture is incompatible with the repaired production invariant and should not remain valid evidence.

The commit replaces many governance/durability setup paths with:

```text
synthetic lifecycle evidence
+
real production runtime source/split seal
```

and retains explicit production probes where production behavior is the subject.

This restructuring is conceptually acceptable: the previous “production” success path was itself based on the exact forgery that this repair is intended to reject, while production WF scientific verification remains intentionally NOT_TESTABLE at the current lifecycle stage.

However, repository-wide pytest performance acceptance requires measured evidence. No performance report has been published yet, so no timing claim is accepted by this review.
