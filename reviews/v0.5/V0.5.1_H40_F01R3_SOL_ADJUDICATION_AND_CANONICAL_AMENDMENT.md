## 1. Gemini findings accepted vs corrected

### 1.1 B-01 — direction accepted, fold count corrected

Gemini correctly identified that production WF expectation must be derived rather than caller-declared.

However, the candidate document incorrectly states that H40 has five canonical WF folds and refers to `fold_0 ... fold_4`.

The frozen split at the audited implementation SHA contains exactly:

```text
WF1
WF2
WF3
WF4
```

and the authoritative WF validation partitions are exactly:

```text
WF1_VALIDATION
WF2_VALIDATION
WF3_VALIDATION
WF4_VALIDATION
```

Confirmation is a separate later stage and is not a fifth WF fold.

The accepted target remains:

```text
expected_wf_authority
=
derive(
  seal-bound runtime split,
  exact WF1..WF4 validation partitions,
  accepted validation-contract authority
)
```

No production API may trust a fully caller-constructed `H40ExpectedSplitAuthority`.

The existing `wf_validation_receipt_contract` already explicitly requires:

```text
derive_the_complete_ordered_fold_set_from_split_manifest_and_split_attestation
accepted_validation_contract_hashes = complete accepted set, no subset or extra
```

Therefore B-01 remains an implementation repair under the existing WF child hash.

### 1.2 B-02 — Gemini hash classification rejected

Gemini classified the durable single-head model as:

```text
CANONICAL_CLARIFICATION_WITHOUT_HASH_CHANGE
```

That is not accepted.

The current `persistence_replay_contract` specifies:

- run-scoped storage;
- write-once receipts;
- atomic create-if-absent;
- lineage/hash checks;
- filename/label non-authority.

It does **not** define:

- exactly one committed authoritative head per run;
- a canonical durable head object;
- linearizable compare-and-advance;
- one-successor ownership for a committed predecessor;
- committed terminal absorption across process restart;
- head-lineage-only restoration.

Those are new authority semantics, not an implementation detail hidden inside the old hash.

Therefore the persistence child must be amended.

### 1.3 Gemini filesystem race model corrected

Gemini proposed concurrent writers using independent `os.replace(head.json)` operations and stated that sequence checks make only one writer win.

That is not sufficient.

Two writers can both:

1. read the same current head;
2. independently validate the same expected predecessor;
3. independently construct sequence N+1;
4. each atomically replace `head.json`.

The final state is last-writer-wins, not compare-and-swap.

Required semantics are implementation-independent:

```text
durable head advance must be a linearizable transactional compare-and-advance
against the current committed predecessor and sequence
```

Recommended implementation for this repository:

```text
SQLite transaction
BEGIN IMMEDIATE
read current head row
verify expected predecessor + sequence + terminal=false
conditional INSERT/UPDATE
COMMIT
```

A different mechanism is acceptable only if it proves equivalent single-winner linearizability.

### 1.4 B-03 — Model A accepted, but must become explicit authority

Gemini selected:

```text
Model A:
reverify root source truth at every production transition use
```

This is accepted as the smaller and safer repair for v0.5.1.

Required rule:

```text
Every production transition issuance, revalidation and consumption of a cached
VerifiedLifecycleAuthorization must recursively reverify the root runtime snapshot
seal and current active-source truth.

Cached and cold-restored authority must apply identical root-truth checks.
```

Because the old persistence/replay child does not explicitly define verified-capability lifetime, this rule is added to the amended persistence child.

### 1.5 H-01 — receipt-first direction accepted, commit semantics corrected

Receipt bytes must be fully materialized and durable before they can be referenced by committed lifecycle state.

The durable head is the lifecycle commit point.

A fully published receipt not referenced by the committed head is an **uncommitted orphan** and confers no lifecycle authority.

The final receipt path must not be destructively overwritten by a racing writer.

Recommended implementation:

```text
write temp
fsync temp
atomically publish content-addressed immutable receipt without overwriting different existing bytes
fsync receipt directory
then perform transactional durable-head compare-and-advance
```

### 1.6 M-01 — candidate rule rejected as written

Gemini's M-01 section contains two incorrect assumptions:

1. it refers to `receipt.row_count`, while the current typed source validation receipt exposes `timestamp_count`;
2. it hard-codes expected values such as a specific row count and `gap_count == 0`, which are not the generic authority rule.

M-01 is therefore **not accepted as written**.

Safe future rule:

```text
For an active VERIFIED runtime source:
record.row_count == cold_receipt.timestamp_count
record.gap_count == cold_receipt.gap_count
record.start_utc == cold_receipt.first_timestamp_utc
record.end_utc == cold_receipt.last_timestamp_utc
```

with no fixed count or zero-gap assumption.

Because M-01 is MEDIUM and not required to close B-01/B-02/B-03/H-01, it remains a pre-P3 implementation obligation and is not used to expand this canonical amendment.

## 6. Required implementation semantics after acceptance

### 6.1 B-01

Production expected WF authority must be internally derived.

Exact WF folds:

```text
WF1 -> WF1_VALIDATION
WF2 -> WF2_VALIDATION
WF3 -> WF3_VALIDATION
WF4 -> WF4_VALIDATION
```

No caller-selected subset/extra/reordering.

### 6.2 B-02/H-01

Use one committed durable head per `run_authority_id`.

Recommended implementation:

```text
immutable content-addressed receipt files
+
SQLite durable run-head table
+
BEGIN IMMEDIATE / transactional compare-and-advance
```

The SQLite row is the lifecycle commit point.

Receipt publication precedes head advance.

A receipt not reachable from the committed head is an uncommitted orphan and grants no lifecycle authority.

### 6.3 B-03

Model A is normative for v0.5.1:

```text
production transition use
-> recursively reverify root runtime seal
-> cold revalidate current active source truth
-> only then consume cached prior authority
```

Cold and cached paths must be equivalent.

### 6.4 M-01

Do not implement Gemini's fixed-count/zero-gap assumptions.

If closed in the same code repair, use only generic receipt equality:

```text
row_count == cold_receipt.timestamp_count
gap_count == cold_receipt.gap_count
start_utc == cold_receipt.first_timestamp_utc
end_utc == cold_receipt.last_timestamp_utc
```

Otherwise keep M-01 explicitly open as a pre-P3 medium obligation.
