# 1. Repairs accepted

## 1.1 SOL-01 closed — production WF replay

Production WF revalidation and cold restore now:

- derive expected WF authority internally again;
- compare persisted/context split authority against newly derived authority;
- call production WF authorization with `split_authority=None`;
- preserve explicit split injection only for synthetic mode.

This removes the prior self-contradiction where an internally derived production split was replayed through the caller-override rejection path.

Current production remains fail-closed while accepted P3 validation contracts are not materialized.

## 1.2 SOL-03 closed — authoritative fsync fail-closed

Authoritative receipt-directory fsync now uses:

```text
_fsync_dir(..., fail_closed=True)
```

and propagates failure before durable-head advancement.

The non-authoritative mirror may remain best-effort.

## 1.3 SOL-04 closed — immutable receipt publication

The authoritative receipt path now uses hard-link create-if-absent semantics.

`FileExistsError` compares exact bytes.

Generic hard-link failure fails closed.

The overwrite-capable `os.replace` fallback was removed from the authoritative receipt path.

## 1.4 SOL-05 closed — termination issuance root revalidation

`authorize_termination()` now calls the Model-A root source truth verifier before issuing a production termination authorization.

## 1.5 SOL-06 substantially closed — durable head integrity

# 2. F01R3R1-SOL-01 — BLOCKER — raw durable-head mutation remains an authority bypass

## Evidence

`H40LifecycleArtifactStore.advance_run_head()` remains a public method with:

```python
authorization: VerifiedLifecycleAuthorization | None = None
```

The authorization check is conditional:

```python
if authorization is not None:
    ...
```

Therefore production callers can still omit the verified authorization entirely.

The method now requires a typed, content-hashed persisted receipt, which is an improvement, but a caller can write such an envelope directly.

The R1 tests explicitly demonstrate this unsupported authority model:

```text
R15 valid root receipt commit:
_publish_mock_envelope(...)
store.advance_run_head(... authorization omitted)

R16 sibling race:
_publish_mock_envelope(...)
store.advance_run_head(... authorization omitted)

R17 terminal genesis:
_publish_mock_envelope(...)
store.advance_run_head(... authorization omitted)
```

Thus the test suite currently treats a caller-created typed receipt as sufficient committed lifecycle authority.

That contradicts the accepted V2 rule:

```text
only_the_accepted_implementation_verifier_may_atomically_construct_and_persist_authorization_after_recomputation
```

## Transition-matrix bypass

The low-level method verifies receipt type -> target state, but it does not verify the source-state transition against the accepted lifecycle matrix.

For example, a caller can construct an `H40WFValidationReceipt` whose upstream hash is the current Discovery receipt hash.

The typed WF receipt does not itself prove that its predecessor is a Candidate Lock receipt.

The raw method can therefore attempt:

```text
committed H40_DISCOVERY
-> caller-written typed WF receipt
-> H40_WALK_FORWARD_VALIDATED
```

without a verified Candidate Lock authorization.

Likewise a termination receipt's `source_state` is not matched against the current committed head state.

R17 currently commits:

```text
H40_PREREGISTERED -> H40_NO_GO
```

as sequence-zero raw storage behavior even though the accepted transition matrix does not make an arbitrary caller-written preregistered termination receipt authoritative.

## Required closure

There must be no production public path from caller strings/typed receipt bytes directly to committed head.

Required model:

```text
persist_authorization(
    authorization,
    service=<typed issuing service>
)
  -> service.revalidate_authorization(authorization)
  -> immutable receipt publication
  -> private _advance_verified_run_head(authorization)
  -> transactional commit
```

The commit primitive must require a non-null `VerifiedLifecycleAuthorization`.

It must check:

```text
authorization receipt == persisted typed receipt
authorization.run_authority_id == run
authorization.source_state == current committed predecessor target state
authorization.target_state == receipt target state
authorization.upstream_receipt_hash == current head receipt hash
accepted receipt type / source / target adjacency
```

For genesis, only an exact verified null-upstream authorization accepted by the lifecycle service may create sequence zero.

Do not retain a public optional-authorization commit API.

If raw transactional mechanics need direct unit testing, expose only an explicitly test-only helper/token that cannot be used as production authority.

# 3. F01R3R1-SOL-02 — BLOCKER — persistence root revalidation is still caller-supplied

## Evidence

`persist_authorization()` currently accepts:

```python
revalidate: Callable[[VerifiedLifecycleAuthorization], None]
```

and performs:

```python
revalidate(authorization)
```

The caller therefore chooses the function that is supposed to establish fresh Model-A authority.

A caller holding a previously valid but now stale cached production authorization can pass:

```python
revalidate=lambda _: None
```

and bypass:

- runtime seal revalidation;
- cold active-source verification;
- current source truth.

The subsequent `advance_run_head(... authorization=authorization)` checks object/receipt identity but does not itself run root-truth revalidation.

This contradicts the accepted persistence contract:

```text
every_production_transition_issue_revalidation_and_consumption_must_recursively_reverify_the_root_runtime_snapshot_seal_and_current_active_source_truth
```

and:

```text
only_the_accepted_implementation_verifier_may_atomically_construct_and_persist_authorization_after_recomputation
```

## Required closure

Replace arbitrary revalidation callback authority with a typed lifecycle authority service.

Preferred API:

```python
persist_authorization(
    transition_key,
    authorization,
    *,
    service: H40LifecycleAuthorityService,
)
```

Then:

```python
service.revalidate_authorization(authorization)
```

must be called internally.

Because `revalidate_authorization()` validates issuer identity, a foreign service cannot revalidate an authorization issued by another verifier.

Synthetic tests may pass their exact synthetic issuing service.

Production callers may pass only the production issuing service.

Do not accept arbitrary callables, lambdas, or booleans as revalidation authority.

For defense in depth, the private verified head-commit helper should only be called after this internal service revalidation in the same persistence operation.

Required adversarial test:

```text
production-shaped cached authorization
active source invalidated
attempt persist with no-op/foreign authority
-> impossible by API or fails closed
-> head remains unchanged
```

# 4. Transition adjacency must be enforced at commit boundary

The R2 repair must explicitly bind durable state to the verified transition, not only receipt target type.

For successor commit require:

```text
authorization.source_state == current_head.head_state
authorization.upstream_receipt_hash == current_head.head_receipt_hash
```

and require `authorization.source_state -> authorization.target_state` to be an accepted transition.

For termination, source state must equal current committed state.

For Candidate Lock, source must be H40_DISCOVERY.

For WF validation, source must be H40_CANDIDATE_LOCKED.

For Confirmation Ready, source must be H40_WALK_FORWARD_VALIDATED.

F02 transition remains prohibited.

No storage helper may create a transition that the verified lifecycle service did not issue.

# 5. MEDIUM — legacy empty head_hash migration should fail closed

`_get_sqlite_conn()` migrates a pre-existing run-head table using:

```sql
ALTER TABLE ... ADD COLUMN head_hash TEXT NOT NULL DEFAULT ''
```

and `_validate_and_parse_head_row()` verifies the storage hash only when:

```python
if curr_head_hash:
```

Thus legacy rows with empty `head_hash` are accepted without the new integrity index.

There are no accepted production H40 runs requiring permissive migration.

Preferred repair:

```text
existing row with empty/missing head_hash
-> fail closed
```

or deterministically backfill only after verifying all scalar fields, canonical JSON, exact receipt lineage and accepted authority.

Do not silently treat empty hash as equivalent to a verified storage hash.

This is MEDIUM and may be fixed in R2 while touching the head store.
