### R2-F01 — HIGH — Controller P3/Discovery grant is not a checked runtime prerequisite

**Expected invariant:** An independently published controller P3 and Discovery grant must precede production Discovery authorization and outcome consumption. Implementation acceptance alone is insufficient.

**Current enforcement:** production() selects the accepted implementation hash. authorize_discovery() checks that implementation against service state, cold-validates the seal, derives the run, checks frozen roots, then constructs the Discovery receipt. The state machine checks receipt/run/predecessor/adjacency. These are substantive runtime checks.

**Missing invariant:** No controller grant is an input to authorize_discovery, its receipt, the state machine, the verifier constructor, or the evidence resolver. No equivalent guaranteed gate before the public outcome-consuming verifier/resolver is present in the inspected production call graph. The module assumes an independently authorized producer, but does not enforce that producer or a grant. Absence of a CLI Discovery command or an implemented producer is not an authorization check.

**Minimum repair scope:** Add or integrate a distinct controller-issued authorization capability checked before production Discovery receipt creation and before outcome evidence reads. Bind it to the intended implementation, scientific roots, run/source/split and permitted partitions, and recheck it during restore. Keep source metadata validation and synthetic test paths separate. Publish this boundary only through a separately authorized repair and controller acceptance.

**Required regression concept:** With the exact accepted implementation and valid source/split metadata but no controller grant, every public production Discovery authorization and outcome-read entrypoint refuses before reading outcome content. Independently accepted matching grants permit only the intended partitions; expired, foreign, or absent grants fail on restore.

**Scientific identity impact:** No scientific rule change is required. A new controller capability/receipt or lifecycle contract may need a new governance/schema identity; controller adjudication and implementation reacceptance are required, rather than assuming frozen hashes may be edited.

**Scope of conclusion:** Source inspection establishes the missing prerequisite; R2 makes no claim of actual protected-data exposure.

## PIT and ordinary dataflow

The distinction between a causal prefit input and an explicitly retrospective Discovery calculation is essential. `_candidate_science` fits calibration on eligible non-neutral WF1_CALIBRATION labels and applies the fit on that named population. This is the accepted retrospective design; it does not establish that `p_up` or final actions existed at historical decision time. No alternative calibration rule is proposed. The missing invariant in R2-F03 is causal construction of raw features/scores/states before the retrospective calculation.
