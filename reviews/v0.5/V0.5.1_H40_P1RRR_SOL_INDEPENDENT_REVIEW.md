## What P1RRR correctly closes

The implementation correctly closes the P1RR offline self-consistency bypass:

1. `assert_authoritative(...)` now requires a non-optional `repo_root`.
2. `None`, empty root, or omitted root cannot obtain authority.
3. BTC and ETH artifacts are cold re-read and revalidated from disk.
4. Cold file SHA-256, timestamp-membership hash, and timestamp count must match the persisted attestation/source receipts.
5. BTC/ETH timestamps are re-extracted from disk, intersected, and the complete split membership is deterministically reconstructed.
6. Reconstructed base count, exclusion counts, partition objects, timestamp hashes and split hash must exactly match persisted state.
7. Persisted partition tampering followed by rehashing no longer survives the cold verifier.

The implementation is narrow: production changes are confined to `src/btc_quant_agent/h40/split_manifest.py`, with focused P1 tests. Local report records `63 passed` for the scaffold, `1149 passed` full pytest, Ruff/mypy/compileall/diff-check success, and no H40 outcomes/search/backtests.

## Remaining independent finding

### P1RRR-F1 HIGH — cold bytes are verified, but the source root itself is still caller-substitutable

P1RRR correctly proves that the files referenced by the supplied source manifest actually exist and match that manifest. It does **not** yet prove that the supplied source manifest represents the preregistered H40 source authority.

The public authority path still accepts:

```text
caller-chosen repo_root
+ caller-constructed H40SourceManifest
+ caller-chosen VERIFIED source records
+ real files under that caller root
```

provided the bytes, receipts, membership hashes, attestation and split are internally consistent.

`H40SourceManifest` remains directly constructible. `materialize_authoritative(...)` retrieves the logical BTC/ETH IDs from the supplied manifest, but does not independently require those records to match the preregistered source specification from `H40SourceManifest.build_preregistered_reference(protocol_identity_hash)`.

Consequently, a caller can create two unrelated synthetic parquet files in an arbitrary temporary root, label the records `BTCUSDT_USD_M_1H` and `ETHUSDT_USD_M_1H`, cold-validate them into self-consistent VERIFIED receipts, then successfully obtain an authoritative split. The existing synthetic positive tests intentionally exercise essentially this chain. That is appropriate as a validator unit test, but the same unrestricted production authority path means source identity/provenance is not actually anchored.

This conflicts with the original P1 authority requirement:

```text
If an exact required artifact is absent:
- do not substitute another source;
- do not loosen PIT semantics;
- do not infer its hash from an old report;
- record MISSING / UNVERIFIED / NOT_TESTABLE.
```

The problem is no longer cryptographic consistency or cold-byte verification. It is **semantic source substitution**: the verifier proves "these bytes match this caller manifest", but not "this manifest is the preregistered H40 BTC/ETH source authority".

### Why this is HIGH

Split membership is a material research input. A substituted source can selectively add/drop timestamps while preserving fixed date boundaries, thereby changing which observations enter training/calibration/validation and their timestamp-membership hashes. This is the same class of authority problem that the project previously treated as material-input substitution.

No H40 market outcome has yet been computed, so this is still cheap to repair without contaminating research.

## Required closure

Before an authoritative split can be produced or accepted, BTC and ETH source records must be independently bound to the preregistered source specification, not just to caller-supplied records.

At minimum the verifier/materializer must independently enforce, for the canonical BTC/ETH source IDs:

```text
source_id
product
cadence / interval
preregistered locator or immutable source identity
expected/reference raw-content identity when protocol-authorized
archive/checksum lineage when required
protected/allowed role
protocol identity
```

The simplest valid design is to derive a canonical source-spec identity from `build_preregistered_reference(protocol_identity_hash)` and require any materialized VERIFIED record used for H40 authority to prove correspondence to that spec. A caller-supplied replacement reference manifest must not be able to redefine the canonical source root.

Historical hashes that BASE explicitly marks as reference-only must not be misrepresented as automatic authority. If the exact preregistered artifact needed for a source cannot be independently reproduced from the current environment, that source must remain `NOT_TESTABLE`; do not substitute a convenient local parquet merely to make the gate pass.

Synthetic temporary fixtures remain appropriate for validator mechanics, but they must not exercise the exact same unrestricted production authority route as a canonical H40 source unless the test explicitly uses a test-only/non-authoritative policy object that cannot redefine production source authority.
