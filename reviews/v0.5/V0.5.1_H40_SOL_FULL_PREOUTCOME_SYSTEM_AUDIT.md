# A. Protocol-Level Blockers — Must Close Before P2R1

## H40-FSA-01 — HIGH — Probability/calibration input is not defined

BASE freezes logistic/Platt versus isotonic calibration and action thresholds, but it does not define the deterministic uncalibrated score/model that is passed to the calibrator. R3/R3R1 freeze family names, variants, filters and signs, but still do not define a single reproducible `raw_score -> p_up` pipeline.

This is a fundamental execution gap. Examples of mutually incompatible implementations that are all currently plausible include:

- calibrating only a sign `{-1,+1}`;
- calibrating raw return/breakout/divergence magnitude;
- fitting a logistic classifier over multiple direction/regime/opportunity features;
- using family-specific normalized strength scores;
- fitting one pooled model versus product-specific models.

All can satisfy the existing prose and produce different `p_up`, accepted trades, and ranking outcomes.

**Required closure:** freeze, for every single-family and pair contract, the exact raw score definition, score orientation (`higher => more bullish`), fit inputs, target encoding, model/calibrator fit procedure, intercept/regularization/solver if applicable, standardization policy, tie/degenerate behavior, and the exact mapping from calibrated output to `p_up`. No implementation-selectable estimator may remain.

---

## H40-FSA-02 — HIGH — Active feature formulas and percentile fitting are still not executable

R3/R3R1 improved boundaries but several active contracts still admit multiple legal numerical implementations.

At minimum the final closure must specify exact formulas and timestamp/bar indexing for:

- `D1_V1_RETURN_4H`, `D1_V2_RETURN_12H`;
- `D2_V1_BREAKOUT_24H`, `D2_V2_BREAKOUT_72H`;
- `D3_V1_FAILED_BREAK_24H`, `D3_V2_FAILED_BREAK_72H`;
- `R_VOL_RANGE_V1_24H` raw scalar;
- `O_RANGE_EXPANSION_V1_24H` raw scalar;
- D5 funding/crowding scalar and quantile fit;
- pair-scoped D5 component.

Specific unresolved choices include: exact closed-bar index set, whether the current last-closed bar belongs to the Donchian reference range, close-vs-high/low break definition, equality behavior, same-bar versus multi-bar failed-break semantics, realized-vol versus true-range combination, empirical percentile/quantile method, tie rule, minimum fit N, and warm-up behavior.

There is also a PIT issue in the phrase “fitted on the current training partition, lagged one decision.” For feature values at training timestamp `t`, the protocol must say whether the percentile/quantile reference distribution uses only observations available before `t` or may use the whole training partition. Causal feature contracts cannot silently depend on future rows inside the training partition.

**Required closure:** an independent implementation must be able to compute the same float/state from OHLCV/funding records without guessing.

## H40-FSA-03 — HIGH — D5 interaction hypothesis/tail semantics are still ambiguous

BASE explicitly requires D5 to identify the directional interaction and whether the frozen hypothesis is continuation or crowding reversal. R3R1 binds D5 to exact D1/D2 base variants, but phrases the filter as “funding crowding percentile at q=0.10/0.20; if crowding >= q percentile -> veto.”

That does not uniquely determine:

- signed funding versus absolute crowding magnitude;
- positive versus negative tail;
- base-side-aligned crowding (e.g. positive funding relevant to LONG and negative to SHORT) versus unconditional magnitude;
- whether `q=0.10` means lower 10th percentile, upper 90th percentile, or percentile score >= 0.10;
- continuation versus crowding-reversal interaction;
- last-settled record selection when settlements are irregular;
- quantile interpolation/tie method.

**Required closure:** freeze one exact side-aware or side-independent formula for both single-family D5 variants and the D3+D5 pair component, with tail, inequality, equality, settlement-time and quantile semantics.

## H40-FSA-04 — HIGH — Geometry population and fallback semantics remain ambiguous

R3 freezes cell keys and a pooling hierarchy, while BASE says fewer than 30 training observations in the applicable cell causes `NO_TRADE` and pooling is allowed only by a preregistered hierarchy. It is not yet unambiguous whether `N < 30` causes immediate failure or triggers the next fallback level first.

The estimator population also needs exact definition:

- which training observations enter a cell;
- whether observations must pass regime/opportunity/direction gates first;
- whether the proposed side determines which MFE/MAE series is used;
- how `POOLED_BTC_ETH` combines BTC and ETH observations;
- minimum N at each fallback level;
- exact median convention for even N;
- what happens when all fallback levels remain thin.

**Required closure:** freeze the exact estimator input population, side mapping, pooling/fallback decision algorithm and median definition. Geometry remains training-only; no realization may be computed during protocol authoring/P2.

## H40-FSA-05 — HIGH — Structural configuration identity is improperly coupled to mutable runtime authority state

R3 correctly distinguishes `STRUCTURAL_LEDGER_INCLUSION` from `CURRENT_RUNTIME_TESTABILITY`, but its proposed `source_requirement_hash` includes each source's current `production_authority_state`, and that hash flows into `configuration_hash`.

That means the scientific configuration identity changes if a source moves from `NOT_TESTABLE` to `VERIFIED` before discovery, even though the feature/search configuration is unchanged. This conflicts with the stated immutable 168-row structural ledger and makes source acquisition capable of changing configuration/ledger identity.

A second issue is freeze timing: current authority yields 18 `REGISTERED` and 150 `NOT_TESTABLE` rows. If source authority may improve before first label, the actually searchable candidate set can change unless the authority snapshot is itself frozen before outcome computation.

**Required closure:** separate:

1. immutable structural/scientific configuration identity (required logical sources and immutable source requirement IDs);
2. runtime/canonical source-authority attestation identity and derived testability;
3. the pre-outcome authority snapshot that fixes which rows are testable for this H40 V1 run.

After the first H40 label/outcome is computed, no source promotion may unlock additional rows. If authority is repaired before outcomes, it must create a new explicitly accepted pre-outcome authority snapshot without changing the 168 structural row semantics.

## H40-FSA-06 — HIGH — R2-bound P1 authority to R3 authority bridge is not fully specified

The accepted P1 implementation provides canonical, fail-closed source/split authority. The defect is not P1 itself; it is how R3/P2 consumes it.

Current P2 slots merely carry caller-provided `protocol_hash/source_manifest_hash/split_manifest_hash`. R3 changes the protocol authority from R2 to R3, but the protocol does not yet define a single canonical bridge/re-materialization rule for consuming accepted P1 authority under the new cumulative protocol identity.

**Required closure:** define exactly which P1 artifacts remain authoritative independent evidence, which R3 authority object references them, how the canonical source/split attestation is derived/verified under R3, and which hash/attestation P2 production materialization must consume. Do not reclassify any P1 source state.

## H40-FSA-07 — HIGH — Scope/pooled sample semantics need one exact construction

BASE states that pooled BTC/ETH opportunities remain separate decision rows and use common trustworthy timestamps, but fitting semantics are not fully specified.

The final protocol must freeze:

- exact invariant `BTC_ONLY <-> (BTCUSDT)`, `ETH_ONLY <-> (ETHUSDT)`, `POOLED_BTC_ETH <-> (BTCUSDT,ETHUSDT)`;
- pooled observation construction: one BTC row and one ETH row per common eligible UTC timestamp;
- weighting in raw-score fit/calibration/percentile fit/geometry estimation;
- whether product identity is a predictor (prefer explicit yes/no, not implementation choice);
- behavior if only one product row is feature-complete at an otherwise common timestamp;
- D4 pooled opposite-side behavior already frozen by R3R1 must remain consistent.

Without this, two implementations can fit different pooled models while using the same sources/timestamps.

## H40-FSA-08 — MEDIUM — Hash hierarchy naming/root semantics are inconsistent across R3 and R3R1

R3's `registry_hash` concept transitively binds feature/regime/opportunity/direction/pair/geometry/calibration/availability/refit contracts. R3R1 later introduces `full_authorized_registry_hash` and `active_168_registry_hash` specifically for the ten regime/opportunity contracts. These can coexist as subregistries, but their relationship/root preimage is not frozen clearly enough for independent implementation.

R3R1 also calls 40-hex Git commit object IDs “Git commit SHA-256”; that terminology is incorrect for this repository's current object format and should be replaced with neutral `Git commit object ID / commit SHA` wording.

**Required closure:** define one semantic-root hash tree with exact child hashes and names; define which root enters each `configuration_hash`, structural `ledger_hash`, authority attestation and acceptance record. No same-name/different-membership registry hash.

---

## H40-FSA-09 — MEDIUM — Registry-only contracts are overclaimed as executable canonical contracts

R3R1 adds eight unused registry-only contracts, but definitions such as “trend efficiency ratio,” “relative volatility spread / synchronized trend state,” “Bollinger-bandwidth release,” “cell-conditional ATR/magnitude estimate,” and “TP/BR envelope magnitude” are not bitwise executable.

Because they are not active in the 168 rows, this should not trigger arbitrary extra research work. The final closure should choose one of two explicit approaches:

- fully freeze them if they truly belong to an executable semantic root; or
- demote them to non-executable **authorized family vocabulary / reserved family descriptors** and exclude their unfrozen formula bodies from active configuration identity, while preserving the BASE family whitelist and prohibition on adding them to V1 without new protocol authority.

Prefer the simpler approach that avoids unnecessary research degrees of freedom.

# B. Existing P2 Code Blockers — Repair Only After Protocol Acceptance

These are implementation defects already present at exact code HEAD `52ac1dcb...`. They do not justify editing code before the protocol blockers above close.

## H40-FSA-C01 — HIGH — Production authority is caller-forgeable

`materialize_h40_search_space()` and public slot factories accept arbitrary protocol/source/split hashes. Current tests prove only that changing arbitrary strings changes `config_id`; they do not prove canonical authority.

Production APIs must derive/verify accepted authority objects. Synthetic/test constructors must be explicitly non-authoritative and unable to unlock production status.

## H40-FSA-C02 — HIGH — P2 implementation is still R2 and materially diverges from pending R3 authority

Current `protocol.py` is `H40_PROTOCOL_V1_R2`. Current search space still has the old D5 V2 identity, old D3+D5 funding feature, old calibration IDs/template ordering, and old contract structures. This is expected quarantine evidence, not accepted implementation.

## H40-FSA-C03 — HIGH — Runtime testability bypasses canonical P1 source authority

Current search-space logic hardcodes a funding/ETH exception and can leave BTC-only funding configurations `REGISTERED` despite P1 canonical BTC derivative authority being `NOT_TESTABLE`. P2R1 must derive status from canonical per-feature source requirements plus accepted P1 authority snapshot.

## H40-FSA-C04 — HIGH — Public configuration invariants are not fail-closed

Current code permits or creates semantic drift including:

- `create()` silently injecting D1 as missing D5 base owner;
- no exact `scope <-> asset_scope` consistency invariant;
- allowed depth-two pairs checked as unordered sets even though R3 semantic pair order is base-owner first;
- caller-controlled `status/reason_code` during deserialization instead of production derivation.

## H40-FSA-C05 — MEDIUM — Configuration/hash serialization does not match pending R3 semantics

Current code:

- binds textual IDs instead of the accepted semantic content root;
- sorts `required_feature_ids` even where order is semantic;
- rounds action threshold in `config_id`;
- accepts threshold values within epsilon rather than exact authorized canonical values;
- does not bind the pending exact predictor/geometry/calibration semantics.

## H40-FSA-C06 — MEDIUM — Protected/outcome guards are lexical and incomplete

Current guards use substring path checks and top-level forbidden-key checks. Confirmation-outcome references and nested outcome-bearing payloads can evade the intended boundary. Availability checking is also lexical rather than exact contract identity.

P2R1 should use recursive semantic payload validation and explicit protected locator classes/tokens.

## H40-FSA-C07 — MEDIUM — P2 tests are partly implementation-confirming rather than authority-adversarial

Examples include constructing arbitrary authority hashes as valid test inputs and testing that they alter identity, rather than requiring canonical authority; current tests also encode obsolete source/D5 behavior. P2R1 tests must use an independent expected 168-row oracle derived from accepted protocol authority and adversarially test bypasses.

# C. Future-Stage Blockers — Record Now, Do Not Let Them Block P2 Protocol Closure

## H40-FSA-F01 — HIGH before Discovery/Confirmation — Lifecycle transitions are state-only

`H40LifecycleStateMachine.transition_to()` checks transition adjacency, not evidence/authority receipts. A caller can transition scaffold -> discovery -> lock -> validation -> confirmation-ready without presenting ledger hash, candidate-lock artifact, validation proof or confirmation nonce.

This is acceptable as a scaffold only if it is not treated as authorization. Before Discovery/P3 uses it as a gate, transitions must be evidence-bound.

## H40-FSA-F02 — HIGH before Confirmation — Confirmation guard is caller-driven

Confirmation access must eventually bind one-shot persisted authority/nonce/candidate identity/partition identity, not merely a caller boolean or matching string. Fix before confirmation tooling exists; no confirmation access now.
