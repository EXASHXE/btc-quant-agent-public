## AG-04 residual closure

The previous read-only path used `mode=ro` when a non-empty WAL existed. SQLite may create a missing `-shm` sidecar in that state if the directory is writable, so GET `/health` was not proven filesystem-read-only under crash/recovery state.

R05AR now checks for a non-empty `-wal` before any SQLite open and raises `ForwardStoreWalRecoveryRequired`. `read_status()` converts that into deterministic degraded health. It does not switch to `immutable=1` in the presence of WAL, avoiding stale checkpoint reads that ignore uncheckpointed WAL frames.

New regression coverage uses genuine WAL-mode committed frames and verifies both:

- DB + non-empty WAL + absent SHM -> degraded before SQLite open; SHM remains absent; DB/WAL hashes and directory membership unchanged.
- DB + non-empty WAL + existing SHM -> conservative degraded result; DB/WAL/SHM bytes and membership unchanged.

Negative guards additionally assert the real health path never calls writer construction, `_initialize`, `prepare_schema`, or `finish_schema` across missing/checkpointed/WAL states.

This closes the specific R05A residual identified in the prior independent review.

## LOW operational note

A narrow time-of-check/time-of-use freshness race remains possible between the non-empty-WAL check and the subsequent `immutable=1` open if a writer starts exactly in that interval. The consequence is potentially a transient checkpointed/stale health view, not a write side effect or formal-research authority bypass. It is classified LOW and does not block R05A acceptance. If future operational requirements demand linearizable health freshness, use writer/read coordination rather than expanding this repair.
