## Findings

### R3R1-SOL-01 — HIGH — D5 funding/crowding interaction is still not uniquely specified and does not satisfy the BASE continuation-vs-crowding-reversal commitment

BASE Section 5.3 requires D5 to name its base directional family **and whether the frozen hypothesis is continuation or crowding reversal**. Funding alone remains non-directional.

R3R1 now binds exact base variants, which is good, but defines:

```text
D5 q = 0.10 / 0.20
if crowding >= 0.10 / 0.20 percentile -> veto NO_TRADE
```

This is not sufficient to reconstruct one scientific hypothesis. It does not define:

- the exact scalar crowding variable before percentile ranking;
- whether funding is used signed, absolute, or aligned to the base side;
- whether the relevant tail is upper, lower, or two-sided;
- whether `q=0.10/0.20` means the q-th quantile, an upper-tail mass `1-q`, or another convention;
- whether same-side crowding vetoes continuation (crowding-reversal interpretation) or confirms continuation;
- exact equality behavior at the funding threshold after quantile fitting.

The present `crowding >= 0.10 percentile` wording would also mechanically veto most ordinary percentile values, which strongly suggests the tail convention is not the intended fully specified interaction.

**Required closure:** R3R2 must freeze an exact scalar formula, training quantile construction, tail/orientation, continuation-vs-crowding-reversal identity, threshold comparison including equality, and exact pass/veto output for D5 V1, D5 V2, and the D3+D5 pair-scoped D5 component. No outcomes may be consulted.

### R3R1-SOL-02 — HIGH — Active regime/opportunity transforms are not yet executable formulas

R3R1 freezes state boundaries, but the active numeric feature itself remains ambiguous.

`R_VOL_RANGE_V1_24H` is described as:

```text
realized-volatility / true-range rolling percentile
```

The slash leaves multiple materially different transforms possible: standard deviation of log returns, realized variance, ATR, normalized true range, or a combination. These produce different feature values and therefore different accepted decisions.

`O_RANGE_EXPANSION_V1_24H` is described as:

```text
lagged realized range-expansion percentile
```

but does not uniquely freeze the raw range statistic, denominator/baseline, exact 24h aggregation, or percentile ranking input.

State cutoffs do not close scientific degrees of freedom if the scalar being thresholded is not unique.

**Required closure:** R3R2 must provide exact formulas/pseudocode for the raw scalar and percentile-fit procedure for both active contracts, including exact bar indexing/endpoints, minimum observations, tie handling/rank convention, lag rule, fit population (per product vs pooled), and missing-data behavior.

### R3R1-SOL-03 — HIGH — D2 and D3 active direction features remain semantically underdetermined

The active D2 features are still summarized as `donchian_breakout_sign` over 24h/72h. The protocol must freeze at minimum:

- exact prior-window bounds;
- whether the current/last closed bar is excluded from the Donchian range;
- whether breakout is determined by close, high/low touch, or both;
- upper/lower equality behavior;
- side when both boundaries are touched or data are duplicated/missing.

The active D3 features are summarized as `failed_break_and_close_back_reversal`. That phrase permits several distinct implementations, for example a same-bar wick break and close-back versus a prior-bar close break followed by a later close-back. The event chronology, boundary owner, and side rule are not uniquely frozen.

Because D2/D3 participate in both single-family rows and authorized pairs, this ambiguity reaches a substantial fraction of the 168 ledger.

**Required closure:** R3R2 must freeze executable formulas/state machines for D2 V1/V2 and D3 V1/V2, with strict closed-bar/PIT indexing and equality/missing/dual-break behavior. D1 endpoints should be stated in the same canonical indexing notation for consistency.

### R3R1-SOL-04 — MEDIUM — Registry-only contracts are declared “fully frozen” but several remain non-executable descriptions

R3R1 correctly adds all eight registry-only contracts, but examples remain ambiguous:

```text
R_CROSS_ASSET: relative volatility spread / synchronized trend state
O_EXPECTED_EXCURSION: cell-conditional ATR/magnitude estimate
O_TPBR_MAGNITUDE: TP/BR envelope magnitude
```

These are not unique formulas and omit parameters such as exact volatility definition, cell keys/statistic, TP/BR envelope construction, and Bollinger-band parameters.

These contracts are `ACTIVE_IN_168_LEDGER=false`, so this does not by itself change the active search rows, but it contradicts the cumulative claim that the full canonical registry is fully specified and content-hashed.

**Required closure:** either (A) fully define them mathematically in R3R2, or (B) explicitly downgrade them to `AUTHORIZED_FAMILY_STUB_NOT_ACTIVE_NOT_IMPLEMENTABLE_IN_V1`, exclude their unresolved semantic payloads from claims of executable registry completeness, while preserving their family authority and prohibition on entering the 168 ledger. Option B is preferred because it introduces fewer unused semantics.

### R3R1-SOL-05 — MEDIUM — Protocol hash wording confuses Git object IDs with SHA-256 and should be made algorithm-agnostic

R3R1 Section 5.1 calls each 40-hex Git commit identity a:

```text
Git commit SHA-256 (40-hex)
```

That description is incorrect for the current 40-hex Git object IDs. The actual literal commit strings are unambiguous, so this is not an authority break by itself, but an implementation could incorrectly validate length/algorithm from the prose.

Also, the canonical JSON object is said to use keys “in that order” while repository `canonical_json` uses `sort_keys=True`; object insertion order therefore has no hash significance.

**Required closure:** treat each Git commit identity as an opaque exact Git object-id string supplied by authority; do not assert SHA-1/SHA-256 unless the repository explicitly exposes that format. State that `canonical_json` lexicographically sorts object keys and object insertion order is non-semantic.
