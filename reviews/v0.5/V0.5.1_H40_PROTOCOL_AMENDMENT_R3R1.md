## 3. Close R3-SOL-03: Exact D4 Mathematical and Target-Scope Projection

### 3.1 Common definitions

For a decision boundary `t` and window `W` hours, using only closed bars with `close_time_ms < t`:

```text
r_X(t, W) = log(C_X(t) / C_X(t - W))     for X in {BTC, ETH}
sign(z)   = +1 if z > 0, -1 if z < 0, 0 if z == 0
```

`C_X(t)` is the close of the last hourly bar strictly before `t`; `C_X(t - W)` is the close of the bar at `t - W`. Missing either endpoint makes `r_X` undefined → `NO_TRADE` (`PIT_UNAVAILABLE`).

### 3.2 D4_V1_CONFIRMATION_4H (synchronized agreement)

```text
window W                = 4h
BTC state               = r_BTC(t, 4h)
ETH state               = r_ETH(t, 4h)
agreement               = (sign(r_BTC) == sign(r_ETH)) and sign != 0
side                    = that common sign
```

Exact behavior:

```text
both signs agree and nonzero  -> side = common sign applied to the target product
signs disagree                -> NO_TRADE (no confirmation; reason THRESHOLD_UNMET)
one side zero                 -> NO_TRADE (incomplete confirmation)
both zero                     -> NO_TRADE
magnitude/state equality on a boundary -> zero is the only equality case; sign(z)==0 is the boundary and is handled as NO_TRADE above
```

Target-product projection:

```text
BTC_ONLY        -> side applies to BTCUSDT
ETH_ONLY        -> side applies to ETHUSDT
POOLED_BTC_ETH  -> per-product: the BTC row uses the agreement side on BTC,
                   the ETH row uses the same agreement side on ETH
```

Missing component (either BTC or ETH series unavailable) → `NO_TRADE` (`PIT_UNAVAILABLE`).

Output schema: `{"variant": "D4_V1_CONFIRMATION_4H", "side": -1|0|+1, "agreement": true|false, "window_hours": 4}`.

### 3.3 D4_V2_DIVERGENCE_8H (target-relative divergence, continuation)

Exact single formula, **target-relative and continuation** (BASE: "lagged divergence contains direction"):

```text
window W = 8h
for a row targeting product T with other product O:
    div_T(t) = r_T(t, 8h) - r_O(t, 8h)
    side_T   = sign(div_T(t))
```

- **Meaning**: the target's relative move against the other product continues; `side_T = +1` means LONG the target, `-1` SHORT the target.
- **Not** `sign(r_BTC - r_ETH)` applied identically to both products — the formula is target-relative.
- **Not** divergence mean-reversion — the frozen hypothesis is continuation.
- Target projection:
  - `BTC_ONLY`: `side = sign(r_BTC(t,8h) - r_ETH(t,8h))` applied to BTCUSDT.
  - `ETH_ONLY`: `side = sign(r_ETH(t,8h) - r_BTC(t,8h))` applied to ETHUSDT.
  - `POOLED_BTC_ETH`: per-product rows — the BTC row uses `sign(r_BTC - r_ETH)`, the ETH row uses `sign(r_ETH - r_BTC)` (which, by construction, is the opposite sign when both are nonzero). This is the frozen pooled semantics: **per-product target-relative rows; opposite sides are an expected consequence of the target-relative formula, not an abstention trigger.**
- Zero/equality behavior: `div_T(t) == 0` → `NO_TRADE`.
- Missing component (either series unavailable) → `NO_TRADE` (`PIT_UNAVAILABLE`).

Output schema: `{"variant": "D4_V2_DIVERGENCE_8H", "side": -1|0|+1, "target": product, "divergence": float, "window_hours": 8}`.

Both D4 formulas and scope-projection semantics are bound into the D4 feature/direction contract hashes (Section 5).

```text
   - thresholds/quantiles (0.55, 0.60, 0.65, 0.10, 0.20, 0.40, 0.60, 0.80, 1.5, 1.25)
     are represented as their shortest exact decimal literal (Python float repr),
     e.g. 0.55 -> "0.55", 0.10 -> "0.1", 1.5 -> "1.5", 0.0012 -> "0.0012";
     all enumerated values chosen here have finite binary round-trips and are frozen.
   - c_rt is canonical as the decimal fraction 0.0012 (dimensionless); the cost proxy
     id COST_PROXY_12BPS_V1 binds 12 bps.
   - duration/lookback fields are integers in hours.
   - percentile/state values are floats in [0,1]; the state LABEL (string) is what
     enters the hash for state-machine decisions, not the raw float.
4. NaN/Infinity are forbidden everywhere (canonical_json allow_nan=False raises).
5. Two independent implementations using these rules and the same semantic values
   MUST produce identical contract/configuration/ledger hashes.
```
