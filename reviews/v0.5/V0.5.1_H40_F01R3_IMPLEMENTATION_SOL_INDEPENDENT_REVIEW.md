# 2. F01R3-SOL-01 — BLOCKER — production WF revalidation/restore is self-contradictory

## Evidence

Production issuance explicitly rejects caller-supplied split authority:

```text
src/btc_quant_agent/h40/lifecycle_authority.py
H40LifecycleAuthorityService.authorize_wf_validation()
lines ~3032-3045
```

The logic is:

```python
if not self._synthetic_test_mode and split_authority is not None:
    raise H40GuardError(
        CONFIG_IDENTITY_CONFLICT,
        "caller-supplied split authority cannot override production derivation",
    )
```

This is correct for first production issuance.

However, `revalidate_authorization()` later handles an already-issued WF authorization by extracting its persisted/in-memory `split_authority` context and passing it back into the same production API:

```text
lines ~3288-3303
```

Conceptually:

```python
split = authorization.context["split_authority"]

self.authorize_wf_validation(
    candidate_authority=prior,
    evidence=evidence,
    split_authority=split,
    ...
)
```

Cold restore does the same:

```text
H40LifecycleArtifactStore._cold_restore_authorization()
lines ~4176-4191
```

It resolves `split_authority` and passes it to production `authorize_wf_validation()`.

Therefore, once future accepted P3 validation contracts are materialized:

```text
production WF initial issue
-> context contains internally derived split_authority

revalidate_authorization(WF)
-> passes non-null split_authority back
-> production API rejects it

persist_authorization(WF)
-> calls revalidate_authorization()
-> fails

cold restore WF
-> passes resolved split_authority
-> fails
```

This is not the intended current `P3 contracts not yet materialized -> NOT_TESTABLE` behavior.

It is an independent API contradiction that would remain after P3 contracts exist.

## Severity

```text
BLOCKER
```

F01 is the trusted lifecycle core; future production WF authority must be persistable, revalidatable and cold-restorable without changing its authority source.

## Required closure

For production:

1. internally derive expected WF authority again from the verified current run/seal;
2. if a persisted/context split authority exists, treat it only as an object to compare against the newly derived authority, never as authority input;
3. require exact equality/content identity;
4. call the issuance verifier using internally derived authority, not caller authority.

Acceptable patterns include:

```text
revalidate:
  derived = derive_expected_wf_authority(prior)
  require persisted_context_split == derived
  authorize_wf_validation(... split_authority=None)

cold restore:
  derived = derive_expected_wf_authority(prior)
  require resolved_persisted_split == derived
  authorize_wf_validation(... split_authority=None)
```

Synthetic test mode may continue passing explicit synthetic split authority.

Add a production-shaped test seam that proves this control flow without requiring real outcomes.

# 3. F01R3-SOL-02 — BLOCKER — durable head mutation is caller-accessible without receipt/transition authority

## Evidence

`H40LifecycleArtifactStore.advance_run_head()` is a public mutation method.

Its inputs are:

```text
run_authority_id
receipt_hash
target_state
predecessor_receipt_hash
```

but it does not require or verify a `VerifiedLifecycleAuthorization`.

It does not verify before committing that:

- `receipt_hash` names a fully published immutable receipt;
- that receipt content hash equals `receipt_hash`;
- receipt.run_authority_id equals the run;
- receipt.target state equals `target_state`;
- receipt.upstream hash equals `predecessor_receipt_hash`;
- the proposed source->target transition is an accepted transition;
- the first head is a valid genesis transition.

For an empty run-head row, the method accepts any non-empty target string and even allows a non-null predecessor.

For an existing nonterminal head, it only requires the supplied predecessor hash to equal the current head hash.

Thus code outside the accepted verifier/persistence path can directly mutate the committed lifecycle authority.

Examples that the method currently permits structurally:

```text
empty run
-> arbitrary receipt hash
-> H40_CONFIRMATION_READY
-> sequence 0

or:

current Discovery head
-> arbitrary receipt hash with no receipt artifact
-> arbitrary target_state string
-> committed sequence 1
```

Such a corrupt head may later make restore fail, but fail-closed bricking is not an acceptable substitute for preventing unauthorized committed-state mutation.

The accepted persistence contract says:

```text
only_the_accepted_implementation_verifier_may_atomically_construct_and_persist_authorization...
```

and the durable head is the sole lifecycle commit point.

Therefore the commit point itself cannot be a caller-string API.

## Severity

```text
BLOCKER
```

## Required closure

Make committed-head advancement an internal persistence operation bound to an exact verified authorization and exact already-published receipt.

Recommended:

```text
persist_authorization(VerifiedLifecycleAuthorization)
  -> revalidate authorization
  -> publish exact immutable receipt
  -> internal _advance_verified_run_head(authorization, receipt_path/hash)
```

Before opening the head transaction, verify:

```text
published receipt exists
canonical envelope parses
receipt_sha256 == authorization.receipt_hash
receipt object == authorization.receipt
run id matches
target state matches authorization.target_state
upstream/predecessor matches authorization.upstream_receipt_hash
```

Inside the transaction verify current durable predecessor and terminal state.

Genesis rule must be explicit.

For the current lifecycle, the first persisted authorization must have no upstream receipt and must be a transition that is valid from the preregistered/P1 scaffold boundary. At minimum do not permit a descendant with a missing predecessor to become sequence 0.

If a low-level head method remains public for tests, it must be unmistakably test-only and unable to be reached as production authority.

Also validate `target_state` against the accepted lifecycle state vocabulary / transition matrix.

# 4. F01R3-SOL-03 — HIGH — directory durability failures are swallowed

## Evidence

`_fsync_dir(path)` is implemented as:

```python
try:
    ...
    os.fsync(fd)
    ...
except OSError:
    pass
```

The new persistence V2 contract requires:

```text
receipt_and_bound_evidence_bytes_are_fully_materialized_and_fsynced_before_final_publication
```

and the implementation performs:

```text
publish receipt
_fsync_dir(receipts_dir)
advance durable head
```

Because directory fsync errors are swallowed, execution can continue into the SQLite head commit even though directory-entry durability was not established.

A power loss can therefore violate the intended ordering:

```text
committed head
but receipt directory publication not durably established
```

The new tests do not inject or assert directory-fsync failure.

## Severity

```text
HIGH
```

This is the remaining core of ASTRA-H-01.

## Required closure

Durability failure before head commit must fail closed.

Do not swallow directory fsync failure on the authoritative receipt publication path.

If the platform/filesystem cannot provide the required durability primitive, either:

- fail closed for authoritative production persistence; or
- use a persistence primitive that provides equivalent durable semantics.

Add a fault-injection test:

```text
receipt publication directory fsync fails
-> persist_authorization raises
-> durable head remains predecessor
-> new receipt does not become committed authority
```

The non-authoritative mirror `head.json` may have weaker best-effort behavior only if clearly documented and never used as authority.

# 5. F01R3-SOL-04 — HIGH — immutable receipt fallback can overwrite a racing final artifact

## Evidence

The normal receipt publication path uses a hard link from a fully fsynced temp file to the content-addressed final path.

That is suitable for no-overwrite publication.

However, on a generic `OSError`, the fallback is:

```python
if final_receipt_path.exists():
    compare bytes
else:
    os.replace(temp_path, final_receipt_path)
```

There is a race between the existence check and `os.replace`.

Another writer can create `final_receipt_path` after the check, and `os.replace` will then overwrite the final path.

That violates:

```text
immutable_receipts_are_content_addressed_and_atomically_published_without_overwriting_different_existing_bytes
```

## Severity

```text
HIGH
```

## Required closure

Do not use overwrite-capable `os.replace` as the fallback for immutable receipt publication.

Safer minimal policy:

- hard-link publish from same-directory temp;
- `FileExistsError` -> compare exact bytes;
- any other hard-link failure -> fail closed, unless another proven no-overwrite primitive is used.

Do not trade durability/immutability for platform convenience silently.

Add an adversarial publication-race/fallback test.

# 6. F01R3-SOL-05 — MEDIUM — termination issuance omits Model-A root revalidation

## Evidence

`authorize_candidate_lock()`, `authorize_wf_validation()`, and `authorize_confirmation_ready()` consume prior authority through `_require_prior()`, which calls:

```text
_reverify_root_source_truth()
```

`authorize_termination()` does not use `_require_prior()` and does not explicitly invoke root source revalidation before constructing a termination authorization.

Later state-machine consumption and persistence/revalidation perform additional checks, so this is not presently a forward-progress bypass.

But it violates the accepted V2 capability lifetime rule:

```text
every_production_transition_issue_revalidation_and_consumption
must recursively reverify root runtime source truth
```

## Severity

```text
MEDIUM
```

## Required closure

At the beginning of production `authorize_termination()`, after issuer/type validation and before scientific/failure evidence use:

```text
self._reverify_root_source_truth(prior_authority)
```

or refactor to an equivalent common prior-authority verifier that does not impose the wrong source/target pair.

Add a cached stale-source termination test.

# 7. F01R3-SOL-06 — MEDIUM — durable head integrity is insufficiently cross-checked

## Evidence

The SQLite row stores both scalar columns and canonical `head_json`.

`get_committed_run_head()` reads only `head_json`.

`advance_run_head()` reads scalar columns and `head_json`, but does not require the parsed JSON to equal those scalar columns.

The canonical contract defines:

```text
head_hash_rule =
canonical_sha256(exact_field_contract_keys_only)
```

but the store does not persist/check a separate derived head hash or at least verify scalar-column / JSON equality on every read.

This makes storage corruption/tampering detection weaker than the surrounding content-addressed receipt model.

## Severity

```text
MEDIUM
```

## Required closure

At minimum:

1. parse `head_json`;
2. require every typed field equals the corresponding relational column;
3. require `terminal == (head_state in accepted terminal states)`;
4. require `head_state` is a recognized lifecycle state;
5. fail closed on any mismatch.

Optionally persist a derived `head_hash` column/index and verify it against `canonical_sha256(head.to_dict())`; that does not change the canonical head field contract because the hash is an out-of-band storage integrity index, not an additional canonical field.
