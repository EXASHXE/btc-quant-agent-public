## What P1R4 correctly improves

P1R4 adds an independently derived canonical source specification and production-time source checks for logical source ID, product, cadence, locator, archive lineage, and selected reference identities. Production-default `materialize_authoritative(...)` / `assert_authoritative(...)` now call `assert_canonical_source_record(...)`, so a caller cannot simply move BTC/ETH to an arbitrary noncanonical locator and retain default production authority.

The implementation also honestly reports that the repository's current BTC preregistered locator is a legacy 1m manifest and therefore cannot currently be validated as the required 1h H40 split input. That fail-closed direction is correct and consistent with P1.

## Finding P1R4-F1 HIGH — production/test authority boundary remains caller-selectable

The public authority APIs accept:

```python
authority_policy: H40AuthorityPolicy | None
```

and the package publicly exports `H40AuthorityPolicy.test_synthetic()`.

When the caller supplies the synthetic policy, canonical source-spec checks are skipped while `materialize_authoritative(...)` still returns an `H40SplitManifest` with:

```text
is_authoritative=True
```

and the same caller may pass the synthetic policy to `assert_authoritative(...)`.

This makes the authority mode itself caller-controlled. A test convenience switch must not be capable of changing whether the production authority verifier enforces canonical-source semantics.

This is not merely theoretical: the current P1 tests use the synthetic policy to build and assert authoritative split objects from arbitrary temp fixtures.

### More importantly: BTC production content identity is still substitutable

The canonical BTC reference contains:

```text
locator = data/research/BTCUSDT/data_manifest.json
reference_file_sha256 = 928e913f...
```

but `assert_canonical_source_record(...)` intentionally enforces `reference_file_sha256` only for `ETHUSDT_USD_M_1H`, not BTC.

The current positive-production test therefore writes a new caller-created 1h JSON file at the canonical BTC locator, validates its newly computed SHA, and successfully obtains **production canonical authority**. This directly contradicts the P1/P1R4 invariant that a missing exact canonical artifact must remain `NOT_TESTABLE` rather than being replaced by a convenient file at the same path.

The implementation report itself correctly states that the real repository BTC artifact is a legacy 1m manifest and is `NOT_TESTABLE`; therefore there is no valid basis for a synthetic replacement at the same locator to become production authority.

### Required semantic closure

Do not attempt to fabricate a positive production BTC path in tests.

For current `H40_PROTOCOL_V1_R2`, production authority must behave as follows:

1. BTC exact canonical 1h source identity is not currently established by the available preregistered artifact.
2. Therefore BTC production split-source state remains `NOT_TESTABLE` until a separately authorized protocol/source amendment freezes an exact 1h source artifact and lineage.
3. Caller-created content at the canonical locator must not upgrade this state.
4. Synthetic validator fixtures may test byte/timestamp mechanics, but must remain explicitly **non-authoritative for production**.
5. Public production authority APIs must not expose a caller-selectable policy that disables canonical checks.

A clean design is:

```text
production materialize/assert APIs
    -> always canonical, no policy override

generic/test validator helpers
    -> synthetic allowed
    -> never produce production-authoritative split
```

P1 does not require a successful production split when a required source is unavailable; a safe `NOT_TESTABLE` scaffold is acceptable.
