#### MED-01: Parquet Reader Re-opens Filesystem Path During Economic Extraction

```text
ID: MED-01
Severity: MEDIUM
Title: Parquet reader re-opens filesystem path during economic extraction

Exact code locations:
- src/btc_quant_agent/h40/discovery_evidence.py:1232-1239
- src/btc_quant_agent/h40/discovery_evidence.py:749-754

Exact governing contract locations:
- reviews/v0.5/V0.5.1_H40_PRE_DISCOVERY_REPAIR_CONTRACT_FREEZE_R2.md: Section 4 (R2-F02)
- evidence/v0.5/h40/V0.5.1_H40_PRE_DISCOVERY_REPAIR_CONTRACT_FREEZE_R2.json: "f02_boundary_contract"

Precondition:
Production verifier executes _load_source_bars() during discovery evidence resolution against an on-disk .parquet file.

Minimal repository-local failure sequence:
1. file_path.read_bytes() reads raw_bytes into process memory (line 1232).
2. hashlib.sha256(raw_bytes).hexdigest() verifies against entry["source_file_sha256"] (line 1233).
3. _extract_economic_rows(file_path, raw_bytes, ...) is invoked.
4. For suffix == ".parquet", line 752 calls table = pq.read_table(file_path), reopening the file path from disk rather than reading from raw_bytes.
5. In contrast, for suffix == ".json" (line 767), json.loads(raw_bytes.decode("utf-8")) parses the already-hashed in-memory buffer.

Observed result:
A theoretical time-of-check to time-of-use (TOCTOU) gap exists between the raw byte read/hash and the Parquet table parse. If the file on disk is modified concurrently between steps 1 and 4, the parser parses bytes from disk rather than the validated raw_bytes.

Required invariant:
The economic projection parser must parse the exact bytes validated against source_file_sha256 without re-reading the filesystem path.

Why existing tests do/do not catch it:
Existing tests execute synchronously in a single-threaded test environment where source files are static fixtures on disk, so file contents do not mutate between read_bytes() and read_table().
Furthermore, lines 1241-1245 compute canonical_sha256(canonical_rows) and assert equality against entry["economic_rows_sha256"]. This second-line digest verification fails closed if the parsed economic rows differ, preventing silent data corruption, but does not close the structural path-reopen gap.

Minimum repair scope:
In _extract_economic_rows(), pass an in-memory buffer reader to pyarrow.parquet.read_table:
import pyarrow as pa
table = pq.read_table(pa.BufferReader(raw_bytes))

Required regression:
A test demonstrating that modifying or deleting the file path on disk immediately after passing raw_bytes does not affect parquet parsing.

Scientific identity change required: NO
Lifecycle V5 semantic change required: NO
Blocks P3 controller publication: NO (defense-in-depth improvement; mitigated by economic_rows_sha256).
```

## 5. Adversarial Cases Disproved

The following theoretical attack paths and failure modes were systematically audited and **DISPROVED**:

### Case 1: Premature Discovery Authorization via Implementation Publication Alone
- **Hypothesis:** Having published `ACCEPTED_LIFECYCLE_IMPLEMENTATION_AUTHORITY_HASH = "a23ceec5..."`, a service instance might be able to transition to `H40_DISCOVERY` without a Controller Authority.
- **Audit Proof:**
  `H40LifecycleAuthorityService.authorize_discovery()` invokes `self._assert_current_anchors(require_controller=True)`.
  Because `ACCEPTED_H40_P3_CONTROLLER_AUTHORITY_HASH` is strictly `None`, the method unconditionally raises `H40GuardError(H40ReasonCode.NOT_TESTABLE, "no independently accepted H40 P3 controller authority exists")`.
  Implementation publication alone cannot bypass the separate Controller gate.
- **Verdict:** **DISPROVED (Airtight)**.

### Case 2: Auto-Synthesis or Substitution of Controller Authority / Run Grant
- **Hypothesis:** An attacker passes a synthetic or forged controller authority/grant to `production()`, or the service automatically synthesizes one.
- **Audit Proof:**
  In `production()` (`synthetic_test_mode=False`), passing any `controller_authority` when `ACCEPTED_H40_P3_CONTROLLER_AUTHORITY_HASH is None` fails immediately in `__init__` with `ValueError("controller authority object/hash mismatch")`.
  Furthermore, `_synthesize_controller_authority()` is only invoked in `synthetic_for_tests()`, which is unreachable in production mode.
  In `authorize_discovery()`, `expected_grant` is derived deterministically from the active controller and run authority; any supplied grant that does not equal `expected_grant` raises `CONFIG_IDENTITY_CONFLICT`.
- **Verdict:** **DISPROVED (Airtight)**.

### Case 3: Synthetic Registry and Resolver Leakage into Production
- **Hypothesis:** Objects cached in `_SYNTHETIC_CONTROLLER_REGISTRY` or `_SYNTHETIC_GRANT_REGISTRY` can be resolved or accepted by production verifiers.
- **Audit Proof:**
  `H40LifecycleAuthorityService.production()` enforces `synthetic_test_mode=False`. If an `evidence_verifier` with `synthetic_only=True` (e.g. `H40SyntheticEvidenceVerifier`) is passed, `production()` raises `ValueError("production service cannot use a synthetic/test-only verifier")`.
  In `authorize_discovery()`, `seal.synthetic_only` is explicitly checked: if `True`, it raises `H40GuardError(H40ReasonCode.NOT_TESTABLE, "synthetic runtime seal is non-authoritative")`.
  Real seals must call `seal.verify_against_accepted_ledger()`.
  Synthetic registries cannot satisfy production requirements.
- **Verdict:** **DISPROVED (Airtight)**.

### Case 4: Long-Lived Service Surviving Authority Supersession
- **Hypothesis:** A long-lived service constructed under an old implementation authority continues to authorize transitions after a new authority is published.
- **Audit Proof:**
  Every transition method (`authorize_candidate_lock`, `authorize_wf_validation`, `authorize_termination`, etc.) and `revalidate_authorization()` invokes `_assert_current_anchors()`.
  `_assert_current_anchors()` checks `self._accepted_implementation_authority_hash != ACCEPTED_LIFECYCLE_IMPLEMENTATION_AUTHORITY_HASH`.
  If the in-process constant changes, the service raises `H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT, "service implementation authority anchor has been superseded")`.
- **Verdict:** **DISPROVED (Airtight)**.

### Case 5: V1 Persistence or V2 Receipts Accepted During Cold Restore
- **Hypothesis:** A legacy V1 persistence context or V2 Discovery receipt is injected into cold store and accepted by a production service.
- **Audit Proof:**
  In `_cold_restore_authorization()`:
  Line 6025: `if isinstance(context, H40LifecyclePersistenceContextV1): raise H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT, "production cold restore rejects H40_LIFECYCLE_PERSISTENCE_CONTEXT_V1")`.
  Line 6030: `if isinstance(receipt, H40DiscoveryAuthorizationReceiptV2): raise H40GuardError(H40ReasonCode.CONFIG_IDENTITY_CONFLICT, "production cold restore rejects H40_RECEIPT_DISCOVERY_AUTH_V2")`.
  Line 6036: `if context.implementation_authority_hash != ACCEPTED_LIFECYCLE_IMPLEMENTATION_AUTHORITY_HASH: raise H40GuardError(...)`.
  Legacy and unanchored persisted contexts are strictly rejected.
- **Verdict:** **DISPROVED (Airtight)**.

### Case 6: Causal PIT Violation in Feature Reconstruction
- **Hypothesis:** Directional signals (D1/D2/D3) or regime/opportunity filters access contemporaneous or future bar prices (`close_time >= decision_t`).
- **Audit Proof:**
  - D1 (`_compute_d1`): `b_last = bars.get((t - timedelta(hours=1), product))`. Asserts `b_last.effective_close_time < t`.
  - D2 (`_compute_d2`): Reference bars iterate `k in range(2, range_hours)` (`open_time in (t - W, t)` with `t-1` signal bar excluded). Asserts `b.effective_close_time < t`.
  - D3 (`_compute_d3`): Reference bars iterate `k in range(2, range_hours)`. Asserts `b.effective_close_time < t`.
  - R_VOL & O_RANGE: Evaluate over completed bars strictly before `t`.
  - Expanding training percentile reference: `rv_sample = [v for dt, v in rv_series if dt < t]`. Future rows `dt >= t` are filtered out.
  - Frozen calibration reference: Lagged one decision step, evaluated without per-row refit.
  No future or equal-time price leakage exists.
- **Verdict:** **DISPROVED (Airtight)**.
