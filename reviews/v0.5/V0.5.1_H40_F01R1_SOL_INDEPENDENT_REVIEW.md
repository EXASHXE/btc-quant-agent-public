## 1. F01R1 requested fixes

The five findings from the prior review were rechecked.

### F01-SOL-01 — production source/split hash forgery

**PASS for the originally reported defect.**

Production seal construction no longer accepts independent:

```text
source_manifest_hash
split_manifest_hash
split_attestation_hash
```

Instead:

```text
H40RuntimeSnapshotSeal.from_verified_authority(
    source_manifest,
    split_manifest,
    repo_root
)
```

requires typed authority objects and derives their hashes.

Direct production-style dataclass construction is guarded by an internal construction token.

### F01-SOL-02 — incomplete/caller-selected roster

**PASS.**

Production verification now derives the exact accepted 168-slot materialization and requires exact roster equality.

It checks:

```text
runtime snapshot hash
exact REGISTERED roster
registered count
not-testable count
total = 168
```

The old per-entry-only membership weakness is closed.

### F01-SOL-03 — persistence restore not cold

**PASS.**

Persistence now stores an authority context and cold restore recursively:

```text
loads receipt/evidence
resolves implementation authority
resolves run authority
resolves runtime seal
resolves split authority when required
recursively restores predecessor
reruns lifecycle verifier
compares reconstructed receipt bytes/hash
```

The original process-local VerifiedLifecycleAuthorization is no longer required.

### F01-SOL-04 — no future production verifier seam

**PASS.**

A runtime-checkable typed protocol now exists:

```text
H40LifecycleEvidenceVerifier
```

with:

```text
verify_discovery_manifest
verify_candidate
verify_wf_fold
```

Synthetic verifier remains test-only and production rejects synthetic verifiers.

A future non-synthetic verifier can implement the same seam without rewriting lifecycle state machinery.

### F01-SOL-05 — synthetic R3R4 overclaim

**PASS.**

The test was reframed as final selection-order mechanics rather than claiming to prove the complete R3R4 statistical correction engine.

# 2. New BLOCKER F01R1-SOL-06 — production seal is unreachable under the accepted P1/P2 source state

This issue was exposed by the stronger F01R1 production factory.

It is not a regression in the five requested repairs; it is a previously hidden incompatibility between accepted P1/P2 source authority and the newly explicit F01 production seal path.

## 2.1 Accepted upstream authority

P1 final acceptance explicitly states:

```text
BTC canonical 1h authority remains NOT_TESTABLE
```

Current code freezes:

```text
BTCUSDT_USD_M_1H             NOT_TESTABLE
ETHUSDT_USD_M_1H             VERIFIED
BTCUSDT_OFFICIAL_DERIVATIVES NOT_TESTABLE
BTCUSDT_SPOT_FLOW            NOT_TESTABLE
ETHUSDT_DERIVATIVES_FLOW     NOT_TESTABLE
```

P2 final acceptance freezes the corresponding runtime projection:

```text
TOTAL = 168
REGISTERED = 18
NOT_TESTABLE = 150
```

The 18-row universe is intentionally the current fail-closed production universe.

## 2.2 F01R1 production construction

F01R1 now correctly calls:

```python
split_manifest.assert_authoritative(source_manifest, repo_root)
```

before issuing a production runtime seal.

However the existing P1 split authority implementation internally requires canonical BTC and ETH source records to be production VERIFIED.

The canonical source assertion explicitly rejects BTC because:

```text
BTCUSDT_USD_M_1H.production_authority_state = NOT_TESTABLE
```

Therefore, under the current accepted P1/P2 state:

```text
from_verified_authority()
-> split_manifest.assert_authoritative()
-> assert_canonical_source_record(BTC)
-> SOURCE_UNVERIFIED
```

The production runtime seal cannot be materialized for the exact accepted 18/150 universe.

## 2.3 Test gap

The positive F01R1 production-seal test does not exercise the real P1 authority path.

It monkeypatches:

```text
H40SplitManifest.assert_authoritative
```

to return success.

The typed fixture itself is not a real accepted production source/split authority object.

Thus the test proves API binding but not production reachability.

## 2.4 Why this is blocking

The accepted lifecycle contract requires the Discovery authorization to bind:

```text
runtime_authority_snapshot_hash
source_manifest_hash
split_manifest_hash
split_attestation_hash
sealed REGISTERED roster
18 / 150 counts
```

But the current implementation has no valid path to produce that seal while preserving the accepted fact that BTC remains NOT_TESTABLE.

Discovery must not solve this by:

- promoting BTC without new pre-outcome authority;
- weakening P1 canonical source verification;
- using a synthetic split attestation;
- dropping the split attestation;
- expanding the roster;
- changing the three P2 scientific hashes;
- silently changing the 18/150 universe.

This requires an explicit authority compatibility closure before further implementation acceptance.
