### 2.2 Defects and Missing Authority Facts
Before the first signed interaction (`client.query_order` at line 351), the following critical authority facts are **NOT** proven:
1. **Plan Mode Agreement**: The code checks `mode = ExecutionMode(self.config.execution.mode)`, but NEVER checks `plan.mode == mode`. If `plan.mode == "testnet"` and `self.config.execution.mode == "live"`, client mode is LIVE.

# 4. Deployment policy decision

We evaluate two distinct operational policies for resolving `ASTRA-B-04`:

| Evaluation Dimension | Policy A: Zero Signed-Write Capability in Research Deployments | Policy B: Provenance-Bound Risk-Reducing Writes Allowed |
|---|---|---|
| **Safety Posture** | **Maximum / Absolute**. If research is disabled, zero signed writes can occur under any circumstance. | High, provided cryptographic and account provenance preflight is infallible. |
| **Operational Recovery** | Requires a separate emergency operations tool/process to manage stranded positions. | Built-in CLI emergency close/reconcile capability for existing positions. |
| **Architectural Complexity** | Low: hard-kill switch on write transport in research/disabled mode. | Moderate: requires full provenance preflight verification on every write. |
| **Account/Env Spoofing Risk** | **Zero**. No credentials or signed transport available to research. | Low, controlled by strict preflight R1–R16 checks. |
| **Implementation Scope** | Clean separation of research agent from operational execution client. | Requires schema updates, database migrations, and preflight guards. |
| **Auditability** | Trivial: absence of signed capabilities guarantees no trading. | Requires full verification audit receipts for risk-reducing actions. |
| **Failure Modes** | Fail-closed: operator must use external dashboard if power cuts during trade. | Fail-closed: fails if environment, account, or plan hash mismatch. |

### Policy Decision: Policy A with Strict Policy B Execution Guard
- **Normative Research Default (Policy A)**: In all research, backtesting, discovery, and paper environments, `EXECUTION_DISABLED = True`. The `BinanceSignedClient` write methods (`place_order`, `place_protective_order`, `cancel_order`) MUST NOT be initialized or callable. Zero signed writes are exposed to the research agent.
- **Authorized Operational Execution Mode (Policy B)**: If the system is explicitly deployed in an authorized live/testnet execution runner (`allow_live = True`, explicit confirmation phrases present), it MUST strictly adhere to Policy B: only provenance-bound risk-reducing writes are permitted, gated by preflight checks R1–R16. No opening or increasing exposure write is ever permitted during reconciliation.

# 8. Reconcile authority preflight

Before creating a signed client or issuing ANY signed exchange REST request, `ExecutionService.reconcile()` MUST execute the following 16 preflight checks in strict sequence:

```text
R1:  Load persisted plan from repository by plan_id. Fail if absent or kind != "ENTRY".
R2:  Recompute canonical plan hash from payload. Require calculated_hash == plan.plan_hash.
R3:  Verify plan validation_status is acceptable for the mode (e.g. VALIDATED_FORWARD for LIVE).
R4:  Check plan expiration: if expired and status == "PREPARED", mark EXPIRED and abort.
R5:  Extract plan.execution_environment_id and plan.mode.
R6:  Resolve current runtime execution_environment_id and runtime mode from config.
R7:  REQUIRE EQUALITY: plan.mode == runtime.mode AND plan.execution_environment_id == runtime.execution_environment_id.
R8:  Resolve current runtime account_authority_id from local credentials.
R9:  REQUIRE EQUALITY: plan.account_authority_id == runtime.account_authority_id.
R10: Load persisted latest ENTRY order receipt. Fail if absent.
R11: Require entry_order.plan_hash == plan.plan_hash.
R12: Require entry_order.execution_environment_id == runtime.execution_environment_id AND entry_order.account_authority_id == runtime.account_authority_id.
R13: Require entry_order.symbol == plan.symbol.
R14: Classify intended reconciliation actions (QUERY_STATUS, CANCEL_EXPIRED, INSTALL_PROTECTIVE, FAILSAFE_CLOSE).
R15: Assert that intended action is permitted under the active Deployment Policy (Policy A prohibits all writes; Policy B permits only risk-reducing actions).
R16: ONLY NOW instantiate/use signed exchange client for query or write interaction.
```

If ANY step R1–R15 fails, execution raises `ExecutionBlocked` immediately. **Zero exchange requests are made.**

# 10. Failsafe market-reduce policy

### Exhaustive Invariant Answers:
1. **Account/Environment Verification**: MUST verify exact match with plan's `execution_environment_id` and `account_authority_id`.
2. **Position Queried First**: YES. Failsafe market order MUST query `/fapi/v2/positionRisk` immediately before submission.
3. **Side Must Match Direction**: Exit side must be `SELL` for long (`positionAmt > 0`) and `BUY` for short (`positionAmt < 0`).
4. **Quantity Capped to Position**: Order quantity MUST be `min(plan.quantity, abs(current_position_amt))`.
5. **External System Changed Position**: If position amount is less than plan quantity, the order quantity is reduced to match current position.
6. **Zero Position**: If current position is 0.0, failsafe MUST NOT place any order. Status updates to `RECONCILED_CLOSED`.
7. **Flipped Position**: If position has inverted sign, failsafe MUST abort and raise an alarm without trading.
8. **Pre-existing Protective Orders**: Pre-existing protective orders must be cancelled before issuing failsafe market close.
9. **Expired Plan**: If plan expired but position is open, failsafe market close is authorized to unwind risk.
10. **Audit Evidence**: A persistent `OrderReceipt` with `role="FAILSAFE"` and full exchange response payload must be recorded.
11. **Exposure Increase**: **NEVER**. Under no condition may failsafe increase absolute exposure.
12. **`reduceOnly=true` Verification**: Payload constructor must assert `"reduceOnly": "true"`.
13. **Exchange Response Verification**: Asserts response `status in {"FILLED", "NEW", "PARTIALLY_FILLED"}`.
14. **Exchange Rejection**: If exchange rejects `reduceOnly`, fails closed and records incident event in repository.
15. **Environment Mismatch**: Reconcile fails at R7; failsafe is never reached.

# 11. Close/cancel consistency

To ensure complete repository security, `prepare_close()`, `submit_close()`, and `cancel_entry()` MUST be aligned with the same preflight invariants:

1. **`prepare_close(symbol)`**:
   - Must verify `symbol` belongs to active allowed trading roster.
   - Must verify `execution.mode in {TESTNET, LIVE}` and check credentials before querying `/fapi/v2/positionRisk`.
   - Close plan must bind `execution_environment_id` and `account_authority_id`.
2. **`submit_close(plan_id, confirmation_hash)`**:
   - Preflight verifies `ClosePlan` hash integrity.
   - Preflight verifies `plan.execution_environment_id == runtime.execution_environment_id` and account authority match.
   - Request construction enforces `reduceOnly="true"` and caps quantity to verified current position amount.
3. **`cancel_entry(plan_id, confirmation_hash)`**:
   - Preflight verifies `ExecutionPlan` hash integrity.
   - Preflight verifies environment and account authority equality before dispatching `cancel_order` to exchange client.

# 15. Residual risks

1. **Exchange Identifier Recycling**: While Binance rarely recycles order IDs within short horizons, cross-account or cross-environment collision is completely neutralized by binding `(order_id, environment_id, account_id)`.
2. **Subaccount Routing**: When using API keys associated with Binance subaccounts, `account_authority_id` must bind the subaccount UID rather than the master account UID.
3. **Operational Unwind Dependency**: Under Policy A, disabling execution prevents automated unwinding of pre-existing live positions by the research process, requiring manual operator intervention via exchange UI.
