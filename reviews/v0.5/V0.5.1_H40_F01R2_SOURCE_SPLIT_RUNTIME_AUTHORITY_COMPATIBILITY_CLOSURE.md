## 8. Exact authority semantics

### 8.1 `source_manifest_hash`

It identifies the exact full runtime source evidence inventory bound to the
accepted protocol identity. It includes the canonical records and receipts
actually supplied for the run. It does not by itself grant production authority.
For each accepted runtime source ID, identity fields are checked against the
accepted reference source manifest while production status comes only from the
accepted `RuntimeAuthoritySnapshot`.

Thus a locally present BTC file may be inventoried but cannot change BTC from
`NOT_TESTABLE` to `VERIFIED`.

### 8.2 `split_manifest_hash`

It identifies the exact runtime-scoped authoritative split manifest. Immutable
calendar fields—partition IDs, fold roles, partition types, half-open start/end
boundaries, lookback reservation, horizon truncation, and purge structure—must
match the accepted preregistered split manifest. Availability-dependent counts,
exclusions, membership hashes, and first/last timestamps are reconstructed from
the intersection of exactly the cold-verified active required sources.

For the current 18-row snapshot that source set is exactly ETH 1h; BTC is not
part of the runtime split evidence.

### 8.3 `split_attestation_hash`

It is the canonical hash of `H40_RUNTIME_SOURCE_SPLIT_ATTESTATION_V1`, not the
legacy BTC/ETH-pair `H40SplitAttestation`, a synthetic attestation, a preregistered
schedule, a path, or a caller claim. It binds:

- the accepted reference source and split identities;
- the exact accepted runtime authority snapshot and all source states;
- the exact 168-row ledger, sealed REGISTERED roster, and 18/150 counts;
- the roster-derived active source union;
- cold evidence for every and only active required source;
- the exact runtime source manifest and runtime split manifest.

### 8.4 Cold verification and unavailable sources

Before Discovery, every source in `active_required_source_ids` must pass canonical
production identity checks, have a VERIFIED record and receipt, and pass cold
file/timestamp verification. No other source is read merely to create authority.

Every accepted source identity is still checked against the reference manifest.
Every production state is checked against the accepted runtime snapshot.
`NOT_TESTABLE` sources remain in the state entries and exact unavailable-source
set, receive no active evidence entry, and cannot be used by a REGISTERED slot.
Identity validation must be separated from the existing production-VERIFIED
assertion so checking an unavailable source cannot promote it.

### 8.5 WF and replay lineage

Discovery binds all three runtime hashes. Candidate, WF, confirmation-ready,
persistence, and restore retain the existing rule that the exact run, candidate,
source manifest, split manifest, and split attestation identities must match.
Later WF receipts therefore bind the same runtime split identity; no split may be
reconstructed under a different source set inside the same run.

## 10. Adversarial analysis

| Attack | Required fail-closed result |
|---|---|
| Locally present but NOT_TESTABLE BTC substituted as active evidence | Active source union is roster-derived and BTC state is bound as NOT_TESTABLE; reject. |
| Caller changes BTC status to VERIFIED | State entries no longer equal accepted runtime snapshot/hash; reject. |
| Source manifest changes under old snapshot | Manifest and attestation hashes change; old run authority cannot replay. |
| Runtime snapshot changes while old roster is retained | Roster must be rederived from the new snapshot; equality/count check rejects. |
| ETH omitted from the active 18-row source union | Union recomputation and per-slot dependency verification reject. |
| Synthetic split attestation supplied | Schema/type and production verifier reject. |
| Preregistered schedule presented as production evidence | `is_authoritative=False`, no runtime attestation, and no cold evidence; reject. |
| Split from one manifest paired with another attestation | Exact source/split/attestation lineage hashes disagree; reject. |
| New source introduced after seal | Exact source inventory/state set and attestation change; existing run remains immutable. |
| Source becomes VERIFIED after seal and attempts roster expansion | Requires a new accepted snapshot, new seal, and new run authority; no mutation or promotion in the old run. |
| Active source becomes unavailable after seal | Cold verification/reverification fails; no transition authority. The roster is not silently replaced. |
| Cross-run split/source receipt replay | Run, source, split, attestation, roster, and upstream receipt identities must all match; reject. |
| Path/hash self-consistency without evidence truth | Typed objects, accepted-state comparison, cold validation, and deterministic reconstruction are all mandatory; reject. |
