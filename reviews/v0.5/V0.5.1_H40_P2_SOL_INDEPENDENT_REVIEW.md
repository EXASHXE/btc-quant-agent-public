## Findings

### P2-SOL-01 — HIGH — Exact 168-row scientific grid was invented in implementation before protocol authority existed

The accepted `H40_PROTOCOL_V1_R2` freezes the legal families, allowed parameter sets, pair whitelist, and global 168-slot ceilings, but does not uniquely determine:

- the exact two variants per direction family;
- the exact 12 complete configurations per variant/pair;
- exact scope/horizon/calibration/threshold assignment;
- exact regime/opportunity choice per row;
- exact pair semantics;
- exact feature registry and hash preimages.

The P2 prompt explicitly requires escalation if exact materialization requires inventing new research degrees of freedom. A dedicated R3 repair prompt was committed before the implementation report:

```text
prompts/v0.5/research/
v0.5.1_H40R3_EXACT_P2_GRID_AND_FEATURE_SEMANTICS_PREREGISTRATION_REPAIR.md

commit:
18932b91fda432faa435da955102885bea40e9cd
```

However no authoritative document exists at:

```text
reviews/v0.5/V0.5.1_H40_PROTOCOL_AMENDMENT_R3.md
```

and no R3 independent acceptance exists.

Despite that, `search_space.py` chose and froze a concrete grid, including:

```text
D1_V1_RETURN_4H
D1_V2_RETURN_12H
D2_V1_BREAKOUT_24H
D2_V2_BREAKOUT_72H
D3_V1_FAILED_BREAK_24H

D5_V1_CROWDING_Q10_D1

```

and a specific 12-row template repeated across variants/pairs.

The implementation report itself acknowledges that independent review must decide whether these choices require formal R3 codification. They do. Symmetry is a legitimate pre-outcome rationale, but it is not a substitute for preregistration authority.

**Required closure:** author and independently accept R3 before this P2 implementation can become authoritative. Until then the current P2 code is quarantined implementation evidence, not an accepted frozen search space.

### P2-SOL-02 — HIGH — P2 reintroduces caller-forgeable authority identity

`materialize_h40_search_space()` publicly accepts caller-provided:

```text
protocol_hash
source_manifest_hash
split_manifest_hash
```

and inserts them directly into all configuration identities. `H40ConfigurationSlot.create()` and `from_dict()` likewise accept caller-controlled authority strings.

The adversarial test for authority binding proves only that changing the strings changes `config_id`; it does not prove that the strings came from the accepted protocol, the canonical P1 source authority, or the authoritative split reconstruction.

This repeats the class of authority defect closed during P1R/P1RR/P1RRR/P1R4: internal hash consistency is not source authority.

**Required closure:** production P2 materialization must derive or verify protocol/source/split identities from canonical authority objects/reconstruction. Caller-injected authority identities must either be rejected by production APIs or isolated into explicitly synthetic/non-authoritative validator APIs that cannot unlock production status.

### P2-SOL-03 — HIGH — Source testability logic drifts from accepted P1 authority

Accepted P1 canonical authority currently states:

```text
BTCUSDT_USD_M_1H
production_authority_state = NOT_TESTABLE

ETHUSDT_USD_M_1H
production_authority_state = VERIFIED
```

and `get_canonical_source_spec()` treats non-primary auxiliary sources as `NOT_TESTABLE` unless separately authorized.

The P2 search-space implementation instead only marks ETH-involving funding/D5 configurations `NOT_TESTABLE`, and the P2 test suite explicitly asserts that BTC-only D5 using `BTCUSDT_OFFICIAL_DERIVATIVES` remains `REGISTERED` as if that auxiliary source were production verified.

That assertion is not supported by current P1 canonical authority. In addition, many canonical feature contracts name both BTC and ETH primary 1h sources regardless of candidate scope, so source compatibility is not derived from an exact per-scope authority matrix.

**Required closure:** runtime/testability status must be mechanically derived from the authoritative P1 canonical source specs and the exact feature-required source set. No hard-coded assumption may upgrade BTC 1h or BTC auxiliary derivatives authority. Structural inclusion in the 168-row ledger may remain while runtime status fails closed to `NOT_TESTABLE`.

### P2-SOL-04 — HIGH — D5 base-direction invariant is not actually fail-closed

The mandatory P2 rule is that D5 cannot become standalone funding direction and must explicitly depend on D1/D2/D3.

The public `H40ConfigurationSlot.create()` factory silently injects:

```text
base_directional_owner = D1_TREND_CONTINUATION
```

whenever D5 is present and the caller omitted a base owner. Therefore a caller that supplies D5 without a base is not rejected; the factory changes the semantics for the caller.

The test only checks an explicitly invalid base owner and the raw dataclass constructor, so it misses the public-factory bypass.

There is also an internal pair inconsistency: the D3+D5 pair references the feature ID:

```text
D5_V1_CROWDING_Q10_D1
```

whose canonical feature contract is explicitly bound to D1, while the pair payload declares D3 as the base directional owner.

The implementation report also describes D5 V2 as `...Q20_D2`, while code materializes `...Q20_D1`, which is another identity/report mismatch to eliminate when R3 freezes exact semantics.

**Required closure:** missing D5 base owner must fail closed; no factory may inject one. Every D5 feature/pair identity must agree exactly with its declared base owner, and report/protocol/code IDs must match bit-for-bit.

### P2-SOL-05 — MEDIUM — Configuration identity does not bind semantic contract content hashes

Each `H40FeatureContract` has a content hash and geometry/calibration/refit contracts have contract hashes, but `H40ConfigurationSlot.config_id` currently binds mostly string IDs such as:

```text
regime_contract_id
opportunity_contract_id
direction_contract_id
geometry_contract_id
calibration_contract_id
mechanical_refit_policy
required_feature_ids
```

It does not bind the actual content hashes of those contracts.

As a result, a feature or contract definition can materially change while retaining the same textual ID, and the configuration hash can remain unchanged. That conflicts with the P2 invariant that any material semantic mutation must change identity.

**Required closure:** bind canonical semantic contract hashes (or one frozen registry hash that transitively binds them) into each applicable configuration preimage, and test that mutating contract content under the same ID changes the configuration/ledger identity.

### P2-SOL-06 — MEDIUM — Outcome/protected-surface guards do not satisfy the full mandatory boundary

The mandatory tests require H39, Final Holdout, and confirmation-outcome references to be rejected and require no P2 API to accept outcome-bearing payloads.

Current guards reject H39/Final Holdout path markers, but do not generically reject H40 confirmation outcome locators. A required input such as a confirmation-outcome/label path that avoids the H39/Final-Holdout substrings can pass the current path guard.

The configuration forbidden-key checks also inspect only top-level mapping keys; nested mappings can contain forbidden outcome/performance keys without being recursively rejected.

`availability_rule` validation is similarly lexical (`CLOSED_BAR` or `<`) rather than an exact canonical rule identity, so malformed/future semantics can potentially hide behind a permissive string.

**Required closure:** use recursive outcome/protected-token validation across nested semantic payloads and explicit confirmation-outcome locators; use exact canonical availability/closed-bar contract identity rather than substring acceptance. Add adversarial tests for nested payloads and confirmation-outcome paths.

---

### P2-SOL-07 — MEDIUM — Feature contracts do not explicitly freeze normalization/source compatibility at the required granularity

The P2 prompt requires every feature contract to freeze normalization, exact product/scope compatibility, and source-authority requirements.

Current `H40FeatureContract` has transform parameters and product scope, but no explicit normalization contract field and no exact candidate-scope compatibility matrix. Many own-asset features default to requiring both BTC and ETH source IDs, even when used by `BTC_ONLY` or `ETH_ONLY` slots.

This is not merely a documentation omission because it changes whether a row should be structurally compatible/testable and what source authority is required.

**Required closure:** R3 and P2R must define and hash exact normalization plus per-feature/per-scope source requirements. Own-asset features must not silently acquire cross-asset dependencies unless the contract explicitly says so.
