## 6. First-Discovery launch sequence after authorization

The binding operational sequence is defined in
`docs/h40/V0.5.1_H40_DISCOVERY_LAUNCH_RUNBOOK.md`. In compact form:

1. Recompute every accepted scientific, lifecycle and implementation hash.
2. Recompute accepted source states and the exact 168-slot projection.
3. Cold-materialize runtime source/split authority and attestation.
4. Materialize the immutable 18-entry roster and production seal.
5. Materialize `H40_RUN_AUTHORITY_V1`; no caller run ID or nonce.
6. Construct verified `H40_RECEIPT_DISCOVERY_AUTH_V2`.
7. Atomically persist its content-addressed bytes and commit the durable head.
8. Restore/reverify the committed head; only then permit the first Discovery
   outcome read.
9. Produce the complete 18-entry canonical Discovery result evidence.
10. Recompute hard gates and the accepted correction/selection contract.
11. Emit either an absorbing termination receipt (`H40_NO_GO`) or the single
    candidate-lock authorization. Never promote a runner-up.

The accepted selection semantics remain exactly:

```text
within-family universe = REGISTERED rows of that family in the sealed snapshot
PRECISION and NET_EXPECTANCY max-statistic corrections = separate
cross-family correction = Holm over family representatives
selection order = all hard gates
               -> highest adjusted LCB net expectancy
               -> highest adjusted LCB precision
               -> lower complexity
               -> ascending structural_configuration_hash/configuration ID
runner-up promotion = prohibited
```

Later WF consists of exactly `WF1..WF4` validation folds. Confirmation is not
a fifth fold and remains separately sealed by F02.

## 8. Fail-closed conditions

Before any outcome access, stop without issuing Discovery authority for:

- any scientific, lifecycle, governance or implementation hash mismatch;
- publication validation remaining incomplete;
- accepted implementation-authority object/hash mismatch;
- source-state drift or local-file-based source promotion;
- source manifest, split manifest or source/split attestation mismatch;
- runtime snapshot, slot counts or sealed roster mismatch;
- missing/extra/duplicate/reordered roster entries;
- non-deterministic or caller-selected run identity;
- policy other than `RESEARCH_DISABLED_V1` or any execution write authority;
- attempted Confirmation, H39, Final Holdout or signed-exchange access;
- failure to durably commit and restore/reverify the Discovery receipt head.

After Discovery begins, accepted termination/NO-GO paths include failure of an
existing accepted hard gate, no candidate passing every gate, incomplete or
misbound evidence, source truth changing under the run, or any accepted
`H40ReasonCode` condition. No statistical threshold is added or changed here.
No losing candidate may be promoted.

## 9. Additional execution blocker discovered

The executable tree contains the typed `H40LifecycleEvidenceVerifier` seam and
the explicitly non-authoritative `H40SyntheticEvidenceVerifier`, but no
production implementation of the scientific evidence verifier or Discovery
runner. `authorize_candidate_lock()` fails closed with
`no accepted scientific evidence verifier` when none is supplied.

Classification:

```text
ACCEPTED_PRODUCTION_DISCOVERY_EVIDENCE_VERIFIER_NOT_MATERIALIZED
blocks = candidate-lock/NO-GO scientific adjudication after Discovery evidence
does_not_block = deterministic construction of the initial Discovery receipt
```

This preparation does not redesign or implement that verifier. Before any P3
authorization that permits an outcome-bearing Discovery run end-to-end, the
independent authorization decision must require a production verifier that
implements the already accepted seam and exact `DISCOVERY_SELECTION_V1`
contract, with separate acceptance evidence. Synthetic verification cannot be
promoted. This is a bounded implementation/acceptance gap, not a request to
reopen H40 scientific architecture.
