## 3. Chosen WAL/SHM State Machine

The read-only inspection branch of `ForwardDerivativeStore._connect()` now classifies the sidecar state **before any `sqlite3.connect` call**:

| State | DB | `-wal` | `-shm` | Read-only behavior |
| --- | --- | --- | --- | --- |
| Missing store | absent | — | — | `FileNotFoundError` → degraded (unchanged, T1/T2) |
| Stable checkpointed | present | absent or size 0 | absent | `immutable=1` URI read; provably creates no side files (unchanged, T3/T6) |
| Any non-empty WAL | present | present, size > 0 | present **or absent** | **never opens SQLite** — raises `ForwardStoreWalRecoveryRequired` with the stable classification `FORWARD_STORE_WAL_RECOVERY_REQUIRED`; `read_status` degrades deterministically (new, T8/T9) |

The `mode=ro` branch is removed entirely. R2 is satisfied by construction: `immutable=1` is only ever used when no non-empty `-wal` exists, so stale checkpointed state can never be reported in a WAL state, and no read-only connection can ever materialize a `-shm` (or any other recovery state).

### Why conservative degrade on WAL+SHM (T9 decision)

The prompt permits either a `mode=ro` read when WAL+SHM already exist, or a conservative degrade on any non-empty WAL. This repair chooses the conservative degrade, for reasons verified during implementation:

1. **No product expectation requires live-WAL health reads.** `ForwardDerivativeStore.read_status` has exactly one production consumer (`service.py` health handler). A repository-wide search found no test and no caller exercising the live-WAL `mode=ro` branch — the AG-04 suite's populated-store helper closes all writer connections and asserts sidecars are removed before GET.
2. **The single-writer workflow checkpoints on last close.** The store has one writer (scheduled/manual collector); SQLite removes the `-wal`/`-shm` sidecars on the writer's last connection close. A non-empty WAL therefore exists only during an in-flight collection or after a crash — a brief window in which health reporting `DEGRADED` is correct fail-closed behavior.
3. **The `mode=ro` branch is precisely what enabled the defect.** Retaining it would keep a subtle SQLite-behavior dependency (missing-`-shm` materialization; reader lock/read-mark bookkeeping on the SHM) and shift the proof burden onto "no new filesystem member" arguments. Removing it makes the invariant trivially provable: health never opens SQLite in a WAL state, therefore it can never create a directory member, never run recovery, never migrate schema.
4. **SHM byte-equality becomes provable.** Because SQLite is never opened on a WAL store, the conservative design also proves SHM byte-immutability (T9 receipt below) — the caveat the prompt anticipated for a `mode=ro` design does not apply.

The writer constructor `ForwardDerivativeStore(path)` is untouched (R3): `_initialize()` still prepares/migrates the schema, `append()` still writes, and normal writer reads are unchanged. R4 is satisfied: the degraded path reuses the existing `read_status` exception handling; no status/reliability/audit logic was duplicated.

## 4. Crash-Leftover WAL Reproduction Method

T8/T9 build the crash/recovery filesystem state hermetically from **genuine WAL-mode committed content** (never a fake empty file), via the new `_capture_and_restore_wal_image` helper:

1. populate the store through the real writer workflow (`ForwardDerivativeStore(path)` + `append(_record())`); the writer's per-operation connections close and checkpoint, removing all sidecars (asserted);
2. open a raw `sqlite3.connect` on the store and `INSERT` one extra committed row into the real schema — in WAL mode the commit appends genuine frames, leaving the live `-wal` non-empty (and a live `-shm`);
3. capture the non-empty WAL image (and the SHM image when covering T9) while the connection is open;
4. close the connection — the last close checkpoints and removes both sidecars (asserted absent);
5. restore the WAL image — and the SHM image only for T9 — so the final state has **no open connection**: DB + non-empty `-wal` + `-shm` absent (T8 crash-leftover) or present (T9 pre-existing);
6. snapshot directory membership and SHA-256 hashes, invoke the **real** `/health` handler (resolved through the FastAPI routing table, only scheduler/Binance externals mocked), and compare.
