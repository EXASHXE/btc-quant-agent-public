### 1.2 Separation of Feature Maturity Dimensions (Resolving B05)
To prevent confusion between feature registry definitions and actual production Discovery capabilities, this revision distinguishes three distinct engineering dimensions:
1. **`FEATURE_CONTRACT_DEFINED`**: The contract ID and schema are registered in the protocol authority hash tree (`src/btc_quant_agent/h40/protocol_authority.py`).
2. **`FEATURE_FORMULA_IMPLEMENTED`**: The mathematical calculation is implemented in code (`src/btc_quant_agent/h40/feature_contracts.py`).
3. **`PRODUCTION_DISCOVERY_RECONSTRUCTION_SUPPORTED`**: The active execution branch exists in `discovery_evidence._reconstruct_prefit_cached` (`src/btc_quant_agent/h40/discovery_evidence.py:1077-1092`). Currently, **only D1–D3 variants are supported**; D4, D5, and all pair contracts trigger a closed-fail (`H40ReasonCode.NOT_TESTABLE`).

## 3. Detailed Reclassification Findings

### 3.1 Reclassification of BTC / D4 Expansion (Resolving B04)
The previous Baseline R2 asserted that BTC expansion required only "one configuration step" / adding `BTCUSDT_USD_M_1H` to the P1 snapshot. This claim was factually deficient:
1. `P1_SOURCE_AUTHORITY_STATES[BTCUSDT_USD_M_1H] = NOT_TESTABLE` in `src/btc_quant_agent/h40/protocol_authority.py:434-450`.
2. The canonical BTC production authority is currently `NOT_TESTABLE`.
3. The frozen BTC locator in `source_manifest.py` is `data/research/BTCUSDT/data_manifest.json`, which is an archive inventory/checksum manifest, not economic hourly OHLC rows. The production JSON adapter requires actual hourly bars/rows.
4. **Mandatory Future Closure Steps**:
   - Binding canonical BTC 1h economic artifact/adapter (`hourly_bars` exposure).
   - Validating byte-to-economic-row integrity via content digests.
   - Materializing formal source validation receipts.
   - Promoting runtime source authority state to `ACCEPTED`.
   - Minting a new runtime authority snapshot hash.
   - Running full production verifier checks on the newly bound source.

### 3.2 Production Discovery Support Boundary (Resolving B05)
1. **D1–D3 Variants**: Fully implemented and supported in `discovery_evidence._reconstruct_prefit_cached`. Powers the 18 REGISTERED slots.
2. **D4, D5, and PAIR Variants**: While formulas exist in `feature_contracts.py`, `_reconstruct_prefit_cached` actively branches to `_fail("unsupported direction contract", H40ReasonCode.NOT_TESTABLE)`. They cannot run under current production Discovery code until:
   - Dedicated reconstruction/composition logic is added to `_reconstruct_prefit_cached`.
   - Focused unit tests verify causal reconstruction for pairs.
   - Exact-SHA evidence is produced and accepted by the Controller.
