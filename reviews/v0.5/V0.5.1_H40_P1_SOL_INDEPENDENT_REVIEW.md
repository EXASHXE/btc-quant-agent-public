## Findings

### P1-F1 — HIGH — Confirmation readiness is caller-forgeable

`H40ConfirmationGuard` accepts public constructor input `is_confirmation_ready=True`. A caller can therefore instantiate an unlocked guard without any `H40_CONFIRMATION_READY` authority, attestation, nonce, or lifecycle proof.

`H40LifecycleStateMachine` similarly accepts an arbitrary `initial_state`, including post-P1 states, so a caller can construct a state machine already at `H40_CONFIRMATION_READY` or later without traversing the authorized chain.

The existing test verifies only the default-false path. It does not attempt the forged-ready constructor attack.

Required closure for P1: pre-confirmation code must not expose any caller-controlled mechanism that turns outcome access on. Until a future separately authorized task introduces a content-addressed readiness attestation, P1 confirmation outcome access should remain hard-denied. Lifecycle construction must not permit arbitrary initialization into later states.

### P1-F2 — HIGH — Protected-source loader can be re-labeled to open H39 / Final Holdout

`H40SourceManifest.verify_file_integrity()` checks source status and then opens `record.locator`. It does not invoke `H40ProtectedSurfaceGuard` before filesystem access.

An adversarial caller can construct a new `H40SourceRecord(status=VERIFIED, locator=<H39-or-Final-Holdout-path>)`, place it in a manifest, and call `verify_file_integrity()`. Because the record is labeled VERIFIED, the default FORBIDDEN source records are bypassed and the protected locator can be opened.

The prompt explicitly required that H39/Final Holdout locators cannot be opened through the H40 source loader. Current tests cover only default FORBIDDEN records, not a re-labeled/re-hashed manifest attack.

Required closure: protected-surface/path authority must be checked independently of caller-supplied source status, before `exists()`, `read_bytes()`, parsing, or any other file content access. Add adversarial tests using a re-labeled VERIFIED protected locator and a re-hashed serialized manifest.

### P1-F3 — MEDIUM — Split authority is generated from an assumed continuous calendar, not reconstructed from verified source timestamps

`H40SplitManifest.build_default()` calls `get_base_eligible_timestamps()`, which generates a continuous hourly range from hard-coded dates. It then intersects fold windows with that generated set. It does not consume independently verified BTC/ETH timestamp sets, duplicate/gap evidence, or the pooled trustworthy timestamp intersection.

Therefore source gaps, duplicate timestamps, or membership changes do not automatically change the default split. The exclusion counts are also hard-coded constants rather than derived from source timestamp evidence.

`H40SourceManifest.build_default()` also marks multiple sources VERIFIED from embedded metadata/hashes; actual local byte/timestamp validation is a separate optional call and is not a prerequisite to producing the authoritative default source/split hashes.

This conflicts with the P1 requirement that exact eligible/split membership be materialized from verified source timestamps, with gaps removed rather than assumed absent.

Required closure: separate preregistered schedule constants from materialized authority. A source/split manifest that claims VERIFIED/authoritative status must be built from or bound to an explicit validation receipt over the exact local artifacts and timestamp-only inventories. Split membership must be computed from the verified BTC/ETH timestamp intersection (and endpoint constraint), not a synthetic continuous range. Missing/gap/duplicate attacks must deterministically alter/fail the manifest.
