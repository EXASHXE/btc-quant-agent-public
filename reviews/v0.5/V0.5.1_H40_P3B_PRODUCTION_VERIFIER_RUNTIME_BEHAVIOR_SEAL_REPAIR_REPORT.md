## 1. Context and root cause

Prior commit `b653a2e` enforced an exact runtime type seal requiring `type(verifier) is H40ProductionDiscoveryEvidenceVerifier` before invoking scientific verification in `H40LifecycleAuthorityService.authorize_candidate_lock`. However, Python's dynamic runtime environment permitted several severe same-type substitution and tampering vulnerabilities:

1. **`object.__new__` uninitialized forgery**: Callers could bypass constructor validation by instantiating `object.__new__(H40ProductionDiscoveryEvidenceVerifier)` and attaching arbitrary return values or methods, bypassing all source/split/seal integrity checks.
2. **Instance method shadowing**: Instance-level attribute assignment (`verifier.verify_candidate = fake_fn`) shadowed class methods during normal instance dispatch.
3. **Class method monkeypatching**: Class methods could be replaced or intercepted at runtime without detection.
4. **Authority-state mutable replacement**: Instance fields bearing authority context (`_resolver`, `_seal`, `_receipt`, `_split`) could be mutated post-construction to point to different data without failing validation.
5. **Transitive mutation via resolver/root**: The evidence resolver or root directory could be pointed elsewhere post-construction.
6. **Scientific result post-verification tampering**: The internal cache `_verified` could be mutated after `verify_discovery_manifest` but before `verify_candidate` consumption.
7. **Test suite reliance on illegal double**: The lifecycle test suite itself utilized `_ProductionEvidenceVerifier()` constructed via `object.__new__` with monkeypatched lambdas, masking test holes.

This repair establishes a hardened, in-process runtime behavior and authority seal that eliminates all of these attack vectors while keeping legitimate scientific verification and explicit synthetic lifecycle modes fully operational.

## 3. Runtime behavior seal mechanism

The runtime behavior seal operates across four structural boundaries:

### 3.1 Class-level write protection (`__slots__` and write-once `__setattr__`)
`H40ProductionDiscoveryEvidenceVerifier` and `H40DiscoveryEvidenceResolver` declare explicit `__slots__` covering all internal attributes. Their `__setattr__` methods enforce write-once semantics for all authority-bearing fields (`_resolver`, `_seal`, `_receipt`, `_split`, `_approved_evidence_root`, etc.):
- During `__init__`, attributes are assigned once.
- Once `_initialized` is set, attempting to overwrite authority-bearing fields or set arbitrary new attributes raises `TypeError` or `H40GuardError(CONFIG_IDENTITY_CONFLICT)`.

### 3.2 Constructor completion and integrity binding (`_VERIFIER_BINDINGS`)
Upon completion of `H40ProductionDiscoveryEvidenceVerifier.__init__`, a complete binding tuple:
```text
(root_resolved, resolver, seal_hash, receipt_hash, split_hash)
```
is registered in a private module-level `WeakKeyDictionary` `_VERIFIER_BINDINGS`.
If an instance was created via `object.__new__` or aborted during `__init__`, it lacks an entry in `_VERIFIER_BINDINGS`. Calling any method or passing it to lifecycle authority triggers `assert_runtime_integrity()`, which immediately raises `H40GuardError(CONFIG_IDENTITY_CONFLICT, "production verifier failed constructor integrity verification")`.

### 3.3 Class-bound dispatch and class method immutability
In `lifecycle_authority.py`, all calls to the verifier are dispatched via frozen class mappings:
```python
_VERIFIER_METHODS["assert_runtime_integrity"](cast(H40ProductionDiscoveryEvidenceVerifier, verifier), seal=seal, receipt=discovery_receipt)
_VERIFIER_METHODS["verify_discovery_manifest"](cast(H40ProductionDiscoveryEvidenceVerifier, verifier), evidence, evidence.candidate_result_entries)
_VERIFIER_METHODS["verify_candidate"](cast(H40ProductionDiscoveryEvidenceVerifier, verifier), entry, run_authority_id=..., correction_manifest_hash=...)
```
Because dispatch uses `_VERIFIER_METHODS[...]` directly, any instance-level method shadowing is completely bypassed.
Furthermore, `assert_runtime_integrity()` verifies:
```python
all(getattr(H40ProductionDiscoveryEvidenceVerifier, name) is method for name, method in _VERIFIER_METHODS.items())
all(getattr(H40DiscoveryEvidenceResolver, name) is method for name, method in _RESOLVER_METHODS.items())
```
Any tampering with class-level methods is detected and rejected.

### 3.4 Scientific result binding (`_VERIFIER_RESULTS`)
At the end of `verify_discovery_manifest`, canonical SHA256 of `_manifest_hash`, `_evidence_hash`, `_verified` results, `_entries_by_id`, and `_dependencies` is computed via `_result_binding()` and stored in `_VERIFIER_RESULTS[self]`.
In `verify_candidate()`, `assert_runtime_integrity()` and `_result_binding()` matching are validated. Any direct tampering with `_verified` post-verification raises `H40GuardError(CONFIG_IDENTITY_CONFLICT, "production verifier scientific results changed after verification")`.

### 3.5 Legitimate mutable caches preserved
Normal scientific execution that mutates `_manifest_hash`, `_evidence_hash`, `_verified`, `_dependencies`, and `_entries_by_id` during legitimate verification flows is fully preserved.
