## Findings

### R3-SOL-01 — HIGH — Regime and opportunity gate boundaries remain unfrozen

BASE Section 5.1 explicitly authorizes rolling-percentile cutoffs:

```text
{0.20, 0.40, 0.60, 0.80}
```

and BASE Section 5.2 requires opportunity output to be one of:

```text
NONE | WATCH | ELIGIBLE
```

with the numeric boundaries persisted in the complete configuration. Only `ELIGIBLE` may proceed.

R3 selects one regime contract and one opportunity contract for all 168 rows:

```text
R_VOL_RANGE_V1_24H
O_RANGE_EXPANSION_V1_24H
```

but specifies only a rolling percentile / expansion percentile and says `ELIGIBLE` proceeds. It never freezes:

- which exact R_VOL percentile cutoff/state is required for a row to pass;
- the exact numeric boundary between regime states;
- the exact numeric `NONE -> WATCH -> ELIGIBLE` boundaries for O_RANGE_EXPANSION;
- exact equality-edge behavior at each boundary.

Therefore two compliant implementations can materialize the same textual contract IDs while emitting different gate decisions. This is a direct remaining research degree of freedom and prevents the 168 rows from being semantically constructive.

**Required closure:** R3R1 must freeze exact numeric state boundaries and equality behavior pre-outcome. No threshold may be left to implementation, fitting-time choice, or later tuning.

### R3-SOL-02 — HIGH — Single-family D5 variants do not bind an exact independent base-direction variant

R3 correctly states that funding never supplies side and freezes:

```text
D5_V1_CROWDING_Q10_D1 -> base family D1_TREND_CONTINUATION
D5_V2_CROWDING_Q20_D2 -> base family D2_BREAKOUT_CONTINUATION
```

But R3 itself freezes two different D1 variants and two different D2 variants:

```text
D1_V1_RETURN_4H
D1_V2_RETURN_12H
D2_V1_BREAKOUT_24H
D2_V2_BREAKOUT_72H
```

The D5 single-family required-feature lists do not include an exact D1/D2 base-direction feature, and the D5 contracts do not state which base variant/lookback produces the side. `base directional owner = D1` or `D2` is therefore insufficient to reconstruct an exact direction signal.

This is not the already-fixed D3+D5 pair mismatch; it is a separate ambiguity in the 24 single-family D5 rows.

**Required closure:** each D5 single-family variant must bind exactly one base direction contract/variant/feature, exact lookback, side-generation operator, and include that base feature in the required-feature/source/hash identity. Missing or mismatched base identity must fail closed; no family-level default is allowed.

### R3-SOL-03 — HIGH — D4 directional projection is not uniquely defined across BTC_ONLY / ETH_ONLY / POOLED scopes

R3 freezes:

```text
D4_V1_CONFIRMATION_4H: sign of synchronized BTC+ETH agreement
D4_V2_DIVERGENCE_8H: sign of relative divergence between BTC and ETH
```

and declares both variants compatible with all three scopes. But it does not freeze the exact operator that converts the two-asset state into a target-product side.

For `D4_V2_DIVERGENCE_8H`, materially different implementations remain possible, for example:

- `sign(r_BTC - r_ETH)` applied identically to both products;
- target-relative `sign(r_target - r_other)`;
- divergence continuation versus divergence mean-reversion;
- pooled mode emitting opposite product sides versus one common side versus abstention.

For `D4_V1_CONFIRMATION_4H`, the exact behavior when signs disagree, one sign is zero, or magnitude/state equality lies on a boundary is also not fully specified.

Because D4 contributes 24 single-family rows and appears in two authorized pair families, this ambiguity is material.

**Required closure:** R3R1 must freeze exact mathematical formulas, target-product projection, pooled behavior, conflict/zero/equality behavior, and output schema for both D4 variants. No implementation-defined sign convention may remain.

### R3-SOL-04 — HIGH — Protocol/hash identity is not yet bitwise reproducible

R3 improves the hash hierarchy by binding contract content transitively, but the final identity still contains unresolved representation choices.

First, `configuration_hash` binds:

```text
H40_PROTOCOL_V1_R3 identity/hash
```

without defining the exact protocol-authority hash algorithm or exact value that independent implementations must use.

Second, `registry_hash` is defined over the "entire frozen semantic registry", while R3 does not fully freeze the registry-only regime/opportunity contracts that are not used by the active 168 rows. Therefore registry membership/content is not unique.

Third, Section 10 says numeric rounding follows repository `canonical_json` and parenthetically describes floats as rounded to the source-field precision. The repository canonical serializer does not itself perform such float rounding. That description is therefore not an exact executable canonicalization rule.

These ambiguities defeat the R3 requirement that independent implementations reproduce identical `configuration_hash` and `ledger_hash` values.

**Required closure:** R3R1 must define a non-ambiguous protocol-authority identity/hash procedure, exact registry membership/order, and exact numeric canonicalization. Prefer direct use of the repository canonical JSON semantics with no implicit rounding, or explicitly encode normalized numeric values before canonical serialization. The final independent acceptance must record the exact accepted R3 authority identity used by P2R1.

### R3-SOL-05 — MEDIUM — The original R3 contract-registry requirement is only partially satisfied

The R3 repair prompt requires one canonical semantic contract identity for every authorized regime family:

```text
R_VOL_RANGE
R_TREND_RANGE
R_LIQ_ACTIVITY
R_CROSS_ASSET
R_FUNDING_CROWDING
```

and every authorized opportunity family:

```text
O_RANGE_EXPANSION
O_COMPRESSION_RELEASE
O_BREAKOUT_DISTANCE
O_EXPECTED_EXCURSION
O_TPBR_MAGNITUDE
```

The amendment fully specifies only the two contracts selected into the active 168-row search:

```text
R_VOL_RANGE_V1_24H
O_RANGE_EXPANSION_V1_24H
```

and leaves the other eight at family-level BASE semantics. Because R3 simultaneously refers to a full authorized registry and to an `registry_hash` over the entire frozen registry, this incompleteness is not purely editorial.

**Required closure:** freeze the remaining canonical registry-only contracts to the required deterministic granularity, or—only if the governing R3 requirement is explicitly superseded—define a narrower active-registry hash membership that cannot be confused with the full authorized family registry. The safer closure is to fully freeze all ten canonical regime/opportunity contracts as originally required.
