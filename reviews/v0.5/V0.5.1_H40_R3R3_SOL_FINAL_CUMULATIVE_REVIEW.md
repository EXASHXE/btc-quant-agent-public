## 3. Remaining findings

### R3R3-SOL-10 — HIGH — Calibration can still emit a side opposite to the frozen direction owner

R3/R3R1 freeze a direction owner's side-generation rule. R3R2/R3R3 then map signed `raw_score` to `p_up`, but the action rule remains effectively:

```text
LONG  if p_up >= q
SHORT if p_up <= 1-q
```

R3R3's `a >= 0` constraint prevents rank inversion but does **not** guarantee sign-consistent actions because the fitted intercept is unrestricted. Example: with sufficiently positive `b`, a negative raw score can still have `p_up >= q` and emit LONG. The same issue exists for isotonic calibration: a monotone nondecreasing map may still assign `p_up > q` to a negative score.

That would silently transform a preregistered continuation/reversal side into the opposite side without a registered direction family.

Required repair:

```text
proposed_side = sign(raw_score)

if proposed_side == +1:
    emit LONG only if p_up >= q
    otherwise NO_TRADE

if proposed_side == -1:
    emit SHORT only if p_up <= 1-q
    otherwise NO_TRADE

if proposed_side == 0:
    NO_TRADE

Calibration is a confidence gate only. It never flips side.
```

This preserves BASE/R3 direction ownership and creates no new slot or threshold.

### R3R3-SOL-11 — HIGH — Isotonic prediction semantics between/outside fitted scores remain undefined

R3R2 freezes PAVA training and tie pooling but does not define how an arbitrary future `raw_score` is mapped to `p_up` when it lies:

- between distinct fitted calibration scores; or
- below the minimum / above the maximum fitted score.

Different valid isotonic implementations use stepwise, linear-interpolated, clipped, or error-on-out-of-range prediction. D1 continuous scores make this outcome-affecting.

Required repair: freeze one deterministic evaluation map. Recommended minimal contract:

```text
PAVA produces fitted probability at each sorted unique calibration score.
For query x:
  x <= min_score -> fitted probability at min_score
  x >= max_score -> fitted probability at max_score
  otherwise      -> probability at the greatest fitted score <= x
```

This is a clipped left-step monotone map; no interpolation parameter exists.

### R3R3-SOL-12 — HIGH — Adaptive-bin ECE is still not reproducible

BASE makes `ECE <= 0.05` a hard calibration gate with at least 20 observations/bin. R3R3 freezes the binary population but still leaves adaptive bin count, ordering, tie treatment, leftover allocation, and exact ECE formula unspecified.

Two implementations can therefore accept/reject the same candidate differently.

Required repair: freeze one exact equal-frequency adaptive-bin algorithm, including:

- bin count;
- deterministic sort/tie key;
- exact integer boundaries;
- minimum-20 rule;
- empty/insufficient behavior;
- `ECE = sum_b (n_b/N) * |mean(y_b)-mean(p_b)|`.

No calibration threshold may be tuned from ECE.

### R3R3-SOL-13 — HIGH — Discovery/candidate-lock ranking and multiplicity universe are not fully frozen

Cumulative authority says:

- discovery/initial lock uses only WF1 Train + WF1 Calibration;
- configurations are compared within family by block-resampled max-statistic;
- family representatives undergo Holm control;
- final selection is lexicographic by adjusted LCB expectancy, adjusted LCB precision, lower complexity, lexicographic ID.

Still unresolved:

1. Which partition supplies the actual candidate-selection precision/expectancy statistics.
2. Which rows form the within-family correction universe after the runtime authority snapshot (all 168 structural rows cannot all emit metrics when many are `NOT_TESTABLE`).
3. Whether precision and expectancy correction are run independently as separate metric families.
4. How a family with zero testable/defined candidates is represented.
5. What exactly `lower complexity` means.
6. Exact deterministic tie ordering.

Required conservative closure:

- WF1 Training fits feature/gate/geometry parameters and supplies training-only null inputs.
- WF1 Calibration is the only discovery outcome partition used for candidate-ranking precision/expectancy and fitted calibrator.
- The correction universe is frozen from the sealed pre-outcome runtime authority snapshot. `NOT_TESTABLE` rows remain in the immutable ledger but never become candidates and never get substituted.
- Run metric-specific max-statistic correction separately for precision and net expectancy using their existing metric IDs/seeds.
- A family with no eligible representative produces no representative and cannot win.
- `complexity = len(family_combination)` only (`1` single-family, `2` pair); all same-depth candidates tie on complexity.
- Final fallback ordering is ascending canonical structural configuration ID.

The repair must preserve existing alpha levels/nulls and must not invent a new outcome threshold.

### R3R3-SOL-14 — HIGH — `p0` is exact per fold but not exact for discovery and pooled multi-fold comparison

R1/R2 define fold-specific empirical base-rate nulls using each fold's training label rates and evaluation side mix. BASE later compares pooled walk-forward precision against a single `p0` but does not freeze pooled aggregation. Discovery candidate-lock also lacks a uniquely named `p0` construction.

Required repair:

```text
p0_discovery:
  WF1 training label rates + emitted LONG/SHORT mix on WF1 calibration.

p0_fold_k:
  fold-k training label rates + emitted side mix on fold-k validation.

p0_WF_pooled:
  accepted-trade-count weighted mean of p0_fold_k across the four validation folds
  (equivalently average per-trade fold-specific null hit probability).

p0_confirmation:
  preserve R2 exact pre-confirmation training definition + confirmation side mix.
```

Every `p0` remains `max(0.50, base_precision)`.

### R3R3-SOL-15 — MEDIUM/HIGH — Candidate-lock training sample-floor population is ambiguous

BASE requires `training n_eff >= 120` and calibration accepted-trade/sample floors, but final action acceptance depends on a calibrator fitted later on WF1 Calibration. It is not explicit whether the training floor is measured on:

- pre-calibration directional opportunities; or
- retrospectively applying the calibration-fitted action rule to WF1 Training.

This affects `NOT_TESTABLE` status and candidate availability.

Required repair: define the training floor as a **fit-support floor**, not retrospective final-action performance:

```text
training_fit_population = WF1 training rows passing A..F with proposed_side != 0,
                          before confidence calibration/threshold.
training n_eff is computed on this proposed-side population using the existing HAC rules.
```

Calibration accepted-trade floors remain based on actual calibrated/thresholded actions on WF1 Calibration. This preserves chronology and gives the two floors distinct roles.

### R3R3-SOL-16 — HIGH — Mandatory `RANDOM_MATCHED` final benchmark has no executable sampler

BASE requires canonical net PnL to exceed the 95th percentile of `RANDOM_MATCHED`, matched on eligible opportunity set, trade count, side count, horizon/holding time, product scope, and deterministic seeds. The exact randomization/sampling algorithm is not frozen.

That leaves a final GO/NO-GO degree of freedom after observing outcomes.

Required repair before any outcome:

- universe = candidate's evaluation rows passing source/PIT/regime/opportunity gates before direction selection;
- preserve candidate primary horizon and product scope;
- for each product, match exact accepted trade count and LONG/SHORT counts of the locked candidate;
- sample entry rows uniformly without replacement within product for each replicate;
- assign exact side counts by deterministic RNG permutation;
- 10,000 replicates;
- canonical JSON seed preimage including protocol/candidate/partition/`RANDOM_MATCHED`;
- explicit insufficient-universe fail-closed behavior;
- exact upper-95th nearest-rank value = sorted replicate net PnL index `9499` for `M=10000`;
- run every sampled decision through the same frozen fixed-horizon economic/cost semantics; no outcome-aware matching.

This is a baseline definition, not a new strategy/search family.

### R3R3-SOL-17 — MEDIUM — Side-specific `n_eff` should be made explicit

BASE hard gates use LONG-specific and SHORT-specific `n_eff`. The cumulative HAC contract is exact for a supplied trade series but does not explicitly say how side-specific series are constructed.

Required clarification:

```text
LONG n_eff  = run the existing n_eff algorithm on the chronological subset of accepted LONG trades only.
SHORT n_eff = run it on the chronological subset of accepted SHORT trades only.
Timestamps are retained unchanged; occupied UTC days and exact-hour lag pairs are recomputed on the subset.
```

No new estimator is introduced.
