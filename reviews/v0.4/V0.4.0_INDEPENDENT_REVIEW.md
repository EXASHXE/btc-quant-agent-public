## 3. BLOCKER findings

### B1 — 非默认初始资金产生无交易收益

**FACT：** `economic/portfolio.py:25–34` 分别将 `initial_cash` 和 `cash` 默认设为 100,000。传入 `initial_cash` 不会更新正值的默认 `cash`。`economic/simulator.py:103` 只传入前者。

影响：本金、收益率、仓位大小、随机基准和 drawdown 起点全部可能错误。

最小复现：`cash_creation`，一根价格恒定的 candle、无信号、`initial_cash=1000`。期望终值 1,000、PnL 0；实际终值 **100,000、PnL +99,000、收益率 9,900%**。空 candle 输入反而返回 1,000，形成输入长度依赖。

建议修复：新建组合现金唯一来源为初始本金；恢复快照必须使用明确的独立接口。不得把合法的零余额默默恢复为初始资金。测试任意正本金、空/非空输入均满足无交易恒等式。

### B2 — 未来信息被提前使用，持仓/资金费事件没有统一时间顺序

**FACT：** `execution_model.py:97–118` 使用尚未收盘的 candle close，却记录为 `earliest_fill_ms` 成交；LIMIT 用整根 high/low 证明到达后成交。`simulator.py:129–148,272–295` 在当前循环立即应用未来 candle 的成交，并先处理整根 bar 的资金费，之后才处理其开盘信号。

影响：能在未来成交前 mark-to-market、平仓或收费；资金费遗漏/多收；具有前视信息的成本与仓位历史不能用于 qualification。

最小复现：

- `future_close_at_earlier_time`：bar `[1000,1999]`，open=100、close=120；实际把 1999 才可知的价格 120 记在 **1650** 成交。
- `future_fill_applied_immediately`：LIMIT 在 **3000** 成交，却在 **2999** 已平仓，净赚 1；事件历史明确倒序。
- `entry_bar_funding_missed`：已报告 1650 开仓，1800 结算应支付 1，实际 0。
- `post_exit_funding_charged`：已报告 2000 平仓，2500 结算应为 0，实际支付 1；历史先写 2500 funding，再写 2000 close。

建议修复：统一按实际信息可用时间和事件序号推进，未来成交仅作为 pending event，到账时才改变组合。价格、成交量及市场状态也必须带 availability。OHLC 内到达前后的极值无法分解时输出 `AMBIGUOUS/NOT_TESTABLE` 或使用明确的保守场景；禁止反向补写资金费或持仓。

### B3 — 退出触发与成交脱节，未成交仍可被记为平仓

**FACT：** `simulator.py:166–219` 的 stop/target 只是触发条件，正常 MARKET 退出价格来自之后的 bar；失败时 `actual_exit_price` 直接回退到理想触发价。LIMIT 退出复用了 entry order type，却没有传 `limit_price`，因此被执行层拒绝后仍由回退路径成交。反转路径 `:246–255` 完全绕过执行模型。退出历史采用 bar close 而不是返回的实际 fill timestamp。

影响：可在无流动性、缺失后续数据或不可知的盘内路径下制造收益、限制亏损；声称 stop-first 并不能保证保守结果。

最小复现：

- `stop_target_collision` / `short_stop_target_collision`：入场 100、stop/target ±5%，下一 bar high=110、low=90，之后开盘分别 120/80。LONG 和 SHORT 都记 **+20**，且最大回撤 0。应报告歧义或明确的保守止损场景，不能认证 +20。
- `gap_stop_fabricated_fill`：入场 100，下一根也是最后一根 bar 全部在 80，5% 止损却以 **95** 成交，损失仅 5；95 没有成交证据。
- `trailing_extreme_order`：O/H/L/C=100/120/99/115、trailing 10%；low→high→close 路径没有触发，high→low 路径可能触发，实际统一以 108 平仓、+8。
- `entry_bar_stop_target_skipped`：零延迟在 bar open 入场、同 bar 同时触及 stop/target，实际完全不检查，保留持仓。

建议修复：分离退出触发规则和退出订单；所有退出经过同一执行接口。只有确认成交才能减少持仓。数据耗尽应保留未平仓并标记结果不完整，或采用预注册且有数据支持的终值处置；禁止 fallback fill。保存 exit reason、触发时间、下单时间和实际成交时间。

### B4 — 公共账本接受非法方向转移，且校验失败后已改变状态

**FACT：** `portfolio.py:69–99` 不校验 action 与现有仓位方向；`TradeEvent` 在组合变更后才构建（`:101`）。事件数量用请求 quantity，即使实际 close 被截断。

影响：下游正常误用即可消除已存在的浮亏、改变错误方向的仓位，或留下没有 ledger event 的持仓。当前 simulator 的部分路径避开了这些调用，但作为通用经济账本接口不能成立。

最小复现：

- `implicit_opposing_open`：short 1@100，再 `OPEN_LONG 1@110`，应拒绝或实现亏损 10 的平仓；实际仓位归零、现金/PnL 不变，浮亏被抹掉。
- `wrong_side_close`：long 1@100，再 `CLOSE_SHORT 1@90`，应拒绝；实际 long 变成 **2**，现金加 **10**。
- `non_atomic_trade`：以 `timestamp_ms=0` 开多，事件构造抛错，但实际仍留下 quantity=1、history=[]。

建议修复：先完整校验，再原子计算并提交状态与事件；明确单向净持仓的合法 action 表，先平后反向开仓或统一 signed-fill 语义。超量平仓选择拒绝或记录真实成交量，禁止请求量与状态差分不一致。

### B5 — 正式经济资格结论没有可比基准及运行证据约束

**FACT：** `benchmarks.py:183–227` 接收任意 `SimulationSummary`，仅比较 PnL 是否超过现金和 5 次随机试验的均值，直接返回 `ECONOMICALLY_QUALIFIED`。summary 未绑定数据区间、policy、execution/cost/funding 配置、实验版本或完整性。随机基准未接收策略实际交易数/曝光约束，且没有传入策略的 funding events 或自定义 execution model。

影响：混用不同风险、成本或市场窗口的结果，也会产生正式 qualified；并不只是“缺少更先进的统计检验”。

最小复现：`unbound_qualification` 从无交易、无事件、gross=0 的 summary 只改 final/PnL 为 +1，即得到 qualified；不需要 ledger 或 experiment。`passive_not_required_for_qualification` 中 Passive BTC +10%，构造的策略仅 +0.001%，仍 qualified。后者本身不证明必须击败 BTC，而是证明“所有基准必过”的架构文档和代码不一致。

建议修复：将当前布尔结果降为诊断比较；正式判定必须绑定不可变的 simulation evidence 与预注册 comparison contract，验证经济恒等式、输入区间、产品、资本/风险/曝光、成本和终值可比性。明确 Passive BTC 是强制 hurdle 还是背景指标。最终研究晋级由独立决策层合并统计和经济证据，模拟器无需硬编码统计方法。本审查不新增盈利或显著性阈值。

## 4. HIGH findings

### H1 — 声明的风险、市场状态和若干策略参数未执行

**FACT：** `policy.py:22–60,89–117` 声明多项参数；`simulator.py:235–279` 没有读取 `risk_budget`，`should_enter(sig)` 使用默认 spread=0，quantity 调用不传 ATR，LIMIT 价格固定为 bar.open。

影响：用户改变风险约束却得到相同交易结果；缺数据时反而扩大仓位。

最小复现：`ignored_risk_and_filters` 设置 max positions=0、gross cap=1、巨大最小成交量、禁止 regime，仍在零量 bar 开 100 notional；`drawdown_halt_ignored` 的 halt 阈值为 1，亏损 10 后继续开仓；`missing_atr_full_allocation` 中 ATR=None/0/-1 都按全额本金配置；`limit_offset_ignored` 设置 500 bps 被忽略，买单应为 95 且不成交，实际 100 成交；`signal_asset_not_checked` 将 ETH 信号交易为 BTC。

建议修复：逐字段建立“执行或显式拒绝”契约；风险检查覆盖订单提交、pending exposure、实际成交及资金变化。缺 ATR/market-state 应 fail closed。仓位应以可用信息计算并包含费用缓冲；现有 leverage cap 只限制参考 open notional，成交滑点/跳空后可突破。缺乏保证金/强平模型时明确限制支持范围，不能声称支持任意杠杆。

### H2 — LIMIT 流动性、maker 分类和成本假设过度确定

**FACT：** `execution_model.py:159–239` 严格 trade-through 后无条件全量成交，所有 LIMIT 都标 maker；touch 参数只判断 `>=1.0`，没有概率抽样或部分成交。`fee_model.py:39–44` 在零 volume 时把 impact 设为 0；使用整根成交 bar 的 volume 计算此前的成交成本。执行模型和模拟器可以分别持有不同 FeeModel。

影响：可能低估手续费、冲击和未成交风险；声称存在 queue uncertainty 与实际行为不符。没有 L3 模型本身不是问题，无证据的全量 fill 才是问题。

最小复现：`zero_volume_full_fill` 的 volume=0，却将 1000 单位买单全部填在 95、maker=true；`touch_probability` 在默认 0.2 与 0.99 下均恒定不成交。`fill_after_expiry` 的到期时间 1600，实际 1650 才成交（到期时序根因归 B2）。

建议修复：OHLC-only 明确使用有边界的保守场景或不可测试状态；不能证明 maker 或容量时拒绝正式评估。统一成本配置身份，禁止 reversal/fallback 绕过。分离 spread 与 impact 输入并标记观察时刻；没有数据不得默认为零成本。

### H3 — 注册协议可就地修改，状态可跳级、解冻和覆盖

**FACT：** `research_contract/registry.py:19–49` 暴露 `allow_update=True` 覆盖同 ID，返回内部对象，允许任意状态转移；frozen dataclass 的嵌套 dict/list 仍可改。`status_updated_at` 保存的是状态名称而非时间。

影响：事后改公式/参数/方法不产生新 protocol identity，且无法证明 qualification 所依据的是哪一份定义。

最小复现：`registry_mutation_and_thaw` 通过返回对象把参数 k 从 1 改成 999，然后 `PROPOSED→ECONOMICALLY_QUALIFIED→FROZEN_ARCHIVE→PROPOSED` 全部成功；`registry_protocol_overwrite` 以同 ID 改 statistical test，无 revision/history/hash。

建议修复：分离不可变 protocol 与追加式 decision events；注册后修改必须新 revision/hash；读取返回不可变内容或副本；明确 legal transition graph 和证据引用，冻结状态不可回退。无需绑定 FWL，也无需实现通用 workflow 框架。

### H4 — JSON 注册表写入不原子，独立 writer 会静默覆盖

**FACT：** `registry.py:23–26,61–76` 先修改内存，再直接 `write_text` 全文件；无原子替换、锁、revision CAS 或失败 rollback。读取坏 JSON 会抛异常，但没有保留上次有效快照的机制。

影响：部分写入可毁掉当前注册历史；两份合法实例都会报告成功，但早先记录丢失。

最小复现：`registry_lost_update` 在同一路径先创建 r1/r2，再分别注册 a/b，最终只剩 b；`failed_save_memory_disk_divergence` 注入磁盘错误后，内存已有 c 而磁盘无 c；`corrupt_registry` 返回 JSONDecodeError，属于正确的 fail closed，但没有恢复路径。截断写入风险来自 `write_text` 静态语义，本次未模拟断电或真实磁盘损坏。

建议修复：最小方案是明确单 writer 并真正加锁，用版本比较及同目录临时文件+原子替换，失败不提交内存；或者使用简单事务存储。保留有效历史/损坏诊断。加载时核验外层 key 与内部 experiment ID 一致。

### H5 — 绩效指标的口径不足以支撑经济比较

**FACT：** `simulator.py:224,259,307–333` 胜负只减 exit fee，不减 entry fee/funding；PF 用 gross realized PnL；gross 字段只算已平仓，net 包含未平仓 MTM；Sharpe 固定 `sqrt(35040)`，没有时间间隔验证。Passive 的 terminal fee 不进入曲线/DD；random 的均值 summary 配最后一次 trial 的曲线。

影响：净亏交易被列为胜利，无风险/高 Sharpe 印象被放大；终值和曲线无法对账。

最小复现：`net_loser_reported_winner`：gross +0.075、总费 0.1000375、net **−0.0250375**，实际 win rate=100%、PF=∞；`open_terminal_position`：net +10、gross 0、trade count 0，缺 unrealized 字段；`sharpe_cadence_ignored`：1 秒与 15 分钟的相同价格路径均报 **146.850069411063**；`passive_terminal_fee_curve` 和 `random_mean_vs_last_curve` 见 §9。

建议修复：逐 round trip 分配 entry/exit fees 与 funding，gross/net 指标分别命名；报告 realized/unrealized 及终端处置。按经校验的时间 returns 计算、或不输出权威年化 Sharpe；加入初始本金点。非有限值应以显式状态序列化。净值、曲线、费用和交易明细必须可重建对账，曝光时间/资本利用率必备。

## 6. Accounting verification table

合成单位：USDT、quantity=1；本金 C₀=100,000。合法线性永续账本应满足：

`cash = C₀ + Σrealized − Σfees + Σfunding`

`equity = cash + signed_qty × (mark − average_entry)`；`net = equity − C₀`。

开仓不扣除/加入全部合约买卖本金，SHORT 不增加卖出所得：**这是线性衍生品现金/抵押品口径，未发现现货卖出所得与 PnL 双计**。它不是完整保证金或强平引擎。

## 7. Execution/fill verification

| 项目 | 当前实际行为 | 审查判断 |
| --- | --- | --- |
| MARKET | 找第一根 close_time≥arrival 的 bar；bar 内到达使用未来 close，却记 arrival timestamp | B2，不满足 point-in-time |
| LIMIT strict trade-through | low<buy limit / high>sell limit 即整笔成交；不能证明发生在到达之后 | B2/H2；只是换了比较运算符，没有解决事件顺序 |
| mere touch | 默认不成交；参数 0.99 仍不成交，≥1 才全量成交 | 默认保守可接受，但概率名及 queue 描述不真实 |
| partial / capacity | 无 partial；任意量都可全填 | H2；先明确有限支持范围，不要求实现 L3 |
| expiry | 仅比较 bar.open 与 expiry；arrival>expiry 也能填 | B2，`fill_after_expiry` 已复现 |

## 8. Cost/funding verification

### 手续费与滑点：手算对照

默认 rate 只是代码假设，本审查没有验证账户实际 fee tier。

| 参考价100、quantity2、固定滑点10bps，BUY / SELL | 100.1 / 99.9 | 100.1 / 99.9 |
| 上述 BUY/SELL，taker 5bps，按实际 notional | .1001 / .0999 | .1001 / .0999 |
| maker rate2bps、notional200 | .04 | .04 |

BUY 向上、SELL 向下，因此对 LONG/SHORT 的双边方向均正确。spread-and-impact 只加一次半 spread；slippage 已进入 fill price，没有再从 cash 单独扣减，未发现基础公式双扣。FIXED_BPS 不另外加 spread，应写明它是总滑点场景而非 spread 数据模型。

固定路径的高滑点单调性已核验；**改变滑点也可能改变触发/仓位/交易序列，不能要求所有策略回放收益全局单调**。需要同时保留固定 fill-path 不变量与路径变化解释。当前 fallback/reversal 和两份 fee_model 的分歧破坏了成本口径统一性（H2）。

### 资金费：符号正确，时序错误

模型使用离散给定结算事件，公式 `−signed_qty × settlement_mark × rate`；没有实现按持有时长比例分摊，尽管 docstring/原报告使用了 proration 字样。`settlement_interval_hours=8` 实际未参与计算。

| --- | --- | --- |
| q=+2/−2，mark100，rate=+.01 | −2 / +2 | −2 / +2 |
| q=+2/−2，mark100，rate=−.01 | +2 / −2 | +2 / −2 |
| q=0 | 0 | 0 |
| q=1，结算1000/2000/3000，每次−1，window[1000,3000] | 当前闭区间定义下−3 | −3 |
| window[1001,2999] | −1 | −1 |
| window[2000,2000] | 必须指定事件同刻顺序；不能仅靠闭区间推断 | 0（entry>=exit提前返回） |
| 连续 windows[1000,2000] 与[2000,3000] | 同一结算事件不得重复 | −2 + −2 = −4，共享2000被重复统计 |

窗口 helper 的双计来自调用两个闭区间，当前 simulator 未调用它；不能把该 helper 风险误写成 simulator 已双计，simulator 的已复现问题是 B2。

对交易所语义仅查阅官方说明，没有请求 live rate API：Binance 说明资金费取决于结算时持仓，USDⓈ-M 名义价值按 mark×quantity；实际结算处理存在时间偏差，边界附近开平仓不能仅凭名义整点断言是否收费。因此本内核应把 settlement event 解释为给定的实际事件，明确同 timestamp 顺序；不能把当前 Python 的闭区间任意选择当作 Binance 精确重现。[Binance 官方资金费说明](https://www.binance.com/en/support/faq/detail/360033525031)（查阅：2026-09-08）。
