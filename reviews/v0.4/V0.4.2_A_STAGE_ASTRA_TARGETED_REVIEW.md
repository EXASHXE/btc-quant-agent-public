### AS-01: production atomic destination replacement bypasses the guard

`FormalBenchmarkSuite.write(path)` at `economic/qualification.py:680` calls
`_atomic_write_json`. `EconomicRunResult.write` and qualification-result writing
share the same primitive. The writer checks/creates only the destination parent,
uses `tempfile.mkstemp` and `os.fdopen`, then calls `os.replace(temporary, target)`.
The A02 fixture wraps `open`, several `Path` methods and `sqlite3.connect`, but
does not guard `os.replace`'s destination.

Concrete scenario: a test mistakenly passes the protected runtime file
`var/quant.db` as the result output path. The parent `var` is allowed, the temporary
filename is not `quant.db`, and the final replacement does not call a wrapped
file-opening method. Likewise, a file named `final_holdout.json` in an allowed
parent can be replaced even though a direct read of that file is forbidden.
Targets below a wholly forbidden parent are normally stopped by `parent.mkdir`;
that protection does not cover these exact-file cases.

Reproduced with a public production API, without mocking its writer:

```text
quant.db read BLOCKED FORBIDDEN_OPERATIONAL_FILE_ACCESS
quant.db PUBLIC suite.write RETURNED
final_holdout.json read BLOCKED FORBIDDEN_FINAL_HOLDOUT_ACCESS
final_holdout.json PUBLIC suite.write RETURNED
quant.db overwritten_to P6_BENCHMARK_SUITE
final_holdout.json overwritten_to P6_BENCHMARK_SUITE
```

Only disposable, auditor-created sentinel files under `/tmp/a_stage_public_write_*`
were overwritten. No actual operational or holdout file was targeted.

Consequence: a wrong output parameter in ordinary Phase-B persistence tests can
destroy a protected exact-file store while CI remains green. This is not a
malicious raw-syscall counterexample: the public production writer performs the
replacement itself.

Smallest safe repair: extend the test guard at the repository's atomic
replace/rename boundary, checking source and destination semantics (including
relative paths, symlinks and supported directory descriptors), or install an
equivalent comprehensive guard on the actual persistence boundary. Preserve
production behavior. Regression: call real public artifact `write` methods on
populated synthetic forbidden exact files and Final Holdout-named files; require
`ForbiddenTestAccess` before replacement and verify original bytes remain intact.
Include an allowed temporary-output positive control and Python 3.11/3.12/3.13.

### AS-02: SQLite localhost URI is checked as a different filesystem path

`_sqlite_candidate` strips `file:` and the query and unquotes the rest. Given
`file://localhost/tmp/example.sqlite3?mode=ro`, it checks
`//localhost/tmp/example.sqlite3`. SQLite accepts `localhost` as a local URI
authority and opens `/tmp/example.sqlite3`. Thus the denylist checks a different
path from the one SQLite opens. Ordinary `file:/...` and `file:///...` controls
were blocked; the localhost form reached a registered forbidden synthetic DB.

The actual `_open_sqlite` production helper accepts `path_or_uri` and forwards
`uri=True`, so the probe used the project's real SQLite entry point. Most current
callers construct `file:{path}?mode=ro`; no claim is made that they all currently
emit localhost URIs. This is a valid input to the guarded API, not an alternative
database library or a disabled guard.

```text
plain BLOCKED FORBIDDEN_OPERATIONAL_FILE_ACCESS
uri BLOCKED FORBIDDEN_OPERATIONAL_FILE_ACCESS
localhost_uri BYPASS ('synthetic-only',)
```

Consequence: normal SQLite URI spelling can bypass both protected-root and
protected-file matching and read real store contents during a test.

Smallest safe repair: parse SQLite filename URIs according to SQLite's local
authority/path interpretation before canonicalizing. Handle empty authority and
`localhost`, reject unsupported authorities, preserve percent-decoding and memory
database behavior, and distinguish URI-enabled connections as necessary.
Regression: populated fake Forward/H39/runtime stores, plain/relative/absolute
URIs, `file:///`, `file://localhost/`, encoded paths and symlink aliases must all
fail before connection; allowed temporary and in-memory databases must work.
