# v0.5.0 R02 — Runtime / Orchestration Convergence

## Mission

Continue the v0.5 simplification on `EXASHXE/btc-quant-agent` after accepted R01.

R02 is an **orchestration and entry-surface convergence round**, not an economic-kernel redesign. Reduce duplicated runtime construction, duplicated command wrappers, overlapping health/diagnostic surfaces, stale compatibility entrypoints and unnecessary API/CLI exposure so that the repository presents one obvious current research workflow and a small number of operational/supporting surfaces.

Do not optimize for a cosmetic module count. Optimize for fewer ways to reach the same semantics and fewer paths an agent/researcher must understand.

# 3. Canonical orchestration goals

After R02, the active tree should have an obvious separation:

```text
A. Formal research
   explicit formal job
   -> formal facade
   -> accepted replay / benchmark / qualification kernel

B. Forward evidence collection
   PIT market/derivatives/opportunity/microstructure collection
   -> stores / evidence health

C. Protected H39
   blind accumulation / integrity / readiness / frozen one-shot machinery

D. Operational diagnostics
   health / network / evidence status

E. Execution interface
   separately gated and disabled by default
```

A new reader should not have to distinguish several wrappers that ultimately perform the same orchestration.

# 4. CLI convergence

Current R01 report records approximately 22 top-level commands / 62 leaf paths. Re-audit actual R02 baseline and reduce the surface where semantics overlap.

Prefer coherent command families rather than many historical top-level verbs. Candidate convergence directions include, but are not mandates:

- keep one formal research family for `backtest/research/replay` semantics, preserving explicit job/output requirements and fail-closed behavior;
- consolidate overlapping forward evidence status/audit/health/doctor surfaces where they are only presentation wrappers around the same evidence providers;
- consolidate network diagnostic entrypoints if duplicate;
- remove aliases that add no semantic distinction;
- place legacy read-only performance output under an explicitly diagnostic namespace or remove it if no retained consumer requires it;
- keep H39 operations visibly separated/protected rather than blending them into generic research;
- keep execution visibly separated/gated rather than hiding it behind research orchestration.

Do not change formal research commands into implicit-default jobs. Missing/malformed formal inputs must remain fail closed and must not construct operational state as fallback.

Every removed CLI leaf requires a negative parser/dispatch test proving it cannot silently fall through to another authority.

---

# 5. Runtime service construction

Audit `QuantService` construction and configuration loading.

Goals:

- avoid constructing runtime DB/network/service objects for commands that do not need them;
- avoid multiple wrappers that create the same service with slightly different defaults;
- centralize only genuinely shared orchestration, not semantic authority;
- preserve explicit-config fail-closed behavior;
- preserve bounded network behavior;
- preserve execution-disabled defaults;
- preserve formal command behavior that runs before operational service construction.

Do not create a new general-purpose dependency-injection framework. Prefer small explicit functions/data objects.

---

# 6. Health / diagnostics convergence

Inventory all `status`, `health`, `doctor`, `audit`, `diagnose-*` paths.

Where multiple surfaces merely gather the same underlying read-only state, converge them into a small explicit diagnostic layer with structured data and thin presentation.

Requirements:

- diagnostics remain read-only unless an existing command is explicitly an operational recovery action;
- diagnostics must not become research/promotion authority;
- H39 diagnostic/status functions must not read blinded outcomes beyond already accepted metadata boundaries;
- no public exchange call from tests;
- network diagnostics continue through bounded request semantics;
- recovery/mutation operations must remain explicitly named and cannot be triggered by a read-only health call.

Do not force unrelated scientific validation logic into a generic health object.

---

# 7. API surface

Re-audit the current API routes instead of assuming the old Astra count.

The project is a personal low-frequency research tool, not a public multi-tenant service. Keep HTTP API only where it provides a real current workflow benefit.

For each route decide:

```text
KEEP_REQUIRED
KEEP_OPTIONAL_READ_ONLY
REMOVE_REDUNDANT
DEFER_EXECUTION_GATED
```

Prefer a much smaller optional read-only API over preserving routes solely for historical completeness.

Do not remove an execution safety gate by deleting an outer route while leaving a newly easier internal bypass. If execution routes remain, disabled/default confirmation semantics must remain exact.

Do not alter formal economic authority through API simplification.

---

# 8. Remaining tools

R01 reduced `tools/` heavily. Re-audit the remaining scripts.

Keep standalone scripts only when they are genuinely useful as:

- protected H39 operations;
- formal research entrypoints not cleanly covered by `quantctl`;
- bounded maintenance/evidence operations;
- repository engineering tooling such as surface inventory.

If a tool is just a thin duplicate wrapper around a canonical CLI/facade and carries no distinct hermetic/offline role, remove it or redirect documentation to the canonical path rather than maintaining both.

Do not remove independent verifier/probe scripts merely because their behavior resembles production authority; independence can be scientifically valuable.
