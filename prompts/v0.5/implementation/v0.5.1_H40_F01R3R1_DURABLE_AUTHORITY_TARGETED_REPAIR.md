## SOL-01 — production WF revalidation / cold-restore contradiction

Current issue:
- initial production authorize_wf_validation correctly rejects caller-provided split authority;
- revalidate_authorization for WF extracts the stored split authority and passes it back to authorize_wf_validation;
- cold restore does the same;
- therefore a future production WF authorization would be unable to revalidate, persist or restore even after P3 validation contracts exist.

Required semantics:

Production initial issuance:
1. derive expected WF authority internally from verified run/seal;
2. verify evidence against the derived object;
3. issue WF authorization.

Production revalidation:
1. derive expected WF authority internally again;
2. if an existing persisted/context split object exists, compare it exactly with the newly derived object;
3. do not pass that object through the public caller-override parameter;
4. rerun WF verification.

Production cold restore:
1. cold-resolve root run/seal;
2. derive expected WF authority internally;
3. if a persisted split context exists, require exact equality with the newly derived object;
4. invoke WF verification without treating the persisted object as caller authority.

Synthetic test mode may keep explicit split injection.

Do not add public trusted/internal/skip flags. If needed, use a private helper or construction token.

Keep the current production fail-closed behavior while accepted P3 statistical validation contracts do not yet exist. Do not invent P3 contracts.

Required tests:
R01 production-shaped initial WF uses internally derived authority
R02 production-shaped WF revalidation avoids caller-override path
R03 production-shaped WF cold restore avoids caller-override path
R04 persisted split mismatch fails closed
R05 synthetic split injection remains test-only
R06 current production remains NOT_TESTABLE until P3 contract materialization

## SOL-02 — committed durable head must be bound to verified authorization

Current issue:
advance_run_head accepts raw run ID, receipt hash, target state and predecessor and can mutate committed state without verifying a real published receipt or VerifiedLifecycleAuthorization.

Required production flow:

VerifiedLifecycleAuthorization
-> full revalidation/root truth
-> exact immutable receipt publication
-> verify published envelope/receipt
-> internal transactional head compare-and-advance

The raw head mutation method must not remain a production authority surface. Prefer a private internal method accepting the verified authorization or a private typed commit candidate.

Before the transaction verify:
1. content-addressed receipt exists;
2. envelope parses canonically;
3. envelope receipt hash equals authorization.receipt_hash;
4. typed receipt equals authorization.receipt;
5. run ID matches;
6. target state matches authorization.target_state;
7. upstream/predecessor matches authorization.upstream_receipt_hash;
8. authorization has just passed full revalidation.

Inside the transaction retain WAL, synchronous=FULL, BEGIN IMMEDIATE, current-head reread, predecessor check, terminal check, exact sequence increment, single winner and commit.

Genesis:
- sequence zero only;
- predecessor must be null;
- only a valid null-upstream lifecycle root/scaffold transition may be first persisted;
- Candidate Lock, WF and Confirmation may not become sequence zero;
- unknown target state must be rejected.

Validate target state and transition against accepted lifecycle state/receipt semantics.

R11 wrong upstream rejected

## SOL-04 — immutable receipt publication must never overwrite

Current generic os.link failure path may fall back to exists-check then os.replace, creating a race that can overwrite another writer's final receipt.

Required authority rule:
- final content-addressed receipt is create-if-absent only;
- FileExistsError means compare exact bytes;
- different bytes fail closed;
- non-FileExists publication failure must fail closed unless using a proven no-overwrite primitive;
- do not use overwrite-capable os.replace for authoritative immutable receipt publication.

Recommended minimal POSIX behavior:
fully fsynced same-directory temp -> os.link(temp, final) -> if exists compare -> otherwise fail closed -> remove temp -> fsync receipt directory.

Required tests:
R19 identical existing receipt idempotent
R20 different existing bytes rejected
R21 non-FileExists publication failure does not replace
R22 conflicting publisher cannot overwrite winner
