# v0.5.0 R02R — Read-Only Signal API Repair

## Mission

Repair one independently confirmed R02 acceptance defect on `EXASHXE/btc-quant-agent`.

R02 implementation HEAD:

```text
6fe04536f79c95b3ba6cbb9522f39cf53d10ec48
```

R02 fast CI receipt:

```text
34829160136
FAST_CI_GREEN_PY313
```

Independent review found that R02 declares all retained HTTP API routes read-only, but two retained GET handlers still mutate repository state:

```text
GET /signals/latest
GET /signals/{signal_id}
```

Both call:

```python
service.repository.expire_signals(int(time.time() * 1000))
```

and `Repository.expire_signals()` performs persisted `UPDATE signals ...` writes.

Therefore HTTP method classification alone is insufficient: these GET routes are not behaviorally read-only.

This is a narrow R02 boundary repair. Do not broaden scope.

## Required repair

Make every retained API route classified as read-only actually behaviorally read-only.

At minimum repair:

```text
GET /signals/latest
GET /signals/{signal_id}
```

### Preferred behavior

The API should perform pure repository reads only.

It is acceptable for the API to return the persisted signal object exactly as stored without causing an expiry transition.

If preserving a user-visible logically-expired status is considered necessary, compute it only in an ephemeral response copy/view. Do **not** persist status changes, call mutating repository methods, write runtime events, update notification fields, or trigger any other side effect from GET handlers.

Do not introduce a new repository abstraction/framework just for this repair.
