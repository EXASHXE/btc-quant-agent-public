## Root cause already established

Current `ForwardDerivativeStore._connect()` read-only branch does roughly:

```text
if non-empty <db>-wal exists:
    sqlite3.connect(file:...?mode=ro)
else:
    sqlite3.connect(file:...?immutable=1)
```

This is insufficient for the no-filesystem-side-effect contract.

SQLite WAL read-only behavior allows a reader to create a missing `-shm` file when WAL exists and the directory is writable. Therefore:

```text
DB exists
non-empty DB-wal exists
DB-shm absent
GET /health
```

can become:

```text
DB exists
DB-wal exists
DB-shm CREATED
```

The current implementation comment claiming this state necessarily fails closed is incorrect.

Do not attempt to solve this by trusting the current comment or by weakening the acceptance test.

# Required semantic invariant

After this repair:

```text
GET /health
=> NEVER creates any directory
=> NEVER creates DB
=> NEVER creates -wal
=> NEVER creates -shm
=> NEVER migrates schema
=> NEVER writes application rows
```

This must hold for:

1. missing directory;
2. existing directory, missing DB;
3. normal checkpointed DB;
4. invalid/incomplete schema;
5. non-empty WAL + existing SHM;
6. non-empty WAL + missing SHM (crash-leftover state).

The last case must fail closed/degrade BEFORE SQLite can create recovery state.

## R1 — classify sidecar state before connect

In the read-only inspection path, before `sqlite3.connect`:

- compute DB path;
- compute `<db>-wal` and `<db>-shm` paths;
- inspect existence and WAL byte size without creating anything.

Required classification behavior:

### Stable checkpointed state

```text
DB exists
non-empty WAL absent
```

Use the existing sidecar-free immutable inspection path.

### WAL state with SHM already present

```text
DB exists
WAL exists and WAL size > 0
SHM exists
```

A `mode=ro` read may be used if it does not create a new filesystem member. Preserve existing files. Do not run schema migration or writer initialization.

### Crash/recovery state: WAL without SHM

```text
DB exists
WAL exists and WAL size > 0
SHM absent
```

**Do not call `sqlite3.connect` on the source DB.**

Fail closed into a deterministic degraded inspection result. Suggested error/classification:

```text
FORWARD_STORE_WAL_RECOVERY_REQUIRED
```

or another stable project-appropriate code/string.

The response should communicate that a non-empty WAL exists but the read-only health path refuses to materialize missing recovery sidecars.

Do not delete, truncate, checkpoint or otherwise alter the WAL.

## R2 — do not use immutable=1 to ignore a non-empty WAL

This is forbidden:

```text
non-empty WAL
-> immutable=1 main DB read
-> pretend status is current
```

because `immutable=1` may ignore WAL content and therefore can expose stale checkpointed state.

Fail closed is preferred to stale health data.

# Mandatory regression tests

Extend the existing R05A AG-04 test file. Do not create a broad unrelated suite.

## T8 — crash-leftover WAL without SHM

Construct a realistic SQLite WAL state where:

```text
DB exists
DB-wal exists and size > 0
DB-shm absent
```

The test must make sure the WAL is genuinely non-empty. Do not fake this only by creating an arbitrary empty file.

One acceptable test construction is:

1. create a temporary WAL-mode SQLite DB and write committed content;
2. preserve a valid non-empty WAL image;
3. close/checkpoint the writer as needed;
4. restore the WAL file;
5. ensure SHM is absent;
6. snapshot directory membership and hashes;
7. invoke the **real** `/health` handler;
8. assert degraded/fail-closed response;
9. assert no `-shm` was created;
10. assert DB/WAL hashes and directory membership are unchanged.

If the platform-specific SQLite lifecycle makes this construction awkward, use a subprocess crash/abrupt-close fixture, but keep it hermetic and deterministic.

The critical assertion is not merely the returned status. It is:

```text
before files == after files
before DB hash == after DB hash
before WAL hash == after WAL hash
SHM absent before AND absent after
```

## T9 — WAL + SHM pre-existing

Cover a realistic state where both non-empty WAL and SHM already exist.

If production chooses to inspect it with `mode=ro`:

- GET must not create additional files;
- DB/WAL membership must remain unchanged;
- source schema/application rows must not change;
- no writer initializer/migration runs.

If the platform makes exact SHM byte equality unsuitable because SQLite reader locks/read-marks can alter SHM bookkeeping, do **not** claim byte-immutability of SHM. The authority invariant is no new source files/schema/application writes. Record this distinction explicitly in the report.

It is also acceptable to conservatively degrade on any non-empty WAL instead of opening it, provided existing product expectations do not require live-WAL health reads. If choosing this simpler design, explain why and keep the code smaller.
