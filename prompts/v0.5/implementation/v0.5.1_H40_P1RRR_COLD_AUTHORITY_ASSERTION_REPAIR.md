## Mission

Close exactly this blocker:

```text
P1RR-F1 HIGH — offline caller-forgeable receipt / source-manifest / split-attestation chain
```

Current P1RR correctly prevents raw timestamp arrays and a bare `is_authoritative=true` flag from granting authority. However, `H40SplitManifest.assert_authoritative(...)` currently allows `repo_root=None`.

Because `H40SourceValidationReceipt`, `H40SourceManifest`, `H40SplitManifest`, and `H40SplitAttestation.create()` are all publicly constructible and use ordinary unkeyed hashes, a caller can create a self-consistent fake chain and pass semantic/hash checks without reproducing any real artifact bytes/timestamps.

The fix must make cold source verification mandatory for any successful authority assertion.

---

## Required semantics

### 1. No offline authority grant

A persisted split/attestation may be loaded, displayed, hashed, compared, or transported offline, but it MUST NOT acquire H40 authoritative status solely from serialized/hash-consistent state.

Any API whose successful return means "this split is authoritative" must require a filesystem/data-root verification context and cold-check source artifacts.

### 2. `assert_authoritative` must require cold verification

Preferred minimal contract:

```python
assert_authoritative(
    source_manifest: H40SourceManifest,
    repo_root: Path | str,
) -> None
```

`repo_root` must be required, not optional.

Do not provide a second public helper that silently restores offline authority semantics.

If compatibility requires accepting `None` at type level, `None` MUST fail closed with `SOURCE_UNVERIFIED`; however, prefer making the parameter required so misuse is impossible at call time/type-check time.

### 3. Reproduce artifact authority, not only hashes supplied by caller

For both BTC and ETH:

- cold-run `validate_source_artifact(...)` or equivalent against the actual referenced artifact;
- require VERIFIED status;
- require exact reproduction of receipt-relevant fields including source identity/locator/product/cadence, file SHA-256, timestamp membership hash/count, first/last timestamps, duplicate/gap semantics, and archive/checksum identity when present;
- protected-source guards must remain in force before any filesystem read.

A caller-created `H40SourceValidationReceipt(status=VERIFIED, ...)` must fail unless actual artifact inspection reproduces it.

### 4. Reconstruct split membership during assertion

Do not trust persisted partition membership solely because its split hash matches its own attestation.

After cold-validating BTC and ETH artifacts:

1. extract their timestamp sequences from the artifacts;
2. compute the BTC/ETH common timestamp intersection;
3. run the same deterministic partition calculation used by authoritative materialization;
4. reconstruct expected base count, exclusion counts, partitions, timestamp hashes, and split hash;
5. require exact equality with the persisted split/attestation.

This closes the case where a caller forges internally consistent source receipts + arbitrary persisted partitions.

### 5. Attestation remains a binding receipt, not a signature

Do not describe SHA-256 self-hash as a cryptographic signature or proof of provenance.

`H40SplitAttestation` may remain content-addressed, but its authority derives from successful cold reconstruction against actual source artifacts, not from possession of `attestation_hash`.

### 6. Keep P1/P1R accepted repairs intact

Do not weaken:

- hard-denied confirmation access;
- lifecycle construction restrictions;
- protected source path/source-id guard;
- caller-array non-authoritative behavior;
- source byte/timestamp validation;
- fixed preregistered partition boundaries;
- H39/Final Holdout protections;
- execution-disabled state.
