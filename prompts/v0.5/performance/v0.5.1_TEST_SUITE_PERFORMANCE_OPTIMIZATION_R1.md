# 3. Profile-First Methodology

All performance work must follow a strict **profile-first** approach. No premature optimization or speculative refactoring is permitted without empirical profiling data.

### 3.1 Baseline Reproduction
In an isolated checkout of `8ecff4ec4b25bf73a35309689fd3ecfacc0d3399`, reproduce the baseline metrics:
```bash
/usr/bin/time -v .venv/bin/python -m pytest -q --durations=100 > /tmp/baseline_pytest_durations.log 2>&1
```
Record:
- Exact test counts (passed, skipped, failed, warnings);
- Pytest execution duration;
- User CPU time and System CPU time;
- Peak RSS memory;
- Top 100 slowest individual tests;
- Slowest test modules and fixture setup times.

### 3.2 Categorization of Bottlenecks
Profile and classify the major contributors to test latency:
- **CPU-bound vs. I/O-bound**: Distinguish computational loops from disk/file access.
- **Intentional Scientific Heavy Tests vs. Accidental Setup Duplication**: Differentiate between tests that intentionally execute heavy simulations (e.g. Monte Carlo or bootstrap validations) and tests where expensive fixtures are reconstructed repeatedly for trivial assertions.
- **Fixture Scopes**: Identify function-scoped fixtures that read files, compute hashes, or initialize SQLite databases repeatedly across hundreds of tests.

# 4. Strict "No Cheating" Rules

Speedup MUST NOT be obtained by compromising test rigor:
- **NO test deletion**: Zero existing tests may be removed.
- **NO test skipping**: Tests may not be converted to `@pytest.mark.skip` or commented out.
- **NO parameter reduction**: Do NOT reduce candidate counts, parameter grids, seed counts, or test matrices.
- **NO bootstrap / sample truncation**: Do NOT reduce bootstrap replicates ($B$), block lengths ($L$), or sample sizes in tests that formally verify statistical properties.
- **NO weakened assertions**: Do NOT widen numerical tolerances, drop assertions, or replace exact checks with superficial smoke checks.
- **NO hidden exclusions**: Do NOT tag previously default tests as "slow" or "integration" solely to exclude them from the default `pytest` invocation.
- **NO `xfail` misuse**: Do NOT use `xfail` to mask flaky or slow tests.
- **NO silent outcome caching**: Do NOT silently cache outcome-bearing scientific data in production modules.

The post-optimization default full suite must retain at least the exact existing logical coverage.

# 5. Priority Optimization Targets

Investigate and implement optimizations in the following prioritized order:

### Priority A: Duplicate Expensive Fixture Setup
- Audit expensive fixtures reconstructed once per test function.
- Promote immutable, read-only fixtures to `session` or `module` scope where tests cannot cross-contaminate.
- Ensure proper cleanup or immutability guarantees when sharing state.

### Priority B: Repeated Filesystem & Database Scans
- Audit repeated SQLite database initialization, PRAGMA checks, table creations, and migrations in temporary directories.
- Audit repeated directory traversals, file discovery, archive hashing, and checksum calculations.
- Introduce session-scoped or content-addressed test fixtures for immutable files and reference data.
- Do NOT weaken production source-integrity checks; optimize test fixtures only.

### Priority C: Large Synthetic Dataset Recreation
- Identify synthetic DataFrames, arrays, and archive fixtures repeatedly rebuilt with identical deterministic parameters.
- Generate reusable in-memory or session-cached synthetic datasets for unit/signal tests.

### Priority D: Process and Subprocess Startup Overhead
- Audit tests that invoke `subprocess.run`, `python -m ...`, or CLI entry points repeatedly.
- Where tests are asserting internal library behavior rather than CLI argument parsing or OS process boundaries, test direct Python APIs instead.
- Retain a dedicated, bounded set of integration tests for true subprocess / CLI verification.

### Priority E: Expensive Scientific Test Loops
- Audit test suites (e.g. H40/H41 bootstrap tests) where multiple test functions independently rerun identical expensive bootstrap loops to check different return attributes.
- Compute the bootstrap simulation once in a module-scoped fixture, and assert multiple independent properties against the shared result.

### Priority F: Parallelization (`pytest-xdist`) Evaluation
- Evaluate `pytest-xdist` (`-n 2`, `-n auto`) **only after** eliminating repeated setup overhead.
- Classify tests:
  - `parallel-safe`
  - `shared-state / resource-contending`
  - `I/O-contention / SQLite-locking`
  - `memory-heavy`
- Benchmark wall time vs. aggregate peak memory under parallel execution. Parallelization must not cause out-of-memory errors on standard developer hardware.

# 6. Test Suite Taxonomy & Objectives

### 6.1 Test Pyramid / CI Tier Architecture
Design a clear, non-regressive tier architecture:
```text
Tier 0: Smoke (< 30 seconds)
Tier 1: Unit & Deterministic (< 2 minutes)
Tier 2: Integration, PIT & Source (< 5 minutes)
Tier 3: Scientific Heavy & Simulation (Isolated / Scheduled)
Tier 4: Authoritative Full Regression (authoritative full gate)
```

### 6.2 Quantitative Performance Objectives
Using the same machine baseline:
- **Authoritative Full Suite Target**:
  - Primary goal: **$\ge 40\%$ reduction in wall-clock time** ($\le 9$ minutes).
  - Stretch goal: **$\ge 60\%$ reduction in wall-clock time** ($\le 6$ minutes).
- **Fast Developer / PR Gate Target**:
  - Default fast test command completing in **$\le 3$ minutes**.
- **Memory Footprint**:
  - Zero material regression in peak RSS memory (target: maintain or reduce below the ~291 MiB baseline).
