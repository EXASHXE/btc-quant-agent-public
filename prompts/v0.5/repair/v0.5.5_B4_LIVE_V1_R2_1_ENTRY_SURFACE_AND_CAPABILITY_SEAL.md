# 3. R2.1-01 — production signed-client side effects must always pass capability policy

## Current gap

`BinanceSignedClient._require_mutation_authority()` currently contains production-code exceptions:

```python
if self.environment == "TEST" or self.base_url.endswith(".test"):
    return
```

These exceptions were added to keep legacy unit tests working with a reserved local test hostname.

That is not acceptable in the production side-effect path.

The structural invariant must be:

```text
every non-GET signed/API-key side effect
-> ExecutionCapabilityPolicyV1
-> explicit environment + namespace + endpoint authority
-> otherwise fail closed
```

Test convenience must live in tests, not in production authorization logic.

## Required repair

Remove the production bypass completely.

`_require_mutation_authority()` must always validate capability for any side-effecting request.

No production condition may skip capability checks merely because:

- environment string equals TEST;
- hostname ends in .test;
- hostname is localhost;
- test mode flag is set.

For unit tests that only validate signing/parameter assembly:

- monkeypatch `_require_mutation_authority` in the test;
- or use a test-only subclass/fake client;
- or directly test pure signing helpers if refactored.

Do not add another production escape hatch.

## Required tests

- UNBOUND client + POST => blocked before transport;
- TEST environment string alone => blocked;
- `.test` URL alone => blocked;
- TESTNET authority + official TESTNET endpoint => allowed to reach mocked transport;
- TESTNET namespace + wrong endpoint => blocked;
- wrong namespace + TESTNET endpoint => blocked;
- LIVE/production endpoint remains unreachable;
- existing HMAC/signing unit coverage still passes using test-only fixtures.

# 4. R2.1-02 — preserve the R02 strictly read-only public REST API invariant

## Current gap

Existing R02 governance tests explicitly define:

```text
API convergence:
mutating routes are absent
retained routes are strictly read-only
Only GET methods allowed on API endpoints
```

R2 currently adds:

```text
POST /live-v1/runtime/intents/{intent_id}/execute
```

through `app.add_api_route(...)`.

Using dynamic registration avoids the AST catalog but does not satisfy the actual R02 invariant.

This must be corrected.

## Required repair

The public FastAPI application must remain read-only in every runtime configuration.

Remove any public POST/PUT/PATCH/DELETE execution endpoint from `api.py`, including dynamically
registered routes.

Do not replace it with another dynamically generated mutating route.

`LiveV1Runtime.execute_intent(intent_id)` may remain as an internal orchestration method for:

- local integration tests;
- explicitly invoked TESTNET validation code;
- future separately governed execution surfaces.

For B4/B5 validation, no persistent public REST mutation surface is required.

If runtime status is exposed over HTTP, it must be read-only and must not violate existing R02
route-count/catalog authority. Prefer reusing an existing read-only status surface rather than
adding an undocumented route.

Do not alter R02 governance tests to permit mutating public routes.

## Required tests

- `create_app()` default: only existing governed read-only API surfaces;
- `create_app(live_runtime=...)`: still no mutating HTTP method;
- no POST/PUT/PATCH/DELETE route under `/live-v1/runtime/*`;
- existing R02 catalog count and GET-only assertions pass unchanged;
- existing R02 behavioral read-only tests pass unchanged;
- `LiveV1Runtime.execute_intent(intent_id)` remains callable directly in local TESTNET/mock tests;
- no raw executable fields can be provided through the public API.
