## R1-01 — One approval must materialize at most one TradeIntent authority

Current problem:

`build_trade_intent()` generates random `intent_id`, `idempotency_key`, and
`client_order_id` using `secrets.token_hex()`.

Therefore the same persisted APPROVE event can be materialized twice into two distinct
TradeIntent objects and two distinct clientOrderIds.

Existing tests only prove replay of the same already-persisted intent ID is idempotent.
They do not prove callback/approval replay cannot create a second intent.

### Required semantics

One approval authority:

```text
(case_hash, proposal_hash, approval_event_id)
```

must map to exactly one executable TradeIntent authority.

Preferred design:

- deterministic `intent_id` derived from immutable approval/proposal/case authority;
- deterministic `idempotency_key`;
- deterministic `client_order_id` derived from intent identity;
- persist `approval_event_id` as a UNIQUE natural authority in `IntentStore`;
- concurrent materialization must produce one row;
- identical replay returns existing identical authority;
- divergent replay under the same approval event fails closed.

Do not use random identity for executable authority.

The intent may bind the compile-time account snapshot hash, but replay of the same approval
must never create a second executable identity because a newer account snapshot exists.

### Required tests

At minimum:

- same approval materialized twice -> same intent identity;
- concurrent same-approval materialization -> one intent row;
- same approval + changed account snapshot -> no second executable intent;
- same approval cannot produce a second clientOrderId;
- callback replay cannot submit twice even if the caller rebuilds before execute;
- divergent payload under same approval natural key fails closed.

## R1-02 — TESTNET credential authority must be real, not hard-coded metadata

Current problem:

`TestnetExecutionBackend` calls capability policy with hard-coded:

```text
env_id = binance_usdm_testnet
cred_ns = BINANCE_TESTNET
```

while `BinanceSignedClient` currently carries only:

- base_url;
- api_key;
- api_secret.

`AccountWatch` also assigns TESTNET credential namespace metadata from mode rather than
verifying signed-client authority.

This proves URL isolation, but not actual credential-namespace binding.

### Required semantics

Introduce explicit non-secret authority metadata on the signed client or a bound credential
authority object, e.g.:

```text
environment
credential_namespace
rest_base_url
```

Requirements:

- TESTNET execution backend must pass the client's actual authority metadata to
  `ExecutionCapabilityPolicyV1`;
- never hard-code a successful namespace in the backend;
- TESTNET client creation must use a TESTNET-specific credential source/namespace;
- no B4 factory may consume LIVE credential variables for TESTNET;
- AccountWatch TESTNET mode must verify the signed client is TESTNET-bound;
- TESTNET namespace + LIVE REST URL -> blocked;
- LIVE namespace + TESTNET REST URL -> blocked;
- missing authority metadata -> blocked;
- LIVE execution still permanently blocked.

Do not serialize API key/secret.

### Required tests

- hard-coded metadata bypass is impossible;
- wrong namespace blocked;
- wrong endpoint blocked;
- wrong environment blocked;
- AccountWatch rejects mismatched client authority;
- execution backend rejects mismatched signed client before any mutation call;
- no LIVE credential source is referenced by B4 TESTNET factory/config.

## R1-03 — Complete pre-execution revalidation

Current `PreExecutionValidator` is incomplete relative to the frozen B4 contract.

It currently checks many useful gates, but does not fully re-check:

- active proposal authority;
- approval hash/actor integrity against the intent;
- current open-order conflict;
- current symbol exposure;
- current portfolio exposure;
- current simultaneous-position limit;
- current margin headroom under the bound RiskPolicy;
- current Tactical validity / current signal authority;
- duplicate `clientOrderId` exchange/local state where relevant.

### Compile-time vs current account snapshot

Do not require the current account snapshot to have the same hash as the compile-time
snapshot merely because account state legitimately changed.

Instead distinguish:

```text
compile snapshot
  -> bound into TradeIntent

current pre-exec snapshot
  -> independently verified fresh/reconciled same-account/same-environment authority
  -> current risk caps are recalculated from it
```

The compile snapshot referenced by the intent must remain verifiable/persisted.

The current snapshot may differ, but must be safer or still within all policy caps.

### RiskPolicy authority

The validator must know the exact deterministic policy whose hash equals:

`intent.risk_policy_hash`

A mismatched policy hash fails closed.

Re-evaluate at least:

- remaining daily-loss budget;
- drawdown kill threshold;
- symbol exposure headroom;
- portfolio exposure headroom;
- simultaneous positions;
- available margin;
- configured notional/leverage cap;
- open-order conflict.

### Tactical validity

For TESTNET execution, require a deterministic current Tactical validity source/callback.

If current Tactical validity cannot be established:

`TACTICAL_VALIDITY_UNAVAILABLE`

and fail closed.

Do not fabricate validity from the old proposal.

### Approval revalidation

Re-read the persisted approval and verify:

- event ID;
- action APPROVE;
- actor equals `intent.approval_actor`;
- proposal/case hashes;
- recomputed approval hash equals `intent.approval_hash`.

### Required tests

Add adversarial cases for every gate above.

## R1-04 — Delayed/partial fill protective-order reconciliation

Current problem:

If initial TESTNET `place_order()` returns:

```text
NEW
executedQty = 0
```

no protective stop is placed, which is correct at that moment.

But later `reconcile_intent()` can observe:

```text
PARTIALLY_FILLED
or
FILLED
```

and currently only updates the entry-order row.

It does not ensure a protective stop now exists for the newly filled quantity.

### Required semantics

Whenever authoritative filled quantity changes:

```text
0 -> partial
partial -> larger partial
partial -> full
```

reconciliation must ensure exchange-side protective coverage is consistent with actual
open/filled quantity.

Required:

- deterministic protective client identity derived from TradeIntent;
- query/reconcile existing protective order before creating another;
- no duplicate protective orders on replay/restart;
- protected quantity never exceeds actual open position;
- if filled quantity increases, coverage is expanded/reconciled safely;
- if protective state is uncertain, fail closed and trip/retain kill switch;
- missing protection beyond grace period trips kill switch;
- restart reconciles entry + protective state before permitting new risk.

Do not rely on initial submit response only.

### Required tests

At minimum:

- NEW/0 fill -> later PARTIALLY_FILLED -> protective order created;
- partial fill increases -> protective coverage updated;
- later FILLED -> final coverage equals actual position;
- reconciliation replay -> no duplicate protection;
- restart after delayed fill -> protection restored/reconciled;
- protective query uncertainty -> fail closed;
- protection quantity never exceeds position quantity.

## R1-05 — PositionSupervisor must be wired into the real execution path

Current problem:

`LiveExecutionService.execute_approved_intent()` calls:

`supervisor.evaluate(...)`

after fills.

That persists trigger events but does not execute:

`PositionSupervisor.process(...)`

therefore the actual coordinator path does not produce:

```text
material PositionEvent
-> PositionCase
-> AnalysisBackend
-> Feishu
```

The existing E2E test manually calls `supervisor.process()` later, so the test proves
the components can work, not that the execution coordinator is wired end-to-end.

### Required semantics

Implement a real durable orchestration path.

Acceptable designs include:

- async `execute_approved_intent` / async post-fill pipeline; or
- persist supervisor work to a durable queue and have a worker call `process()`.

Requirements:

- actual filled execution can create material PositionEvent;
- material event is converted to PositionCase;
- PositionCase is delivered to existing analysis service;
- resulting proposal/review returns through existing Feishu path when configured;
- restart cannot duplicate the same PositionCase analysis.

Do not merely add another test-only call.

### Remove fabricated supervisor inputs

Current coordinator builds supervisor observation using placeholders such as:

- `funding_rate = 0.0`;
- `oi_change_pct = 0.0`;
- `volatility_percentile = 0.2`;
- synthetic Tactical regime based only on long/short side;
- `evidence_id = "0" * 64`;
- `signal_identity = "live-signal"`.

These must not be represented as authoritative market/Tactical data.

Use actual verified sources.

If a field is unavailable:

- represent availability explicitly;
- do not trigger data-dependent predicates from fabricated neutral values.

Funding/OI/regime/grid/ADD triggers must consume actual source-bound inputs or remain
ineligible due to unavailable data.

### Required tests

- actual coordinator fill -> material event -> PositionCase -> analysis call;
- restart/replay does not analyze same event twice;
- unavailable OI/funding/regime data does not masquerade as zero/neutral authority;
- actual supplied market/Tactical values drive the corresponding trigger.

## R1-06 — Short POSITION_OPENED semantics

Current `PositionSupervisor.evaluate()` recognizes POSITION_OPENED only when:

`previous_quantity == 0 and quantity > 0`

This excludes short openings.

Required:

```text
previous quantity == 0
and
current quantity != 0
```

subject to the existing durable open-state dedupe.

Required tests:

- 0 -> positive opens long;
- 0 -> negative opens short;
- repeated same observation dedupes;
- close -> reopen long/short works correctly.
