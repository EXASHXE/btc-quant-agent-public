# 3. R5-01 BLOCKER — PENDING protection recovery requires exact-ID authority

## Defect

A `PENDING_CONFIRMATION` owner can currently be promoted ACTIVE from an aggregate open protective
order listing if clientAlgoId matches, even when `query_protective_order(exchange_id)` remains
unavailable.

## Required repair

For any owner in `PENDING_CONFIRMATION`:

1. preserve exact `exchange_id` and protective client ID;
2. retry `query_protective_order(exchange_id)` first;
3. only a successful exact-ID response may be considered confirmation authority;
4. validate the full protective contract;
5. only then transition to ACTIVE.

Aggregate `open_protective_orders(symbol)` may be used only as:
- anomaly detection;
- duplicate/foreign stop detection;
- reconciliation hint.

It must never by itself promote PENDING_CONFIRMATION to ACTIVE.

Do not default missing `algoStatus/status` to NEW during confirmation. Mandatory confirmation fields
must be present and valid.

If exact-ID query is unavailable/uncertain:

```text
remain PENDING_CONFIRMATION
retain exact owner/exchange identity
kill switch remains blocking new risk
do not resubmit blindly
```

### Required tests

- pending owner + exact-ID query unavailable + matching aggregate list => remains PENDING;
- same with missing status => remains PENDING;
- aggregate list contains exact client ID but exact query not found => remains fail-closed;
- exact query later succeeds with full contract => ACTIVE exactly once;
- repeated restart never duplicates protective POST.
