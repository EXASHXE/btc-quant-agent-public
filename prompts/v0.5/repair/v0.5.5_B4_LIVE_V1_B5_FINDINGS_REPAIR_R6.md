# 3. R6-01 HIGH — typed protective aliases must be type-safe

## Defect

Generic alias equality currently allows Python coercive equality such as:

`1.0 == True`

so a malformed alias can be hidden by a valid primary field.

## Required repair

Do not use ordinary Python equality as the authority rule for heterogeneous protective fields.

Introduce typed helpers, for example:

```text
protective_numeric_field(...)
protective_text_field(...)
protective_status_field(...)
protective_bool_field(...)
```

### Numeric aliases

For fields such as:
- quantity / origQty;
- triggerPrice / stopPrice;

each present alias must be parsed independently.

Requirements:
- reject bool before numeric conversion;
- reject NaN/Inf;
- reject unsupported objects;
- allow only explicitly supported numeric provider representations;
- if both aliases are present, compare their canonical numeric values;
- malformed secondary alias must fail even if primary alias is valid.

Prefer exact decimal canonicalization for provider decimal strings/numbers rather than Python coercive
cross-type equality. Convert to float only after alias authority is proven if downstream APIs require float.

### Text/status aliases

For:
- orderType / type;
- algoStatus / status;

require explicit string representations and exact allowed canonical values. Missing or contradictory
aliases fail closed.

### Required attacks

At minimum:
- quantity=1.0, origQty=true => reject;
- quantity=true, origQty=1.0 => reject;
- stopPrice=false with valid triggerPrice => reject;
- numeric string and equivalent supported numeric representation => behavior explicitly defined/tested;
- NaN / Inf / empty / object / list => reject;
- conflicting numeric aliases => reject;
- complete valid protective response => ACTIVE exactly once.

No malformed alias may be hidden by a valid sibling field.

# 4. R6-02 HIGH — close async runtime authority handoff

## Defect

Runtime readiness can change after the initial check and before new-risk execution because
`execute_intent()` crosses an `await` boundary.

Periodic REST can similarly update internal readiness from a stale pre-await snapshot.

## Required repair

Create one explicit new-risk admission primitive, conceptually:

`assert_current_new_risk_authority() -> verified snapshot/receipt`

It must always evaluate the **latest** account snapshot and current:
- snapshot.verify();
- account_id;
- environment;
- credential namespace;
- reconciled/quality;
- unconfigured nonzero positions;
- kill switch;
- task/stream readiness where applicable;
- legacy lifecycle authority.

### execute_intent

Required ordering:

```text
initial readiness
-> load canonical intent
-> await fresh-case/preparation
-> re-read latest account/runtime authority
-> fail if changed/invalid
-> hand off execution
```

But do not rely on the second runtime check as the sole safety layer.

The final placement path / PreExecutionValidator must also enforce the configured-symbol account
restriction on its fresh placement-time account snapshot so that an invalid runtime account cannot
produce a new-risk exchange write even if authority changes after runtime handoff.

In other words:

```text
runtime admission defense
+
placement-time backend/validator defense
```

must both reject a fresh snapshot containing any unsupported nonzero position symbol.

### periodic REST

After all awaited recovery/case work:
- discard stale local reconciliation authority;
- re-read `latest_snapshot()`;
- run the shared authority gate on that latest snapshot;
- only then set `accepting_risk=True`.

A stale earlier snapshot may never re-enable risk.

### Required attacks

- valid account A -> await -> latest snapshot becomes valid-hash account B => zero new-risk handoff;
- valid account -> await -> unconfigured ETH position appears => zero handoff and zero fake entry POST;
- environment/namespace changes during await => zero handoff;
- kill switch trips during await => zero handoff;
- periodic REST valid result -> await -> latest invalid => accepting_risk remains false;
- authority stays valid => normal path works;
- existing-side-effect recovery remains allowed where required but cannot create new risk.

# 5. R6-03 HIGH — make PositionEvent/outbox authority immutable across lifecycle

## Defect

The initial claimed row is verified, but a concurrent writer can mutate event/dispatch authority after
that check and before/during fresh-market materialization or analysis.

## Required repair

The authority used to produce a PositionCase must be immutable for the entire dispatch lifecycle.

### Schema-level immutability

Add fail-closed database protection so identity/authority fields cannot be UPDATEd or DELETEd after
creation.

At minimum protect PositionEvent:
- event_id;
- event_hash;
- symbol;
- environment;
- credential_namespace;
- account_id;
- position_side;
- position_authority_key;
- immutable event payload fields participating in event_hash.

Protect dispatch authority:
- event_id;
- event_hash;
- symbol;
- any persisted account/environment/namespace/side authority fields.

SQLite triggers or an equivalent enforced mechanism are acceptable.

Normal lifecycle mutations must remain possible only for non-authority fields:
- state;
- retry_count;
- lease token/expiry;
- frozen case fields;
- timestamps.

### Boundary revalidation

Even with schema immutability, re-read and verify durable authority:
1. after claim;
2. immediately before first external fresh-market call;
3. after fresh-market materialization and before freezing;
4. immediately before provider/analysis call;
5. after analysis and before DONE transition.

Use one canonical helper for current event+dispatch authority comparison.

Every SQL transition to freeze/renew/DONE must bind the immutable authority key/hash in its WHERE
predicate, not just event_id + lease/case fields.

### External side effects

If authority mismatch is detected before an external side effect:
- FAILED_CLOSED;
- zero provider call.

If an unauthorized concurrent mutation is attempted:
- mutation must be rejected by the DB authority fence; or
- dispatch must fail closed before further external side effects.

No corrupted authority may reach DONE.

### Required attacks

Deterministically attempt mutation:
- during fresh_market_case;
- immediately after case freeze;
- immediately before analysis;
- during analysis;
- immediately before DONE;

for:
- event_hash;
- symbol;
- environment;
- credential_namespace;
- account_id;
- position_side;
- position_authority_key.

Expected:
- mutation rejected or mismatch FAILED_CLOSED;
- no corrupted analysis admission;
- no corrupted DONE transition.

Also verify:
- static corruption before claim remains FAILED_CLOSED;
- valid frozen retry stays exactly-once;
- expired/stale worker cannot complete;
- normal valid dispatch reaches DONE exactly once.

Do not broaden this into arbitrary DB anti-tamper infrastructure; scope to Live V1 PositionEvent/outbox authority.
