# 2. R2-01 BLOCKER — bind executable TradeIntent semantics to approved proposal

## Defect

Current validation proves hash identities but not that executable intent fields are the exact
deterministic compilation of the approved proposal.

A self-rehashed forged intent can change executable fields while retaining approved hashes.

## Required repair

Create one deterministic compilation authority used by both:

- TradeIntent construction;
- PreExecutionValidator revalidation.

Preferred shape:

`compile_executable_intent_fields(case, proposal, risk_policy, ...)`

It must deterministically derive or validate at least:

```text
symbol
side
order_type
price
quantity
leverage
stop_loss
take_profit_1
take_profit_2
risk_policy_hash
environment/account constraints where compile-time applicable
```

The validator must recompute the approved executable contract from the persisted proposal/case and
reject any divergence.

Do not duplicate formulas independently in builder and validator.

If useful, add an immutable `execution_compilation_hash` to TradeIntent bound to the canonical
compiled executable payload.

### Required attacks

- double quantity + rehash -> blocked;
- change stop + rehash -> blocked;
- change TP -> blocked;
- change leverage within global max but different from proposal -> blocked;
- change LIMIT/MARKET -> blocked;
- change price while remaining inside generic drift cap -> blocked;
- side flip -> blocked;
- any executable divergence -> deterministic reason;
- unchanged canonical intent -> passes.

The validator must not merely check global risk caps; it must prove approval-executable equivalence.

# 3. R2-02 BLOCKER — exchange side-effect boundary requires persisted authorization

## Defect

`TestnetExecutionBackend.submit_intent(TradeIntentV1, ...)` can mutate exchange state from an
arbitrary in-memory intent object.

## Required architecture

The exchange-mutation backend must not accept unproven raw intent authority.

Use a persisted validation authorization/receipt, or an equivalent durable capability.

Recommended:

`PreExecutionAuthorizationV1`

bound to:

```text
authorization_id/hash
intent_id/hash
proposal_hash
case_hash
approval_event_id/hash
risk_policy_hash
account_snapshot_hash used for current validation
market_observation_hash
environment
validated_at_ms
expires_at_ms
validator/version identity
```

Lifecycle:

```text
intent_id
-> load persisted intent
-> PreExecutionValidator
-> persist immutable authorization receipt
-> backend receives authorization_id
-> backend reloads authorization + intent
-> verifies hashes/TTL/environment
-> side effects
```

Backend API should become conceptually:

`submit_authorized(authorization_id, now_ms)`

rather than accepting arbitrary executable TradeIntent objects.

If a different design is used, it must prove the same property:

**no exchange mutation is reachable unless the exact persisted intent passed current pre-execution validation.**

### Required behavior

- nonexistent approval cannot reach margin/leverage/order methods;
- in-memory forged intent cannot reach backend mutation;
- persisted but not VALIDATED/AUTHORIZED intent cannot reach mutation;
- expired authorization blocked;
- authorization/intention hash mismatch blocked;
- authorization current-account/current-market hash tamper blocked;
- replay is idempotent and cannot create a second order;
- transport uncertainty semantics remain unchanged;
- TESTNET only; LIVE remains unreachable.

Do not expose API/Feishu routes that accept raw order fields.

# 4. R2-03 HIGH — lease ownership must be proven before external analysis

## Defect

R1.2 PositionCase freeze UPDATE is guarded by lease_token but its rowcount is ignored.

## Required repair

Every guarded dispatch transition must verify ownership.

At minimum:

1. freeze PositionCase with conditional UPDATE;
2. require `rowcount == 1`;
3. otherwise stale worker aborts immediately with no analysis call;
4. immediately before `analysis_service.analyze_case()`, prove/renew lease ownership;
5. if lease ownership is lost, do not call downstream analysis;
6. DONE transition must also verify expected lease/state;
7. lease recovery by another worker uses the already frozen PositionCase.

Keep downstream B3 case reservation/idempotency as an additional defense, not the only defense.

### Required race tests

- worker A lease expires;
- worker B claims row;
- worker A freeze UPDATE gets rowcount 0;
- worker A makes zero analysis calls;
- worker B uses frozen/authoritative case and completes;
- stale worker cannot mark DONE;
- lease loss immediately before external call blocks the call;
- concurrent workers produce one downstream case/provider analysis.

# 5. R2-04 HIGH — wire B4 services into an owned runtime lifecycle

## Defect

B4 components exist but application startup currently wires only B3 TacticalLiveService.

## Required runtime

Introduce a coherent Live V1 operational runtime/container, e.g.:

`LiveV1Runtime`

owning as applicable:

```text
TacticalLiveService
MarketStreamService
AccountWatch
Account user-data stream task
Account REST reconciliation task
IntentStore
PreExecutionValidator
Execution backend
LiveExecutionService
PositionSupervisor
Position outbox recovery/drain task
KillSwitch
```

Integrate with FastAPI lifespan or a dedicated explicit Live V1 runtime entrypoint.

### Modes

Default must remain safe:

```text
SHADOW / DRY_RUN = no exchange mutation
TESTNET = explicit opt-in + TESTNET credentials + TESTNET endpoint
LIVE = impossible / hard blocked
```

Do not make merely setting `BTC_QUANT_LIVE_V1_ENABLED=true` sufficient to place TESTNET orders.

TESTNET execution must require a separate explicit execution-mode/enable configuration and
valid TESTNET credential authority.

### Startup

When operational B4 runtime is enabled:

- start public market stream;
- start account user stream when authenticated TESTNET mode requires it;
- start periodic REST reconciliation;
- recover/drain unfinished PositionSupervisor outbox;
- expose only intent-ID based execution orchestration;
- restore kill-switch/account reconciliation state before new risk.

### Shutdown

- stop accepting new risk;
- cancel and await market/account/reconcile/outbox tasks;
- close/stop user stream safely where supported;
- persist final state;
- no detached orphan tasks.

### Restart

- account state begins unreconciled until repaired;
- unfinished intents/orders reconcile before new risk;
- unfinished PositionCase outbox drains;
- duplicate order submission remains impossible.

### Tests

Use FastAPI lifespan/runtime tests proving:

- startup owns expected tasks;
- shutdown cancels/awaits them;
- DRY_RUN startup needs no exchange credentials;
- TESTNET startup fails closed without TESTNET credentials;
- TESTNET account stream/reconcile tasks are actually started;
- runtime restart recovers pending state;
- no LIVE endpoint or credential namespace can be selected;
- default API startup makes zero exchange writes.
