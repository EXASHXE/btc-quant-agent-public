# 3. R3-01 BLOCKER — actual placement-time authorization and account revalidation

## Defect

`submit_authorized(authorization_id, now_ms)` currently relies on caller-provided time captured
before the asynchronous side-effect boundary.

A delayed worker can therefore evaluate receipt TTL using a stale timestamp.

The account receipt is also not backed by a forced fresh account reconciliation immediately before
risk-increasing placement.

## Required repair

### Backend-owned execution clock

Inject/use a backend clock:

`clock_ms() -> int`

For every risk-increasing TESTNET side-effect boundary:

- derive current time inside the backend;
- do not use caller-provided stale time as authority;
- verify authorization is active at actual gate time.

Caller timestamps may remain diagnostic only.

### Fresh placement snapshot

Before any new order placement:

1. obtain a fresh current account snapshot through an explicit execution-time account provider;
2. for TESTNET this provider must perform/await authoritative REST account reconciliation, not only
   return a cached snapshot;
3. verify account/environment/credential authority;
4. re-run current risk validation against that snapshot;
5. bind the placement decision to the resulting snapshot identity.

If the snapshot changes after an older receipt was issued, do not silently reuse the stale receipt.
Either:

- issue a new immutable authorization bound to the fresh snapshot after revalidation; or
- fail closed and require reauthorization.

### Final pre-order gate

Immediately before `place_order()` (after any margin/leverage setup that may consume time):

- use the backend clock again;
- authorization must still be unexpired;
- current execution authorization must still correspond to the fresh account/risk decision;
- kill switch must still permit new risk.

If any condition fails, place zero new orders.

### Cancellation

Preserve the R2 cancellation rule: once an external TESTNET request has actually begun, task
cancellation must not abandon unknown transport state. Complete/query/reconcile and persist before
propagating cancellation.

## Required local tests

- authorize at t0; delay past expiry; submit => zero order calls;
- expiry occurs during pre-order setup => zero order placement;
- account changes between receipt issuance and placement => reauthorize or reject, never reuse;
- forced fresh account reconciliation fails => zero order calls;
- fresh account shows new position/open-order/risk conflict => zero order calls;
- unchanged fresh account + valid receipt => normal mocked TESTNET submit;
- caller passes an old `now_ms` => cannot extend authorization lifetime.

# 5. R3-03 BLOCKER — remaining daily-loss and drawdown headroom

## Defect

Current validator checks whether account caps are already exceeded, then checks trade-level risk.

It must also prove that the proposed new trade's worst-case loss fits inside the *remaining*
account-level budgets.

## Required repair

Use the same conservative worst-case trade loss already used by risk validation, including configured
fees/slippage/funding buffer.

Compute and enforce:

### Daily-loss headroom

```text
daily_cap = policy-defined current daily-loss cap
remaining_daily = max(0, daily_cap - current_daily_loss)
require proposed_worst_case_loss <= remaining_daily
```

### Drawdown headroom

Using authoritative peak equity/current equity and the existing max-drawdown policy:

```text
drawdown_floor_equity = peak_equity * (1 - max_drawdown_pct)
remaining_drawdown_usdt = max(0, current_equity - drawdown_floor_equity)
require proposed_worst_case_loss <= remaining_drawdown_usdt
```

If policy semantics use a stricter equivalent formula, use that consistently and document it.

Do not double-count losses already included in current account equity/daily loss.

The most conservative applicable headroom wins.

### Required tests

- current daily loss just below cap + trade risk exceeding remainder => blocked;
- trade risk exactly at permitted remainder => deterministic boundary behavior;
- current drawdown just below max + trade risk exceeds remaining drawdown => blocked;
- daily headroom passes but drawdown headroom fails => blocked;
- drawdown passes but daily headroom fails => blocked;
- both pass => accepted;
- account peak-equity/current-equity inconsistency => fail closed.

# 7. R3-05 HIGH — reconcile submitted/claimed intents before new-entry gates

## Defect

Reconciliation is not new risk entry.

An intent/order that may already exist at the exchange must be queried and reconciled even when the
original approval/proposal/Tactical state has since expired or become unsuitable for a new entry.

## Required repair

Separate two authorities:

```text
NEW_RISK_PLACEMENT_GATES
vs
EXISTING_SIDE_EFFECT_RECONCILIATION
```

For an intent with a durable claim / SUBMITTING / submitted order identity:

1. verify immutable local intent/authorization/environment identity sufficient to safely identify
   the exchange order;
2. query exchange by canonical clientOrderId first;
3. reconcile order/fill/protection state;
4. apply risk-reducing protection/cleanup as needed;
5. never create a new entry if the new-entry authorization is expired/invalid.

Do not require current proposal TTL/Tactical validity merely to observe an already-submitted order.

If exchange proves the entry order absent, only then may new-entry rules decide whether submission
is still allowed. Expired/invalid authority => no new submit.

### Runtime startup ordering

On startup/restart:

```text
recover claims/submitting intents
-> exchange reconciliation
-> protection reconciliation
-> account state reconciliation
-> only then evaluate whether new risk can be accepted
```

### Required tests

- order already exists + proposal expired => order still reconciled, no duplicate submit;
- submitted order partially filled + approval now stale => fill/protection still reconciled;
- claimed intent + exchange proves absent + authorization expired => no submit;
- active exchange order + kill switch active => reconcile/risk-reduce allowed, no new risk;
- stale local state cannot cause active exchange order to be forgotten;
- startup reconciles existing side effects before any new-entry rejection/acceptance decision.
