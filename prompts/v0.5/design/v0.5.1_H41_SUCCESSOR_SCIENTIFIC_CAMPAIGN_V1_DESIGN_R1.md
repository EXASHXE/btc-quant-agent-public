# 4. Interpretation of H41

H41 is terminal exploratory evidence.

You MAY use published H41 results as **exploratory diagnostic history** to
understand failure modes such as:

- insufficient event/day support;
- excessive familywise uncertainty;
- weak unconditional breakout/trend edge;
- descriptive but unsupported coordinates;
- friction sensitivity;
- modifier sparsity.

You MUST NOT:

- rerun H41 with relaxed thresholds;
- change H41 candidates after seeing outcomes;
- rescue a near-positive H41 candidate;
- promote H41 descriptive means to successor scientific evidence;
- treat H41's best point estimate as a successor winner;
- access H41 WF1_VALIDATION scientific values;
- reuse H41 calibration as if it were fresh confirmatory evidence.

The successor is a **new prospective campaign**, not H41 R2/R3.

# 5. Core design thesis

The successor should test whether directional edge is more likely to exist in
**conditioned market states** than in broad unconditional price-pattern rules.

The design must evaluate, subject to PIT/source feasibility, the following
candidate-family directions:

### Family A — Price + regime conditioned signals

Examples of allowable primitives:

- trend slope / multi-horizon return;
- breakout / failed breakout;
- realized volatility state;
- ATR/range compression-expansion;
- volume regime;
- trend-strength regime;
- precise deterministic candlestick structures only if translated into
  machine-checkable formulas.

Do not create a large pattern zoo.

### Family B — Derivatives-state conditioned signals

Evaluate feasibility of:

- funding level / funding change;
- open interest level / delta / impulse;
- price × OI interaction;
- mark/index basis or premium;
- long/short ratio only if authoritative historical PIT coverage exists.

A desired indicator is not automatically an authorized scientific source.

### Family C — Trade-flow / participation signals

Evaluate feasibility of:

- aggTrade buy/sell imbalance;
- signed volume / CVD-like measures;
- volume impulse;
- aggressive flow confirmation/divergence.

### Family D — Cross-asset state

Evaluate compact BTC/ETH relationships such as:

- BTC lead / ETH response;
- relative strength;
- return divergence/convergence;
- volatility divergence;
- cross-asset confirmation.

### Family E — Microstructure

L2 depth, imbalance, spread, queue/depth features may be proposed **only if**
historical PIT coverage and provenance are scientifically adequate for the
chosen research partitions.

If only forward-era L2 exists, classify this family as a separate future-forward
campaign and exclude it from the historical successor candidate universe.

# 10. Avoid modifier sparsity and pseudo-diversity

H41 demonstrated that some modifiers can produce extremely small event
populations.

The successor design must therefore:

- estimate support feasibility without opening successor protected outcomes;
- reject modifiers whose expected support is structurally too sparse;
- prevent many candidates that are merely small variants of the same signal;
- define a candidate-dependence analysis;
- avoid multiplicity inflation through aliases.

Candidate diversity should represent materially distinct mechanisms, not
parameter-grid expansion.

# 11. Statistical design and multiplicity

Review the H41 single-step joint maximum approach and design the successor
inference prospectively.

Compare at least:

### Option 1
Single-step joint maximum across the reduced candidate universe.

### Option 2
Hierarchical family gatekeeping:
family-level omnibus control followed by predeclared within-family testing.

### Option 3
A valid step-down / Romano-Wolf-style procedure or another rigorously justified
familywise method.

The chosen method must:

- preserve dependence across candidates and shared market clocks;
- control the declared familywise error rate;
- handle sparse / unsupported coordinates explicitly;
- bind block/bootstrap methodology prospectively;
- avoid selecting the inference method after Discovery outcomes;
- distinguish descriptive diagnostics from formal gates.

Provide a reasoned recommendation based on expected power, candidate dependence,
and implementation complexity.

Do not execute successor bootstrap inference in this task.

# 12. Endpoint and trading-friction design

The successor is intended to move toward a usable playbook, so define a more
realistic but still auditable endpoint policy.

Evaluate whether the primary scientific endpoint should include:

- fixed round-trip execution friction;
- maker/taker assumptions;
- slippage stress;
- funding for perpetual positions where horizon makes it relevant;
- mark/open/close semantics.

Requirements:

- one frozen primary endpoint;
- separately labelled stress diagnostics;
- no leverage or position sizing inside the primary directional-edge claim;
- no post-outcome cost-model switching;
- the cost model must be compatible with the eventual tactical playbook.

Reuse B-line engineering utilities only when semantics are independently
revalidated for A-line scientific use.

# 13. Regime design

Regime conditioning is a primary successor thesis, but regime labels can become
a source of hidden overfitting.

Design a small prospective regime taxonomy.

Prefer a few mechanistically interpretable regimes such as:

- volatility low / normal / high;
- trend strength weak / strong;
- liquidity/volume normal / stressed;
- derivatives crowded / neutral if authoritative derivatives data exists.

Requirements:

- regime definitions fit only on designated TRAIN data or fixed economic rules;
- no regime threshold search on DISCOVERY outcomes;
- no dozens of regime combinations;
- no regime created because one H41 candidate happened to look good.

# 14. Model-class decision

Compare three campaign forms:

1. deterministic regime-conditioned playbooks;
2. small regularized statistical model trained only on SUCCESSOR_TRAIN;
3. two-stage design where deterministic events define opportunity and a compact
   model scores/filter events.

For each discuss:

- scientific interpretability;
- PIT risk;
- multiplicity/search complexity;
- data requirements;
- validation burden;
- eventual tactical usability.

Recommend one primary V1 architecture.

Do not introduce a large black-box ML search in V1 unless there is an unusually
strong scientific justification.
