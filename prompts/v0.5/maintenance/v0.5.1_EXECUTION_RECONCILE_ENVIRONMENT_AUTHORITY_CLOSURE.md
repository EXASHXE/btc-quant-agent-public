# 1. Current defect

`ExecutionService.reconcile(plan_id)`:

1. loads a persisted ENTRY plan;
2. loads its persisted entry order;
3. reads **current** `config.execution.mode`;
4. chooses the signed client from current mode;
5. queries/cancels/orders using the persisted symbol/order ID;
6. may place STOP / TAKE_PROFIT protective orders;
7. may issue a reduce-only MARKET failsafe order.

It does not first prove:

```text
persisted plan mode == current mode
persisted plan hash is valid
entry order belongs to same execution environment
current signed client/account matches the environment under which the plan/order was created
live write authority existed for the original live plan
```

Therefore a TESTNET plan can be reconciled under LIVE config.

# 8. Failsafe semantics

Current reconcile exception path can issue:

```text
reduceOnly MARKET
```

Define the exact authority required for this emergency action.

Questions:

1. Must the position be independently verified on the same account/environment?
2. Must quantity be capped to actual current reducible position rather than stale plan quantity?
3. What if position direction changed?
4. What if another system owns the position?
5. What if plan order ID collides with unrelated live order?
6. What if only one protective order was placed before failure?
7. What if the current plan is expired?
8. What audit record is required?
9. Can failsafe ever increase exposure?
10. Must `reduceOnly=true` be independently enforced at request construction and exchange response verification?

The policy must never assume “reduceOnly string present” is sufficient proof of correct account/position ownership.
