# 2. Independently confirmed hot paths

Current code still does all of the following in ordinary `status()`.

## P0-A — full finalized-file hashing

`status()` calls:

```python
partition_integrity_audit()
```

and that method currently executes effectively:

```python
hashlib.sha256(path.read_bytes()).hexdigest()
```

for every finalized SQLite partition.

Consequences:
- all immutable history is reread every 15 minutes;
- CPU and disk I/O scale with total historical bytes;
- `read_bytes()` can temporarily allocate the size of an entire SQLite file.

This is a P0 repair target.

## P0-B — active `PRAGMA quick_check` on each cache miss

The active partition changes continuously, therefore mtime/size change continuously.

Its cache entry is normally invalid every health cycle.

Current cache-miss scan executes:

```sql
PRAGMA quick_check
```

on the active database.

This is reported to cost ~36 seconds.

This is a P0 repair target.

## P0-C — full-history bucket materialization

Current status builds:

```python
bucket_candidates: set[tuple[int, int]]
```

for all history and all:

```text
1s
60s
900s
```

intervals.

With ~24 days of history, the 1-second series alone is >2 million Python bucket objects.

This causes both:
- O(history_seconds) CPU every health check;
- very large transient Python heap/RSS.

This is a P0 repair target.

## P1 — raw `gap_rows` cache expansion

Cache-v2 persists every:

```text
(start_ms, end_ms, kind)
```

row.

Production observation:

```text
113,448 raw rows
but only ~14 merged non-overlapping time intervals
```

However raw rows are currently used not only by `_fast_has_gap` and `Counter(kind)`, but also by:

```text
status["gap_count"]
rolling_reliability["24h"]["gap_count"]
rolling_reliability["7d"]["gap_count"]
```

Therefore direct replacement with only merged intervals + type counts is NOT semantic-equivalent unless the raw-row counting outputs are preserved separately.

# 4. Cache schema v3 — compressed gap representation

Upgrade the stats cache schema:

```text
2.0.0 -> 3.0.0
```

Legacy v2 may be discarded and rebuilt.

For each partition, do NOT serialize raw `gap_rows`.

Cache at least:

```json
{
  "gap_count": 113448,
  "gap_type_counts": {
    "DEPTH_SEQUENCE_GAP": 0
  },
  "gap_merged_intervals": [
    [start_ms, end_ms]
  ],
  "gap_min_start_ms": null,
  "gap_max_end_ms": null
}
```

Names may differ, but exact semantics must match.

## 4.1 Merged interval construction

Build the interval union by streaming / iterating gap rows ordered by start/end.

Do not first materialize 100k+ Python 3-tuples solely to merge them.

The union of cached per-partition merged intervals may be re-merged globally.

Unioning already-unioned partition intervals must yield exactly the same overlap semantics as unioning every raw gap row.

## 4.2 Total/type counts

Use exact scalar aggregation:

```text
gap_count
gap_type_counts
```

so:

```text
status["gap_count"]
status["gap_type_counts"]
resync_count
```

remain exact without reconstructing raw rows.

## 4.3 Exact rolling 24h / 7d raw gap counts

Do NOT redefine rolling `gap_count` as merged-interval count.

It currently counts raw gap records overlapping the rolling window.

Preserve:

```text
start_ms < now
AND
end_ms >= window_start
```

exactly.

Recommended bounded strategy:

- finalized partition fully inside rolling window:
  use cached `gap_count`;
- finalized partition wholly outside the window and unable to spill into it:
  contribute zero;
- the single boundary partition containing `window_start`:
  perform an exact bounded SQLite count query, or use an exact compact index;
- current active partition:
  compute exact rolling counts directly during the active scan / bounded SQL;
- gap rows that start in an earlier partition but cross a UTC partition boundary:
  preserve enough compact spill metadata or exact fallback querying to count them correctly.

Ordinary status must never reconstruct the global 113k-row list.

Cross-midnight and long-gap behavior needs adversarial tests.

## 4.4 Cache-size target

Using a synthetic fixture representative of:

```text
>=100,000 gap rows
<=20 merged intervals
small number of kinds
```

require the gap-related serialized cache payload to be dramatically smaller than raw row storage.

Target:

```text
< 200 KiB for gap-derived cache state
```

unless an exact-semantics requirement proves this impossible.

If exact rolling-count support requires a larger representation, STOP and report the measured lower bound instead of silently weakening semantics.

# 6. Move deep SQLite integrity check to correct boundaries

A full/deep check remains available.

## 6.1 Finalization

Before a partition becomes immutable and before its manifest SHA becomes authoritative:

1. ensure no open session prevents finalization;
2. checkpoint WAL successfully;
3. execute:
   ```sql
   PRAGMA quick_check
   ```
4. require result exactly `ok`;
5. only then hash/seal the finalized SQLite file;
6. refuse finalization on failure.

Order may be adjusted only if SQLite correctness requires it, but the immutable manifest must never accept a partition that has not passed quick_check at finalization.

## 6.2 Explicit audit

`quantctl microstructure-forward audit` must retain a deep/force mode capable of:
- active partition quick_check;
- full finalized-file checksum verification.

Ordinary 15-minute health must use the lightweight path.

If necessary introduce:

```python
status(..., deep_integrity=False)
partition_integrity_audit(force_full=False)
```

and call deep mode only from the explicit audit command.

# 7. Persistent finalized checksum attestation cache

Ordinary status must not reread every finalized SQLite file.

For every finalized partition, persist a verified fingerprint bound to the manifest SHA.

Recommended fingerprint:

```text
st_dev
st_ino
st_size
st_mtime_ns
st_ctime_ns
manifest_sha256
```

A cached finalized attestation is reusable only when:
- manifest SHA is unchanged;
- current stat fingerprint exactly matches the fingerprint that was fully hashed.

If no proof exists or fingerprint changed:
- compute file SHA once;
- use a streaming hash, NOT `Path.read_bytes()`;
- compare to manifest SHA;
- persist refreshed proof.

If fingerprint is unchanged:
- reuse the previously verified manifest comparison;
- zero finalized SQLite data bytes should be read.

Explicit `force_full=True` audit always rehashes every finalized partition.

This cache is operational optimization evidence, not scientific authority.

## 7.1 Streaming hashing

Do not use:

```python
path.read_bytes()
```

for multi-GB SQLite hashes.

Use bounded chunk streaming, e.g. 1-8 MiB chunks.

Avoid broad unrelated changes to `publication.file_digest` unless all repository callers are proven compatible.

A local streaming helper is acceptable.
