# Required closure domains

## 1. Define one canonical lifecycle-governance authority

Freeze:

- schema/version identifier;
- parent authority references;
- exact canonical JSON rules (reuse repository `canonical_json` / `canonical_sha256`);
- exact child evidence identities;
- whether order is semantic;
- exact lifecycle-governance root/hash preimage;
- domain separation from the scientific protocol/semantic/ledger roots.

The lifecycle authority must bind, directly or transitively, the already-accepted:

- protocol authority hash;
- semantic root hash;
- structural ledger hash;
- P2 final acceptance evidence.

Do not use caller-provided arbitrary hashes as authority.

## 2. Define typed evidence receipts

Freeze canonical receipt schemas and content hashes for each lifecycle transition that can authorize forward research progression.

At minimum address:

```text
H40_P1_SCAFFOLDED
  -> H40_DISCOVERY

H40_DISCOVERY
  -> H40_CANDIDATE_LOCKED

H40_CANDIDATE_LOCKED
  -> H40_WALK_FORWARD_VALIDATED

H40_WALK_FORWARD_VALIDATED
  -> H40_CONFIRMATION_READY
```

The protocol must state exactly which evidence receipt(s) authorize each transition.

A bare boolean, caller string, state enum, path existence check, or unverified hash is never sufficient authority.

For every receipt freeze:

- schema id/version;
- exact required fields;
- exact field ordering semantics where relevant;
- canonical hash preimage;
- upstream receipt/authority references;
- code/artifact identity binding where required;
- persistence requirement;
- replay/idempotence behavior;
- mismatch/staleness/fail-closed behavior;
- whether the receipt is immutable after creation.

## 3. Discovery-entry evidence

The `H40_P1_SCAFFOLDED -> H40_DISCOVERY` transition must require a deterministic pre-outcome discovery authorization receipt.

Freeze exactly how it binds at least:

- accepted scientific authority identities;
- exact structural ledger;
- accepted P2 implementation/final acceptance;
- exact split authority;
- exact runtime authority snapshot;
- materialized-run authority identity;
- code implementation identity to be executed;
- execution-disabled invariant.

Define exactly when the runtime authority snapshot becomes sealed relative to the first H40 label/outcome. Preserve the accepted rule that no post-seal source promotion can change the discovery candidate universe.

No discovery outcome may be needed to create this receipt.

## 4. Candidate-lock transition evidence

The `H40_DISCOVERY -> H40_CANDIDATE_LOCKED` transition must be impossible from state alone.

Freeze exact evidence required for the single candidate lock, including canonical binding to:

- discovery authorization/run authority;
- sealed discovery universe;
- exact winning structural configuration identity;
- exact candidate-selection contract identity;
- discovery result/selection receipt identity;
- no-runner-up / no-promotion rule.

Do not expose or compute actual discovery results in this task.

## 5. Walk-forward validation transition evidence

The `H40_CANDIDATE_LOCKED -> H40_WALK_FORWARD_VALIDATED` transition must bind to the locked candidate and exact accepted WF partition/split authority.

Freeze the validation receipt identity and its causal lineage so that a receipt from another candidate, split, protocol, ledger, or run cannot authorize the transition.

Do not run validation.

## 6. Confirmation-ready transition boundary

The `H40_WALK_FORWARD_VALIDATED -> H40_CONFIRMATION_READY` transition may be specified as evidence-bound, but this task must preserve the separate blocker:

```text
H40-FSA-F02 — confirmation nonce / one-shot persisted authority
```

Therefore:

- `CONFIRMATION_READY` must not itself reveal or authorize confirmation outcomes;
- `H40_CONFIRMATION_READY -> H40_CONFIRMATION_EVALUATED_ONCE` remains unauthorized until F02 is separately closed, accepted, and implemented;
- no confirmation nonce design should be silently invented as part of F01 unless merely reserving a future field/authority boundary with no unlock capability.

## 7. Failure / terminal-state semantics

Define deterministic evidence expectations for fail-closed transitions to:

```text
H40_NO_GO
NOT_TESTABLE
```

At minimum ensure a caller cannot use terminal-state transitions to forge successful upstream evidence or bypass protected gates.

Use the existing H40 reason-code vocabulary where possible. If the protocol truly requires a new lifecycle-specific reason code, it must be explicitly frozen in this amendment and justified; do not proliferate codes casually.

## 8. Persistence and replay

Freeze:

- where authority is logical vs persisted evidence;
- exactly-once or idempotent semantics;
- duplicate receipt handling;
- receipt replacement prohibition;
- parent/child lineage verification;
- stale receipt rejection;
- cross-run/cross-candidate replay rejection;
- canonical receipt serialization;
- verification from content rather than filenames.

No mutable in-memory-only boolean may serve as durable authority.

## 9. Adversarial acceptance criteria for later implementation

The amendment must define implementation tests proving at minimum:

1. adjacency alone cannot enter Discovery;
2. forged protocol/ledger/snapshot hashes cannot authorize Discovery;
3. P2 acceptance from a different commit/run cannot authorize Discovery;
4. runtime source-state mutation changes run authority but not structural ledger identity;
5. post-seal source promotion cannot unlock candidates;
6. candidate-lock receipt from another run/config cannot authorize lock;
7. validation receipt from another candidate/split cannot authorize WF validated;
8. confirmation-ready does not expose confirmation outcomes;
9. caller boolean/string/path cannot replace typed evidence;
10. receipt mutation changes its hash and invalidates descendants;
11. stale/replayed cross-run evidence fails closed;
12. scientific P2 hashes remain byte-for-byte unchanged by lifecycle authority.

These are synthetic/governance tests only when implemented later.
