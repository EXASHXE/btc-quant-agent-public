# v0.5.0 R03A — Contract & Data-Model Inventory (Gemini-Optimized, Read-Only)

## Mission

Perform a **read-only structural audit** of `EXASHXE/btc-quant-agent` after accepted R02/R02R. The goal is to prepare a precise, low-risk R03 simplification plan for contracts, identities, envelopes, replay inputs, benchmark metadata, qualification payloads, serialization and compatibility adapters.

This round MUST NOT modify production code, tests, configs, semantic goldens, evidence, H39 state, holdout state, or CI. It is inventory + dependency analysis + proposed cuts only.

The main question is:

> Which layers are genuinely independent authority boundaries, and which layers are now redundant wrappers/serialization/compatibility complexity that can be simplified without reopening B01–B12/B13 defects?

Do not optimize for fewer classes or fewer fields by itself. Optimize for fewer duplicated representations of the same fact while preserving authority separation and fail-closed replay/qualification semantics.

# 2. Start from authority, not filenames

Build an authority map from the accepted formal research path downward.

Trace at least:

```text
formal job/spec
  -> protocol / research contract
  -> dataset/evidence identity
  -> decision/signal input provenance
  -> replay input bundle/context
  -> formal run identity / role
  -> canonical execution/accounting replay
  -> candidate result envelope
  -> RANDOM benchmark reconstruction
  -> CASH benchmark reconstruction
  -> comparison/qualification input
  -> qualification decision
  -> registry / persisted decision / promotion state
```

For every edge identify:

- producer;
- consumer;
- authoritative fields;
- derived fields;
- hashes/identities;
- persisted representation;
- replay reconstruction source;
- fail-closed checks;
- legacy/compatibility adapters;
- tests that defend the edge.

Do not infer ownership from class names. Follow actual call sites and accepted tests.

# 8. Target architecture proposal

Propose the smallest credible target model for R03/R04.

The target should preserve explicit separation between:

```text
1. Research protocol + dataset/input provenance
2. Replay authority inputs
3. Canonical execution/accounting result
4. Independently reconstructed benchmarks
5. Qualification/comparison decision
6. Registry/promotion persistence
```

Within those boundaries, identify wrappers/types/adapters that can plausibly disappear.

Prefer:

- one canonical representation per authoritative fact within one ownership layer;
- explicit transformations between ownership layers;
- independent replay/reconstruction rather than trusting submitted outputs;
- small typed objects over generic dict buses;
- explicit versioning only where persisted compatibility actually requires it.

Do NOT propose a generic event bus, dependency-injection container, plugin framework, ORM migration framework, universal envelope, or other new abstraction unless the audit proves it removes more active complexity than it adds. Default assumption: do not add one.

# 9. Future research compatibility constraint

The next research program is expected to investigate low-frequency BTC/ETH perpetual directional opportunities, likely with:

```text
decision cadence around 1h
candidate primary horizons around 4h / 8h / 12h
24h as supporting horizon
LONG / SHORT / NO_TRADE output
microstructure used as optional entry confirmation rather than sole medium-horizon direction authority
```

These are research hypotheses, NOT frozen architecture parameters.

R03 simplification must therefore avoid hard-coding one asset, one horizon or H39-specific semantics into generic formal contracts unless the current accepted authority already requires it.

Audit whether current contracts can represent:

- BTC and ETH independently;
- multiple candidate horizons without identity ambiguity;
- explicit abstention / NO_TRADE;
- optional feature-family provenance (trend/regime/derivatives/microstructure);
- leveraged perpetual cost/funding assumptions through the existing economic authority.

Report gaps, but DO NOT implement the future research model in R03A.

# 10. Required attack-oriented review of every proposed cut

For every proposed R03 simplification answer:

1. Can an attacker now substitute candidate bytes and rehash all outer wrappers?
2. Can CANDIDATE be relabeled as RANDOM_BENCHMARK or vice versa?
3. Can a producer contract be selected by the candidate instead of the protocol?
4. Can replay use submitted price/qty/fee/funding/PnL instead of reconstructing them?
5. Can benchmark outputs be submitted rather than independently reconstructed?
6. Can a legacy schema/object become promotable merely because an adapter reads it?
7. Can a missing identity/version silently default?
8. Can a new multi-asset or multi-horizon candidate collide with another identity?

If the answer is uncertain, classify the proposed cut `SEMANTIC_CUT_REQUIRES_SOL` or `DEFER_UNKNOWN`.
