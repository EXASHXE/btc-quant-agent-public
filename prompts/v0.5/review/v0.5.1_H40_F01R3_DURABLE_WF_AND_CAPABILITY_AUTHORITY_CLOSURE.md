# 5. Finding B-03 — verified-capability lifetime

Current in-memory descendant authorization can outlive active source validity.

Cold restore is stricter than cached reuse.

This semantic gap must close.

## Evaluate two models

### Model A — reverify source truth at every transition use

Every production:

```text
authorize_candidate_lock
authorize_wf_validation
authorize_confirmation_ready
authorize_termination where relevant
revalidate_authorization
state-machine consumption
```

must ultimately prove the root runtime seal/source authority is currently valid.

Advantages:

- simple evidence-truth semantics;
- source disappearance/mutation fails closed.

Costs:

- repeated cold I/O;
- long-running transitions depend on source availability.

### Model B — independently protected immutable run input snapshot

At run seal, active source bytes/timestamp evidence are copied or content-addressed into an immutable protected evidence store.

Later lifecycle transitions verify that immutable snapshot identity rather than the mutable original path.

Advantages:

- stable replay even if original source path changes.

Costs:

- storage/copy semantics;
- immutable store becomes a major authority surface;
- must be protected from mutation/deletion/substitution.

## Required decision

Choose one model or a rigorously specified hybrid.

Do not leave lifetime implicit.

For the selected model define:

```text
when source truth is checked
what object is sufficient authority later
what invalidates cached authorization
what happens if source disappears
what happens if source is modified
what happens if runtime source state changes
what restoration verifies
what an in-memory transition verifies
```

The same semantics must apply to cached and cold-restored authority.
