# 4. AS-01 — atomic replace / rename bypass

## 4.1 Problem

The current guard wraps ordinary file operations but does not comprehensively protect atomic move/replacement APIs.

A malicious or accidental test can potentially create a temporary file outside a forbidden root and then atomically move it into a protected destination without the destination being checked.

Example attack shape:

```python
src = tmp_path / "safe.tmp"
src.write_text("overwrite")

os.replace(src, REPOSITORY_ROOT / "var/quant.db")
```

or equivalent `rename` / `Path.replace` / `Path.rename` variants.

The guard must reject the operation **before any filesystem mutation occurs**.

## 4.2 Required APIs

At minimum inspect and guard the path-mutating APIs actually reachable in Python stdlib usage for this repository:

```text
os.replace(src, dst)
os.rename(src, dst)
Path.replace(target)
Path.rename(target)
```

If the implementation discovers another directly equivalent stdlib atomic-move primitive used by this codebase/tests, include it only if narrowly justified.

Do not attempt to intercept arbitrary syscalls or create a complete security sandbox.

## 4.3 Required source + destination semantics

For rename/replace operations, **both source and destination must be checked**.

Why:

- protected destination: prevents writing/replacing a real operational store;
- protected source: prevents moving/removing a real operational store to an unprotected location.

Therefore these must fail before mutation:

```text
safe source     -> forbidden destination
forbidden source -> safe destination
forbidden source -> forbidden destination
```

The following should remain permitted:

```text
tmp source -> tmp destination
```

The guard should surface the existing sentinel exception (`ForbiddenTestAccess`) or an equally fail-loud project-local guard exception.

Prefer error text that identifies whether the blocked path was the source or destination when practical.

## 4.4 Symlink / canonicalization requirement

The existing guard resolves paths. Preserve that invariant.

A symlink alias to a forbidden source or destination must not bypass rename/replace checks.

Required adversarial examples include at least one resolved-path alias.

## 4.5 No partial mutation

Tests must verify that after a blocked operation:

- original protected sentinel bytes remain unchanged;
- protected source still exists when movement from it was blocked;
- safe source still exists when movement into a protected destination was blocked;
- no destination file was created/replaced.

Do not only assert that an exception was raised.

# 5. AS-02 — SQLite `file://localhost/...` URI bypass

## 5.1 Problem

The current `_sqlite_candidate()` handling primarily strips the `file:` prefix and query string. URI forms with an authority component, especially:

```text
file://localhost/absolute/path/to/file.db
```

can be interpreted incorrectly and therefore avoid comparison with the canonical forbidden path.

The path presented to the guard must match SQLite/Python URI semantics closely enough that equivalent local-file URI spellings resolve to the same protected path.

## 5.2 Required supported URI forms

At minimum test and correctly handle:

```text
plain path:
/path/to/file.db

relative file URI form used by sqlite:
file:relative.db

absolute URI:
file:///absolute/path/to/file.db

localhost authority:
file://localhost/absolute/path/to/file.db

percent-encoded absolute path:
file:///tmp/some%20dir/file.db

URI with query parameters:
file:///absolute/path/to/file.db?mode=ro
file://localhost/absolute/path/to/file.db?mode=rw
file:///absolute/path/to/file.db?immutable=1
```

The query parameters themselves are not the security identity; the underlying local filesystem path is.

Percent decoding must happen correctly before canonical path checking.

## 5.3 Authority handling

For this task, local SQLite file URIs with:

```text
host == ""
host == "localhost"
```

must resolve to the local filesystem path and therefore be subject to the same forbidden-path checks as the equivalent plain path.

Do not invent unsafe behavior for arbitrary non-local authorities. If Python/SQLite behavior for a non-local host is platform-dependent or unsupported, fail closed or leave it to SQLite only if it cannot weaken the protected-local-path boundary. Document the choice.

The critical acceptance requirement is that `file://localhost/...` cannot bypass the guard.

## 5.4 URI flag handling

`sqlite3.connect(..., uri=True)` is the main required URI path.

Also inspect actual Python behavior in this codebase so that a string beginning with `file:` is not accidentally treated inconsistently merely because the caller omits `uri=True`.

Do not overfit to one test literal; implement a small, explicit URI-to-local-path parser using stdlib primitives such as `urllib.parse.urlsplit` / `unquote` if appropriate.

Avoid ad-hoc string slicing that reproduces the current bug.

### SQLITE-02 — `file:///...` blocked

# 9. Scope discipline

This is **not** an invitation to redesign the pytest architecture.

Prefer a small extension of the existing guard.

A reasonable implementation shape is:

```python
def check_two_path_operation(src, dst, operation):
    check_path(src, f"{operation}:source")
    check_path(dst, f"{operation}:destination")
```

and a robust helper conceptually like:

```python
def sqlite_candidate(database):
    if not a file URI:
        return database
    parse URI with stdlib
    map empty/localhost authority to local path
    percent-decode path
    preserve :memory:
    return filesystem candidate
```

This is illustrative, not mandatory API design.

Do not make a large abstraction framework for a two-finding repair.
