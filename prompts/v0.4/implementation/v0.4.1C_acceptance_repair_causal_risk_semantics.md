## 2. Acceptance blockers to fix

### AR1 — Missing spread must not silently become zero

Current behavior in `economic/simulator.py`:

```python
spread_bps = float(sig.metadata.get("spread_bps", 0.0))
```

This makes missing spread look like a perfect 0 bps market and contradicts P4's fail-closed contract.

Required contract:

- If a spread constraint is binding (`max_spread_bps` is being enforced), spread evidence must be explicitly available at or before the decision timestamp.
- Missing / non-finite / negative spread must reject the entry.
- Do not invent `0.0`.
- If the project wants to support a policy with spread filtering disabled, represent that explicitly in the policy contract instead of using missing data as zero.

Add deterministic regressions for missing spread, NaN/inf, negative spread, valid under-cap spread, and over-cap spread.

### AR2 — Do not use current-bar completed volume at bar open

Current P4 code processes signals at `bar.open_time_ms`, but may source market-state volume from the same candle's completed `bar.quote_volume` / `bar.volume`. In historical candles those are whole-bar values and are not causally known at the open.

Required contract:

- Market-state inputs used for an entry decision must have explicit availability no later than the decision timestamp.
- For a signal processed at bar open, do not use the current bar's final quote volume / final base volume.
- Minimal acceptable implementation: require causal volume evidence from signal metadata with explicit availability, or use a previously closed bar / separately supplied already-observed market-state object.
- If required volume evidence is unavailable, fail closed.
- Never infer current-bar full volume from future OHLCV.

Add a regression where changing only the future remainder of the current candle's final volume must not change an entry decision made at its open.

### AR3 — Risk admission must not inspect future fill results

Current code calls `ExecutionModel.simulate_order(...)`, obtains the future `exec_res.fill_price/fill_timestamp_ms`, then uses the actual future fill notional to decide whether the order is accepted. Pending risk reservation also uses already-known future fill prices.

This leaks future execution information into the order-time risk decision.

Required contract:

- Order admission / reservation must use only information available at order time plus predeclared execution/risk bounds.
- Do not use future `fill_price`, `fill_timestamp_ms`, future candle values, or any derived future fill outcome to decide whether the order was submitted/accepted.
- Pending reservations must store an **ex-ante reservation notional/price** derived from order-time observable inputs and explicit deterministic bounds, not the eventual realized fill price.
- LIMIT orders may use their actual limit cap as an ex-ante bound when valid.
- MARKET orders may use an explicit declared worst-case slippage bound if the configured execution model exposes one. If no finite ex-ante bound exists, the combination must fail closed for strict gross-cap enforcement; do not peek at the realized fill.

Add paired tests where two future price paths differ after order submission but order-time risk admission is identical when all order-time inputs are identical.

### AR4 — Never erase an already-accepted fill because risk changed later

Current `_apply_pending_fill()` can return `False` and silently drop a pending open fill if drawdown halt / max-open / gross checks fail at fill time. Current post-fill gross logic can also make a future fill disappear.

This is not valid event semantics: once an order has been accepted and a fill occurs, the fill cannot be retroactively deleted unless an explicit cancel/reject event occurred before the fill.

Required contract:

- Drawdown halt blocks **new order submissions after the halt**, not already accepted market fills.
- A pending fill that actually occurs must be booked into the ledger unless there is an explicit causal cancellation/rejection event before fill.
- Do not silently drop accepted pending fills.
- Do not add a full cancel-order engine in this repair. If explicit cancellation is not modeled, accepted pending orders remain committed.
- Risk reservation at admission must be strong enough that a predictable hard cap is not violated by a supported bounded fill model.
- If an unsupported/unbounded fill model cannot guarantee the hard cap ex ante, fail closed before submission.

Add regressions for:

1. order accepted before a later drawdown halt -> scheduled fill still books;
2. order submitted under cap -> later state change does not erase the fill;
3. unsupported unbounded-market-fill scenario -> rejected before submission, not after future fill inspection.

### AR5 — `ambiguous_exit_handling` is declared but not enforced

`ExitRule.ambiguous_exit_handling` accepts:

- `CONSERVATIVE_STOP_FIRST`
- `REJECT_AMBIGUOUS`

But simulator logic always uses stop-first whenever both SL and TP are touched.

Required contract:

- `CONSERVATIVE_STOP_FIRST`: retain explicitly conservative stop-first semantics.
- `REJECT_AMBIGUOUS`: do not fabricate an exit path. Fail closed with an explicit deterministic exception/result that makes this simulation not eligible as a completed economic result.
- Do not silently map `REJECT_AMBIGUOUS` back to stop-first.

Add LONG and SHORT collision regressions for both modes.

### AR6 — Close inherited P3 gap: every economic exit must use one execution path

The P2/P3 repair report stated that exits are unified through execution semantics, but current simulator still directly calls `Portfolio.apply_trade()` for multiple exit paths (reversal, SL/TP/trailing/max-hold/gap) and manually calculates exit prices/fees.

That bypasses `ExecutionModel` and can bypass slippage, latency, maker/taker classification, fill proof, and consistent event timing.

Required invariant:

```text
exit trigger/decision
    -> exit order
    -> ExecutionModel / single execution adapter
    -> confirmed ExecutionResult
    -> Portfolio.apply_trade
```

`Portfolio.apply_trade()` must remain the ledger commit step, not an execution simulator.

Minimal conservative exit contract for OHLC replay:

- If an intrabar SL/TP/trailing trigger is only knowable once the bar is complete, the trigger becomes actionable no earlier than the bar close; submit the configured conservative exit order then and let the execution model determine a causal fill at/after that time.
- A gap stop known at bar open may create an exit decision at that open, then use the same execution path.
- Reversal exits and max-holding exits also use the same execution adapter.
- Do not fill at an ideal theoretical stop/target price merely because an OHLC extreme crossed it.
- Do not create a full exchange/order-book simulator. Prefer conservative/NOT_TESTABLE behavior when evidence is insufficient.

All exit events must preserve observation/decision/order/fill/settlement monotonicity and use actual execution fees/slippage exactly once.

Add tests proving that changing configured slippage/latency affects exits through the same path, and that no exit `TradeEvent` exists without a confirmed execution result.
