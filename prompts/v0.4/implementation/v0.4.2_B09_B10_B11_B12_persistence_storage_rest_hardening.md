# PART A — B09 Durable JSON Publication

## 3. Objective

Replace non-durable JSON publication patterns for active authoritative/operational artifacts with one canonical same-directory durable publisher.

Required semantics:

```text
serialize canonical bytes
-> write temp file in same directory
-> flush
-> fsync(temp file)
-> atomic os.replace(temp, target)
-> fsync(parent directory)
```

A failed publication must preserve the previously committed target file byte-for-byte. Temporary files must not be mistaken for committed artifacts.

Do not claim this primitive makes SQLite/WAL transactions atomic; B09 is file publication only.

Prefer extracting/reusing the strongest existing atomic writer rather than adding a parallel utility.

### Mandatory B09 attacks

- failure before temp flush -> previous committed target unchanged
- failure after temp fsync but before replace -> previous target unchanged
- failure after replace but before directory fsync -> explicit failure surface; no silent success claim
- concurrent publication attempt without valid ownership/CAS -> fail closed or deterministic owner policy
- no truncated JSON accepted as committed
- serialized bytes/schema of successful existing artifacts unchanged unless a versioned migration is explicitly required

Migrate only active callers needed by the current kernel/registry/manifest/export paths. Do not sweep unrelated archived code.

# PART B — B10 Store Finalization / Writer Ownership

## 4. Objective

Make finalization and mutation ownership explicit for active stores so two writers or a stale writer cannot both believe they successfully finalized the same generation/campaign/artifact.

Use existing generation/CAS/epoch/campaign identities where available. Do not invent a new distributed consensus layer.

Required invariants:

- exactly one successful owner for a finalization transition;
- stale generation / stale manifest / stale writer fails before mutation;
- retry after a committed success is idempotent or explicitly rejected without duplicating state;
- crash before commit leaves the previous committed state authoritative;
- crash after commit cannot cause a second logical finalization;
- registry/event-chain history is append-only; never clear or rewrite consumed state;
- B09 durable publisher is used where JSON publication is the finalization surface.

### Mandatory B10 attacks

- two writers start from same generation; only one can commit
- stale writer after another writer commits -> reject
- retry same finalization -> no duplicate event/output
- injected crash before publication/commit -> old state remains authoritative
- injected crash after authoritative commit -> reopening store shows one committed result
- failure path leaves generation/event chain/manifest internally consistent

Keep scope to active stores needed by the repaired kernel and diagnostics. Do not refactor archived research runners.

# PART C — B11 Explicit SQLite Columns / Compatibility

## 5. Objective

Remove active SQLite logic that depends on implicit positional `SELECT *`, unstable column ordering, or silent old/new schema coercion.

Required semantics:

- active reads use explicit named columns in a declared canonical order;
- active writes name columns explicitly;
- row decoders verify expected schema/version where necessary;
- supported historical schema is read through explicit compatibility adapters;
- unsupported/missing/ambiguous columns fail closed instead of being silently promoted;
- migrations are monotonic and never rewrite sealed research outcomes merely to fit a new reader;
- WAL/database integrity semantics remain separate from B09 JSON durability.

### Mandatory B11 attacks

- database with reordered physical columns -> active reader still correct
- extra unknown column -> either safely ignored by explicit projection or rejected by explicit schema policy; no positional corruption
- required column missing -> fail closed
- legacy supported schema -> explicit compatibility path succeeds
- unsupported legacy schema -> NOT_TESTABLE / explicit schema error
- partial migration / version marker disagreement -> reject
- SQLite URI/path tricks must not bypass existing hermetic test guards

Do not introduce an ORM.

# PART D — B12 Coordinated Bounded REST Requester

## 6. Objective

Consolidate active REST request behavior into one bounded requester with explicit timeout/retry/backoff/rate-limit semantics and clock-aware freshness handling.

Reuse the existing HTTP/client stack. Do not add another networking framework.

Required properties:

- explicit connect/read/overall timeout or equivalent bounded request deadline;
- bounded retry count;
- retry only retryable conditions (e.g. selected 429/5xx/network transient classes), never all exceptions blindly;
- exponential or declared bounded backoff with maximum cap;
- honor `Retry-After` when valid, subject to the configured maximum wait budget;
- no retry for deterministic 4xx/config/auth/schema errors unless explicitly justified;
- shared coordination/rate-limit state where callers currently compete for the same exchange REST budget;
- B08 clock domains preserved: UTC event/receipt/availability timestamps are not replaced by monotonic elapsed-time clocks; monotonic time is used only for elapsed timeout/backoff accounting;
- cancellation/shutdown exits promptly; no unbounded sleep loop;
- execution remains disabled and tests must not call the public exchange.

### Mandatory B12 attacks

- repeated 500 -> stops at retry budget
- 429 + valid Retry-After -> bounded wait then retry
- absurd/malformed Retry-After -> cap/reject safely, never unbounded sleep
- deterministic 400/401/403 -> no retry storm
- network timeout -> bounded retries then explicit error
- NTP/wall-clock rollback -> elapsed retry budget remains monotonic
- concurrent callers -> coordinated limiter/backoff rather than independent retry amplification
- cancellation during backoff -> prompt termination
- typo/missing requester config -> fail closed; no silent unsafe defaults

All tests must use synthetic/mocked transport only.
