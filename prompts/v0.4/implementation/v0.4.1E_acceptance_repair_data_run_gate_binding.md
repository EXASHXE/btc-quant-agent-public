## 1. Acceptance blockers to close

### B1 — In-memory candles are not cryptographically bound to dataset evidence

Current runtime validation checks the dataset `EvidenceReference` hash, observation count, start/end times and a single candle symbol, but it does not prove that the `candles` sequence supplied to `execute_bound_run()` is the exact content represented by `dataset_content_sha256`.

Therefore a caller can potentially keep the same evidence id/hash while substituting different OHLCV values with the same count and boundaries.

#### Required contract

Introduce one explicit, canonical, versioned binding from runtime candle payload to the declared dataset evidence/input contract.

Preferred approaches, in order:

1. If the dataset evidence format used by formal P6 is canonical and parseable, load the local evidence and reconstruct/compare the exact canonical candle payload used by the engine; or
2. bind a canonical `runtime_market_data_sha256` / candle payload hash into the preregistered data interval/input identity, and require it to equal a hash computed from the exact runtime candle sequence.

Whichever design is chosen:

- document the canonical candle fields and ordering;
- include symbol, interval, open/close timestamps, OHLC, base volume and quote volume when those fields can affect execution or filters;
- never silently omit a field that can affect economic results;
- no audit timestamp may enter the semantic hash;
- changing any runtime candle economic input must invalidate the binding before simulation/qualification;
- do not weaken existing dataset evidence hash verification.

A content hash of an unrelated file plus a matching row count is not sufficient.

### B2 — Product scope must equal the runtime instrument

Current formal runtime validation enforces one candle instrument but does not explicitly require that instrument to equal the sole preregistered `protocol.product_scope` / `comparison.product_scope` entry.

#### Required contract

For formal P6:

```text
len(product_scope) == 1
runtime candle symbol == product_scope[0]
benchmark vehicle/product semantics are compatible with that same product
```

At minimum, a BTCUSDT protocol supplied with ETHUSDT candles must fail before simulation.

Do not infer compatibility from string coincidence after execution.

### B3 — `EconomicRunResult` must not be forgeable from self-consistent summary fields

`EconomicRunResult.__post_init__()` currently canonicalizes content but does not prove that accounting was generated by a ledger replay. The registry's independent `validate_accounting()` checks selected arithmetic identities but does not reconstruct all formal metrics from immutable trade events.

A caller must not be able to copy a legitimate `EconomicRunIdentity`, fabricate internally consistent `final_equity / realized_pnl / net_return` fields, persist that artifact, and obtain formal qualification.

#### Required contract

Create a single reusable formal run verifier (location is your design choice, but avoid research_contract importing the full economic implementation if that breaks the dependency boundary) that proves, from the persisted run artifact:

- trade events are present and reconstructable;
- ledger event ids exactly match the trade events;
- `Portfolio.from_events(initial_cash, trade_events)` reproduces final cash/position state;
- realized PnL, fees, funding and terminal unrealized PnL reconcile;
- final equity and net return reconcile;
- terminal notional and terminal policy reconcile;
- round trips can be recomputed and match persisted attribution;
- win/loss/flat counts, net wins/losses and profit factor representation match recomputation;
- fill count, turnover and other qualification-relevant metrics are not arbitrary caller fields;
- equity-curve terminal value and declared interval are consistent;
- metrics contract identity/cadence-dependent metrics are validated when used formally.

Avoid two drifting implementations of accounting semantics. Prefer extracting a dependency-safe verifier/contract that can be called both by economic code and registry validation, or verify through a narrow serialized-ledger contract.

If some metric cannot be independently reconstructed from persisted evidence, it must not be eligible as a formal qualification gate without the additional required evidence.

### B4 — Registry must independently recompute qualification gates

The registry currently checks that gate ids/metrics/operators/hurdles match preregistration and checks boolean `passed`, but it must not trust caller-provided `observed_value`, `testable`, or `passed` fields.

#### Required contract

At economic promotion/rejection time, independently derive every gate from the bound candidate run + benchmark suite + comparison contract.

For every gate, verify exact agreement for:

- observed value (with explicit finite/tolerance semantics),
- testability,
- pass/fail,
- reason code,
- final verdict.

This includes:

- `NET_RETURN_PCT`
- `MAX_DRAWDOWN_PCT`
- `PROFIT_FACTOR`
- `SHARPE_RATIO`
- excess return vs cash
- excess return vs passive
- excess return vs random preregistered quantile

For random gates, independently verify the selected quantile from the persisted individual random trials and the preregistered quantile/operator/threshold. Do not trust an aggregate field.

A manually edited artifact with `passed=true` must fail even if all hashes are recomputed consistently by the caller.

### B5 — Required benchmark comparability must be recomputed, not trusted

Do not trust top-level `comparable=true` alone.

For required benchmarks, independently verify enough underlying semantics to establish comparability:

- correct benchmark kind/vehicle;
- bound candidate/comparison identities;
- formal accounting validity;
- required random trial count and master seed;
- contiguous trial ids;
- each trial's deterministic seed/result identity;
- matching diagnostics must agree with independently recomputed candidate/trial entry counts, long/short counts, holding/exposure/notional tolerances;
- a required failed/incomplete trial makes RANDOM_MATCHED incomparable and therefore formal qualification `NOT_TESTABLE`.

Do not introduce a second unrelated benchmark engine.

## 2. Adversarial regression tests — mandatory

Add deterministic tests that fail on the current P6 implementation and pass only after this repair.

At minimum include:

1. **Dataset substitution attack**: keep the same evidence reference but alter one runtime candle close/high/low/volume value; formal execution must reject before qualification.
2. **Instrument substitution attack**: BTCUSDT protocol/comparison + ETHUSDT runtime candles with same count/times must reject.
3. **Forged run accounting attack**: copy a valid run identity, construct/persist self-consistent but economically false accounting (for example inflated realized/net PnL), recompute artifact hashes, and prove registry promotion rejects it.
4. **Forged gate attack**: start from a genuinely failing qualification, modify gate observed/pass fields and verdict to `QUALIFIED`, recompute all content hashes/attestation fields, and prove registry rejects it by independent recomputation.
5. **Forged random comparability attack**: modify matching diagnostics or comparable flags while retaining internally consistent artifact hashes; registry must recompute and reject.
6. **Dataset hash/content positive control**: exact canonical runtime data remains replayable/deterministic and preserves stable run/result identity.
7. Existing legitimate `QUALIFIED`, `REJECTED`, and `NOT_TESTABLE` lifecycle paths continue to work.
8. Existing P0–P5/P6 tests remain green.

Tests must attack semantic forgery, not merely mutate a file without updating its hash. Existing hash-tamper tests are useful but insufficient for these blockers.
