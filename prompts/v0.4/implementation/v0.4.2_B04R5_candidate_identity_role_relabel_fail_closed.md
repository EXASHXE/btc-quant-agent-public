## 0. Purpose

This is a **very narrow final B04 acceptance repair** after independent review of B04R4.

Do **not** redesign B04. Do **not** start B05/B06/B07. Do **not** change random draw semantics, alpha logic, strategy parameters, economic hurdles, H39, Final Holdout, live/testnet execution, persistence architecture, REST, or SQLite work.

B04R4 correctly introduced explicit `EconomicRunRole` values (`CANDIDATE`, `RANDOM_BENCHMARK`) and blocked direct random-benchmark artifacts from candidate consumers. However one synchronized identity-relabel path remains:

> A valid `RANDOM_BENCHMARK` run can potentially be reconstructed/relabelled as `run_role=CANDIDATE` while retaining the random producer contract and random replay bundle. `_validate_candidate_run_binding(...)` currently checks `run_role == CANDIDATE` and core protocol/dataset/economic identities, but does not independently require `identity.signal_producer_contract == protocol.signal_producer_contract`, and `EconomicRunResult.__post_init__` does not require the embedded `accounting["formal_run_identity"]` to equal `identity.to_dict()`.

This means a caller can potentially alter the outer identity role/producer fields without the consumer proving that the candidate identity is exactly the persisted identity originally produced by `execute_bound_run` under candidate authority.

Goal: make candidate authority **top-down and non-relabelable**:

```text
frozen protocol producer contract
    == candidate EconomicRunIdentity.signal_producer_contract
    == candidate ReplayInputBundle producer contract

and

candidate EconomicRunResult.identity
    == accounting.formal_run_identity
```

for every formal candidate artifact.

## 3. Remaining defect

### 3.1 Candidate consumer does not bind producer identity back to protocol

`_validate_candidate_run_binding(protocol, comparison, candidate_run)` currently checks:

- `run_role == CANDIDATE`
- experiment/protocol hashes
- dataset binding
- economic policy/cost/execution/funding identities
- comparison/metrics/terminal identities
- basic accounting fields

But it does not independently require:

```text
candidate_run.identity.signal_producer_contract
== protocol.signal_producer_contract
```

Therefore a relabelled run can potentially keep:

```text
run_role = CANDIDATE
signal_producer_contract = CANONICAL_RANDOM_BENCHMARK_V1
ReplayInputBundle = random bundle
```

while still sharing the same experiment/protocol/dataset/economic identities.

The persisted verifier is role-aware, but in CANDIDATE mode it currently treats `run_identity.signal_producer_contract` itself as the authority for bundle producer matching. Without a protocol-level comparison at the candidate consumer boundary, an internally consistent but protocol-inconsistent candidate identity can survive.

### 3.2 EconomicRunResult does not bind outer identity to embedded persisted identity

`EconomicRunResult.__post_init__` canonicalizes:

```text
identity
accounting
```

but does not require:

```text
accounting["formal_run_identity"] == identity.to_dict()
```

A caller can potentially construct a new `EconomicRunResult` with a modified outer identity while retaining accounting generated for a different role/producer identity.

This undermines the intended anti-relabel property of B04R4.

## 4. Required repair

### 4.1 Candidate producer identity must exactly equal protocol authority

At the canonical candidate-consumer boundary (`_validate_candidate_run_binding` or a single equivalent funnel), require:

```text
candidate_run.identity.run_role == CANDIDATE
```

and for non-empty signal runs:

```text
candidate_run.identity.signal_producer_contract
== protocol.signal_producer_contract
```

Both ID/version/hash must match via canonical `VersionedIdentity` equality.

If protocol producer contract is absent while candidate signal set is non-empty: reject.

If candidate identity producer contract is absent: reject.

If candidate identity producer contract is `CANONICAL_RANDOM_BENCHMARK_V1`: reject unless the frozen protocol itself explicitly defines a candidate producer contract with that exact identity **and the codebase has an explicit design allowing random producer as a candidate strategy**. Current B04 semantics do not allow that; therefore the recommended behavior is to reject `CANONICAL_RANDOM_BENCHMARK_V1` in `CANDIDATE` role outright.

Do not infer authority from bundle contents.

### 4.2 Bind EconomicRunResult identity to embedded persisted identity

For formal economic run artifacts, enforce:

```text
accounting["formal_run_identity"] == identity.to_dict()
```

at either:

- `EconomicRunResult.__post_init__`, if this does not break legitimate construction order, or
- the single canonical candidate/benchmark consumption boundary before acceptance/qualification.

Prefer the strongest invariant that does not create circular construction problems.

The embedded identity check must include at least:

```text
run_role
signal_producer_contract
replay_input_bundle_sha256
signal_set_sha256
decision_input_set_sha256
protocol_hash
experiment_revision_id
```

Exact full-dictionary equality is preferred if compatible with current schema.

### 4.3 Candidate artifact must not be repairable by synchronized relabel

An attacker must not be able to take a valid random benchmark artifact and make it candidate evidence by simultaneously changing:

```text
outer identity.run_role -> CANDIDATE
outer identity.signal_producer_contract -> random or candidate-chosen contract
run_id/result_id recomputed
```

while leaving accounting/replay bundle otherwise valid.

Candidate consumer must reject because either:

- outer identity disagrees with embedded `formal_run_identity`, or
- candidate producer identity disagrees with frozen protocol producer authority, or both.

### 4.4 Persisted verifier should remain role-aware

Do not weaken B04R4 persisted checks.

If useful, add a helper to compare identity producer contract with an expected protocol contract, but do not create another provenance framework.

### 4.5 Preserve benchmark path

Legitimate `RANDOM_BENCHMARK` runs must continue to:

- use `CANONICAL_RANDOM_BENCHMARK_V1`
- persist `run_role=RANDOM_BENCHMARK`
- pass replay/persisted verification
- remain usable only as benchmark trials, never as candidate evidence

Do not implement B06 random-draw reconstruction here.

## 13. Acceptance criterion

This repair succeeds only if all of the following are true:

1. A random-benchmark run cannot become candidate evidence by changing only `run_role`.
2. A random-benchmark run cannot become candidate evidence by synchronously changing outer `run_role` and outer producer identity.
3. Candidate `identity.signal_producer_contract` must exactly equal the frozen protocol producer contract.
4. `EconomicRunResult.identity` and the persisted `accounting.formal_run_identity` cannot disagree at candidate acceptance boundaries.
5. Legitimate candidate, random benchmark, and zero-signal controls remain valid.

Do not expand beyond this criterion.
