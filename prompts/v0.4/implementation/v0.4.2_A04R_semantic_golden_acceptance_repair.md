# 4. Repair R3 — correct event-order contract wording

## Problem

The A04 report currently presents an ordering that can be read as a universal relationship:

```text
market availability <= signal <= decision <= order <= funding <= fill <= terminal
```

That is too strong.

The accepted semantic is **not** that every order/fill lifecycle must have a funding event between order and fill.

The actual contract is:

1. each event is ordered by its explicit timestamp;
2. observable information must precede or equal the decision/order boundaries that consume it;
3. funding and fills are ordered by timestamp when both exist;
4. **when a funding settlement and fill have exactly the same timestamp, funding is applied first (`FUNDING_BEFORE_FILL`)**;
5. OHLC alone must not invent sub-bar ordering when timestamps are not observable.

## Required repair

Update the golden/report wording so it does not imply universal:

```text
order <= funding <= fill
```

Prefer language equivalent to:

```text
market_observation_availability <= signal_observation_timestamp
signal_observation_timestamp <= decision_timestamp
decision_timestamp <= order_timestamp
order_timestamp <= fill_timestamp

For any funding event that exists:
- order/fill/funding ordering follows the explicit timestamps;
- if funding_timestamp == fill_timestamp, use FUNDING_BEFORE_FILL.

No synthetic funding position in the timeline is implied when no funding event exists.
```

Update `event_order_contract.required_relations`, G09 rationale/expected values, and the report if needed.

Do **not** invent new production event semantics.

## Required tests

Add at least two positive controls:

### Case A — fill with no funding event

Prove the event-order golden permits:

```text
MARKET_AVAILABLE
SIGNAL_OBSERVED
DECISION
ORDER
FILL
TERMINAL
```

with no funding event inserted.

### Case B — equal-time funding/fill

Preserve the existing accepted tie behavior:

```text
... ORDER
FUNDING_SETTLEMENT @ t
FILL @ t
TERMINAL
```

with:

```text
FUNDING_BEFORE_FILL
```

The test must make clear that the tie rule is conditional on the funding event existing.

# 5. Repair R4 — random draw tie-order hardening

## Goal

G08 already correctly uses an independent stdlib PRNG transcription and correctly verifies master/trial seed generation, sampling, and direction shuffling.

However, all current opportunity timestamps are distinct.

Before B06 depends on this golden, add one deterministic positive control that includes at least two eligible opportunities with the **same `timestamp_ms` but different `opportunity_id` values**.

## Required semantic rule

The ordered eligible-opportunity preimage must use a stable deterministic ordering equivalent to:

```text
(timestamp_ms, opportunity_id)
```

before sampling.

After a trial samples opportunities, preserve the currently intended deterministic post-sample temporal ordering. If equal timestamps occur in the selected set, use the same stable tie-break by `opportunity_id`; do not rely on incidental input/list order.

### Important

Inspect the current production random benchmark generator before encoding the new golden. Do not silently change the production algorithm in A04R.

If production currently sorts the input opportunity universe by `(timestamp_ms, opportunity_id)` but post-sample selected items only by `timestamp_ms`, determine whether the exact preregistered semantics already define the equal-timestamp post-sample tie order.

- If the semantics are clearly defined by existing code/protocol and can be captured without changing production, encode that exact rule in the golden.
- If the semantics are genuinely under-specified, do **not invent a new production rule in A04R**. Instead:
  - add a `CHARACTERIZATION_ONLY` or explicit ambiguity note;
  - document the exact gap for B06;
  - keep the independent oracle faithful to what is actually defined.

The goal is deterministic provenance, not opportunistic redesign.

## Test expectation

The test must independently derive the expected seed/sample ordering using stdlib `random.Random` plus explicit deterministic ordering logic. Do not call the production benchmark generator as the oracle.
