## 1. Why P5 exists

P0–P4/C2 repaired cash accounting, causal replay, execution semantics, risk enforcement and transaction-cost bounds. Formal economic qualification is still `NOT_TESTABLE` because a simulation result is not yet bound immutably to a unique research protocol and evidence identity.

Current `research_contract` has several correctness gaps:

1. `ExperimentMetadata` is `frozen=True`, but nested lists/dicts remain mutable.
2. Experiment identity is a caller-provided string and is not cryptographically bound to the protocol payload.
3. `ResearchContractRegistry.register_experiment(... allow_update=True)` permits in-place semantic replacement under the same experiment id.
4. `update_decision_status()` allows arbitrary state jumps and rewrites the current object instead of recording an append-only transition.
5. `save()` uses direct `write_text`; interrupted writes can leave partial/corrupt registry state.
6. Load/save has no revision, content hash, transaction generation or stale-writer detection.
7. A malformed/corrupt file can fail parsing, but there is no explicit transactional recovery/fail-closed contract.
8. P5 must not create a second competing research-governance universe. Existing `research_registry.py`, `research_protocol.py`, H39 freeze/hash patterns and historical evidence remain authoritative for their historical scope.

The purpose of P5 is therefore not “build a database framework”. It is to create the **minimum auditable protocol/evidence layer required for future economic qualification**.

## 3. Required protocol contract

### 3.1 Canonical immutable protocol payload

Define a protocol object whose semantic contents are deeply immutable after construction.

At minimum bind:

- experiment family / human-readable name;
- input/data contract identity;
- feature definition including parameters and bounds;
- prediction target and horizon;
- statistical/evaluation method and parameters;
- economic policy identity **and version/hash**;
- fee/slippage/funding/execution model identity **and version/hash**;
- benchmark/comparison contract identity or explicit `P6_PENDING` placeholder;
- product/instrument scope;
- code revision / implementation revision identifier;
- terminal treatment / data completeness policy where relevant;
- optional metadata only if explicitly classified as semantic vs non-semantic.

Nested collections must not remain externally mutable. Copy/freeze recursively or use immutable representations.

Changing any semantic field must create a new protocol revision/identity. It must never silently mutate an already registered protocol.

### 3.2 Canonical serialization and cryptographic identity

Implement deterministic canonical serialization for the semantic payload.

Requirements:

- stable key ordering;
- stable enum/string normalization;
- no timestamps or non-semantic metadata inside the semantic hash;
- SHA-256 content identity;
- identity reproducible after save/load;
- equivalent semantic payloads hash identically;
- any semantic change changes the identity;
- document the canonicalization contract.

Recommended identity structure:

```text
protocol_hash = sha256(canonical_semantic_json)
experiment_revision_id = <human family id> + protocol_hash prefix/full hash
```

Exact naming may differ, but caller-controlled ids alone must not establish semantic identity.

### 3.3 Revision semantics

Do not support `allow_update=True` style semantic overwrite.

Required behavior:

- same semantic protocol registered twice -> idempotent exact duplicate or explicit duplicate error; choose and document one deterministic contract;
- same human experiment family with changed semantic payload -> new revision identity;
- previous revision remains readable and unchanged;
- frozen/terminal revisions can never be thawed or rewritten;
- created timestamp, sequence number and audit metadata are append-only evidence, not part of semantic protocol hash unless explicitly justified.

## 4. Decision lifecycle and legal transitions

Separate immutable protocol definition from lifecycle decisions.

Do not store mutable `decision_status` as if it were part of the protocol definition.

Implement an append-only decision/event record with at least:

- experiment/revision identity;
- previous status;
- new status;
- decision timestamp;
- evidence references / evidence hashes;
- decision reason;
- actor/source identifier if available;
- optional statistical result reference;
- optional economic result reference;
- event id/hash or sequence allowing reconstruction.

Define an explicit transition table. At minimum enforce conservative lifecycle semantics around statuses currently used by v0.4, e.g.:

```text
PROPOSED -> REGISTERED
REGISTERED -> STATISTICALLY_QUALIFIED | REJECTED | FROZEN_ARCHIVE
STATISTICALLY_QUALIFIED -> ECONOMICALLY_QUALIFIED | REJECTED | FROZEN_ARCHIVE
ECONOMICALLY_QUALIFIED -> FROZEN_ARCHIVE   # no arbitrary backwards transition
REJECTED -> FROZEN_ARCHIVE                 # terminal except archivalization
FROZEN_ARCHIVE -> no transitions
```

You may refine the table if existing project governance requires it, but:

- no arbitrary jumps;
- no thawing a terminal/frozen state;
- no status mutation without an append-only event;
- failed transition must leave storage unchanged.

Important: P5 must **not** make `ECONOMICALLY_QUALIFIED` reachable from actual performance yet unless P6 evidence requirements are explicitly satisfied. Prefer blocking this transition or requiring an explicit P6 evidence type that does not yet exist. Formal economic qualification remains disabled.

## 5. Evidence binding

A decision must point to immutable evidence identities, not merely mutable file paths.

Implement a minimal evidence reference contract containing as appropriate:

- evidence type;
- logical id;
- path/URI if local;
- SHA-256 content hash;
- generated/observed timestamp;
- producing protocol/revision id;
- producing code commit/version when applicable;
- completeness / status marker.

Rules:

- missing required evidence fails closed;
- if a local evidence path is supplied and exists, hash mismatch fails closed;
- changing file contents after registration cannot silently preserve the same evidence identity;
- evidence reference can be stored without loading prohibited/holdout content;
- do not read H39 labels, Final Holdout, or Forward raw data during this task.

P5 only establishes binding mechanics. It does not create statistical or economic success evidence.

## 6. Persistence and concurrency contract

Implement the minimum robust local persistence needed for the registry.

### 6.1 Atomic commit

Direct `write_text()` replacement is not acceptable.

Use a transactional/atomic pattern such as:

```text
serialize complete new state
-> write temp file in same filesystem
-> flush
-> fsync file
-> atomic os.replace
-> fsync parent directory where supported
```

If the project already has a tested shared atomic JSON writer, reuse it.

### 6.2 Lost-update prevention

Two writers must not silently overwrite each other.

Implement at least one deterministic stale-writer defense, e.g. generation/version compare-and-swap or file lock + generation check.

Required invariant:

```text
writer A loads generation N
writer B commits N+1
writer A attempts commit from stale N
=> A must fail; B's state must remain intact
```

Do not claim distributed/database-grade transactions. This is a local single-file registry contract.

### 6.3 Corruption / write failure

- invalid JSON/schema/hash/generation must fail closed on load;
- no “empty registry fallback” after corruption;
- simulated write failure before atomic replace must leave previous committed state byte-for-byte readable;
- duplicate or partially applied decision events must not appear after failure;
- temporary files may be cleaned safely but must never be mistaken for committed state.

## 8. Mandatory deterministic tests

Add focused tests, preferably `tests/test_v041_p5_protocol_evidence_persistence.py`.

At minimum cover:

1. **Deep immutability**
   - mutate source dict/list after object construction;
   - registered protocol/hash must remain unchanged;
   - direct nested mutation through exposed object must be impossible or isolated.

2. **Hash determinism**
   - save/load same protocol -> identical hash;
   - dict key insertion order / equivalent representation -> identical canonical hash.

3. **Semantic-change identity**
   - change feature parameter, target, evaluation method, economic policy, cost/execution config, input contract or terminal policy -> new protocol identity.

4. **Non-semantic metadata**
   - allowed audit timestamp/comment change must not silently change semantic identity if classified non-semantic.

5. **No semantic overwrite**
   - registering changed semantics under same family cannot replace prior revision.

6. **Duplicate registration**
   - exact duplicate behavior is deterministic and leaves one canonical revision.

7. **Legal transition table**
   - valid transitions append exactly one event;
   - invalid jumps reject with zero state mutation.

8. **Frozen/terminal behavior**
   - `FROZEN_ARCHIVE` cannot transition;
   - rejected/frozen protocol cannot be silently reactivated.

9. **Economic qualification gate**
   - P5 alone cannot produce `ECONOMICALLY_QUALIFIED` without the not-yet-implemented P6 evidence contract.

10. **Evidence hash binding**
    - correct local evidence accepted;
    - tampered file/hash mismatch rejected;
    - registered evidence identity remains immutable.

11. **Atomic write failure**
    - inject failure before replace;
    - previous registry file remains valid and unchanged.

12. **Stale writer / lost update**
    - two registry instances from generation N;
    - first commits;
    - second stale commit fails closed and cannot erase first writer.

13. **Corrupt registry**
    - bad JSON, wrong schema, wrong content hash/generation -> explicit failure, never empty fallback.

14. **Append-only reconstruction**
    - replay protocol revision + decision events reconstructs current status deterministically.

15. **Legacy isolation**
    - `ResearchRegistry` historical/runtime eligibility behavior remains unchanged;
    - Final Holdout SEALED regression remains intact.

16. Run all P0–P4/C2 economic regression suites and the full repository suite.
