## 1. Objective

Create one explicit supported workflow:

```text
PIT / causal market-data evidence
    -> registered signal producer / verified decision inputs
    -> ReplayInputBundle
    -> canonical EconomicSimulationEngine execution
    -> canonical candidate replay
    -> reconstructed CASH / RANDOM_MATCHED benchmarks
    -> preregistered qualification
    -> append-only registry decision
```

All **new** research/backtest/shadow entrypoints must either:

1. route through this formal workflow, or
2. be explicitly labeled and technically restricted as legacy/diagnostic compatibility paths.

It must no longer be possible for a reasonable developer to invoke something named simply `backtest`, `research`, `formal_research`, or the default shadow workflow and unknowingly use old R-based economics as though it were the current formal qualification path.

This is a **semantic consumer cutover**, not a LOC-reduction round.

## 4. Required architecture

### 4.1 One formal workflow facade

Introduce one narrow application-level owner for new formal research jobs. It should orchestrate existing accepted components rather than reimplement their arithmetic or validation.

The facade should make the supported sequence explicit and typed, for example conceptually:

```text
FormalResearchJobSpec
    -> authoritative protocol/evidence loading
    -> producer + ReplayInputBundle construction
    -> execute_bound_run / canonical engine
    -> benchmark reconstruction
    -> qualification verification
    -> optional registry decision
    -> immutable result/evidence references
```

Names may differ if current types already provide a better fit.

The facade must not become a second source of truth for:

- fill price;
- fees/slippage;
- funding;
- ledger/PnL;
- terminal policy;
- random benchmark sampling;
- CASH benchmark;
- qualification hurdle logic.

Those stay with the accepted canonical owners.

### 4.2 Verification reuse without weakening verification

Astra identified repeated candidate replay across binding/qualification/benchmark/registry paths. You may reduce duplicate execution **within a single trusted acceptance transaction** only if the reusable verification result is bound to the complete semantic authority.

Never cache/reuse merely by submitted `result_id`.

If introducing a verified context/result object, its identity must include all material authority required to prevent stale or synchronized-rewrite substitution, including as applicable:

- protocol identity/hash;
- dataset/evidence identity;
- run role;
- producer contract;
- replay bundle/input hashes;
- policy/execution/fee/funding identities;
- comparison contract;
- canonical result identity/version.

Cold independent replay tests must remain.

If safe reuse cannot be proven simply, retain duplicate verification rather than weakening the boundary.

### 4.3 Break only harmful dependency cycles

The B13 audit measured these cycles:

```text
economic.qualification
    <-> economic.execution_replay
    <-> economic.acceptance_verifier

economic.signal_producer
    <-> research_contract.models
```

You may extract leaf value-contract/protocol types or move orchestration upward to reduce these cycles, but:

- preserve canonical serialization and hashes;
- preserve public compatibility imports where needed;
- do not duplicate verification logic to make imports look cleaner;
- do not rename/move the entire `economic` package for aesthetics.

A cycle may remain if removing it would increase semantic risk.

### 4.4 Remove `backtest` as a data-type authority

Current data modules import legacy backtest helpers/types such as resampling/funding representations. Move only genuinely reusable leaf behavior/types out of `backtest.py` into narrow data/domain owners.

Requirements:

- data ingestion must not depend on the legacy simulator;
- versioned historical readers must still decode old artifacts;
- formal funding behavior remains owned by the accepted economic funding model;
- extracted functions must have differential/characterization tests against the immutable baseline where semantics are intended to remain unchanged.

### 4.5 New-consumer routing

Audit and cut over at least these surfaces:

#### `quantctl backtest`
It must not silently represent legacy economics as the current formal path.

Choose one safe outcome:

- route the default/new form through the formal research facade; or
- rename/require an explicit legacy mode while introducing an unmistakable formal command.

Backward-compatible aliases are allowed only if they clearly advertise legacy/diagnostic semantics and cannot promote evidence through P5/P6.

#### `quantctl research`
New formal research must use the formal workflow. Historical runner dispatch may remain in C-lite, but it must be explicitly legacy/versioned and not the default meaning of generic `research`.

#### `tools/run_formal_research.py`
A tool named `formal` must actually use the repaired formal path. Do not leave a misleading wrapper around `research.run_full_suite`.

#### shadow/service path
New shadow economic evaluation must not acquire economic truth from the old R-based `shadow.py` ledger/resolution path. Preserve compatibility reading of old shadow rows, but keep new formal-shadow outputs versioned/separate so old rows are never silently reinterpreted as canonical cash-ledger results.

`QuantService` remains an application coordinator, not an economic authority.
