# 1. Why A04 is a stage boundary

B01–B07 will modify causal execution, PIT data contracts, provenance bundles, benchmark reconstruction and persisted qualification replay.

Those repairs need a stable answer to:

- what should a correct fill be?
- when is ordering unknowable from OHLC?
- which data was available at decision/fill time?
- what accounting numbers are independently correct?
- what exact event stream should a declared strategy produce?
- what does a true CASH benchmark contain?
- what random draw should a given seed/opportunity set produce?
- which current P7 attacks must be rejected rather than reproduced?

A04 defines those expectations before the repair code is written.

A wrong golden is worse than no golden because it can make later incorrect implementations appear formally verified.

Therefore:

- every expected numerical result must have an independent derivation;
- known defects must be represented as expected-rejection/pending-repair cases, not accepted outputs;
- production helper functions under repair must not be used as the sole oracle for their own tests;
- frozen H39/statistical semantics must not be generalized into unrelated economic semantics.

# 4. Golden design principles

## 4.1 Independent oracle requirement

For every `VALID_GOLDEN` case involving arithmetic, provide a derivation independent from the production implementation.

Acceptable independent oracles include:

- direct hand-calculated formulas encoded in the test;
- a tiny local pure-function oracle written only from the formal equations in the report;
- explicit event-by-event tabulation with exact expected cash/position/PnL;
- deterministic seed/draw calculation using Python stdlib primitives documented in the golden.

Do not import and call `summarize_ledger`, `Portfolio.from_events`, `ExecutionModel`, benchmark generators, or qualification verifier as the sole source of expected values for cases testing those same semantics.

Production output may be compared to the independent oracle for currently-correct cases, but the oracle must stand on its own.

## 4.2 Known defect cases

For B1/B2/H1/H2/H3/H4, the A04 tests must capture the attack as a **known defect specification**.

Do not write a normal green assertion that says the current buggy behavior is correct.

Choose one of these patterns:

1. store the case in the golden JSON as `KNOWN_DEFECT_EXPECT_REJECTION` and add a test proving the case is present and well-formed, while documenting current behavior separately; or
2. if useful, add a characterization test that explicitly asserts the current defect is still reproducible, but name/mark it clearly as defect characterization and do not let it become the future acceptance oracle.

Do not use blanket `xfail` as a substitute for a precise defect contract.

## 4.3 Numerical precision

Use exact decimal/string quantities where binary floating-point ambiguity would make a golden fragile.

Where existing production types require float, specify explicit comparison tolerance in the golden/report and justify it.

Do not loosen tolerances until a buggy implementation passes.

## 4.4 Versioned semantics

If a golden intentionally describes semantics that differ from current behavior, record:

- current observed behavior;
- desired corrected behavior;
- future task that owns the change;
- whether existing historical artifacts remain historical/read-only.

No historical result should be silently recomputed under new semantics.

# 5. Required valid goldens

At minimum cover the following currently-correct or independently definable semantics.

## G01 — Linear perpetual LONG accounting

Synthetic example with simple prices and no ambiguity.

At minimum define:

- initial cash;
- open price;
- quantity;
- close price;
- entry fee;
- exit fee;
- optional funding = 0 for this base case.

Independently derive:

```text
realized_pnl = quantity * (close_price - open_price)
net_cash_change = realized_pnl - entry_fee - exit_fee
final_equity = initial_cash + net_cash_change
```

Verify current accounting matches.

## G02 — Linear perpetual SHORT accounting

Equivalent explicit SHORT formula:

```text
realized_pnl = quantity * (open_price - close_price)
```

with fees exactly once.

## G03 — Partial close / weighted entry / round-trip accounting

Use at least:

- two opens or one open plus partial close;
- nontrivial quantity split;
- explicit expected remaining position;
- realized vs unrealized separation;
- fee attribution.

Provide event-by-event hand calculation.

## G04 — Funding sign and tie semantics

Include at minimum:

- LONG pays positive funding;
- SHORT receives positive funding;
- zero position receives/pays zero;
- funding before equal-time fill according to the existing accepted causal contract.

Do not change H39 or broader market statistics.

## G05 — Terminal policy semantics

Cover both supported terminal modes if the formal kernel supports both:

- flat-required terminal handling;
- explicit unrealized terminal state / non-flat handling if supported.

Independently derive final equity and notional.

## G06 — CASH benchmark true no-trade semantics

Define the desired exact CASH policy:

- initial equity constant across expected marks;
- zero trades;
- zero fills;
- zero fees;
- zero funding;
- zero turnover;
- zero exposure;
- zero realized/unrealized PnL;
- no position;
- correct benchmark kind/vehicle.

This is a `VALID_GOLDEN` for desired semantics even if current persisted verifier does not yet enforce all of it.

The H2 attack itself must be a separate `KNOWN_DEFECT_EXPECT_REJECTION` case.

## G07 — Passive benchmark deterministic simple case

Use a tiny simple market path where the expected passive entry/hold/exit accounting is hand-computable under a zero-cost model or an explicitly hand-computed nonzero cost model.

Do not use the passive verifier/generator as its own oracle.

This case protects the passive repair from regressions while later provenance work proceeds.

## G08 — Deterministic random seed primitive

Without yet repairing H1, define a tiny ordered eligible-opportunity set and a fixed master seed/trial id rule matching the currently preregistered randomization semantics.

Record the expected deterministic trial seed(s) and, if the existing draw rule is unambiguous and discoverable, the expected sampled indices/directions using an independent stdlib implementation.

If the existing persisted contract is insufficient to reconstruct the full draw, explicitly classify the missing full-draw replay as H1 rather than inventing semantics.

## D-B2 — LIMIT touch timing is unresolved from OHLC

Canonical case:

```text

high = 110
low = 90
close = 100
bar interval = 15m
BUY LIMIT = 95
submit time = bar open

```

Desired semantic:

- do not backdate a fill to open based on full-bar low;
- mark/refuse the ordering as unresolved unless lower-resolution evidence exists;
- no early funding entitlement may be inferred from an unknown touch.

Also specify the valid contrasting case:

- BUY LIMIT priced at or above an observable opening ask/open-marketability condition may fill at open if the declared model supports that observable state.

Future owner: B01.

## D-H3 — Opening fill cannot use future completed-bar volume

Construct two otherwise-identical bars/runs:

- same opening price;
- same order time;
- same prior-available state;
- different volume accumulated later in the bar.

Desired semantic:

```text
an already-observed opening fill price/cost must not change when only future suffix volume changes.
```

Future owner: B02.

## D-H4 — closed=False / PIT availability must not become formal COMPLETE evidence

Desired semantic:

## D-H1 — random benchmark cloned-candidate trials

# 10. Test implementation rules

## 10.1 No self-oracle tests

Bad:

```python
expected = summarize_ledger(events)
assert summarize_ledger(events) == expected
```

Bad:

```python
expected_fill = execution_model.fill(order, candle)
assert execution_model.fill(order, candle) == expected_fill
```

Good:

```python
expected_realized = qty * (exit_price - entry_price)
expected_final_cash = initial + expected_realized - entry_fee - exit_fee
assert current_result.final_cash == pytest.approx(expected_final_cash)
```

Good:

- independently encode the expected random seed/index calculation from the formal rule;
- compare production result only after the independent result is established.

## 10.2 Existing bugs must remain visible

If a current defect case is executable, optionally capture its present observed behavior in a field such as:

```json
"current_characterization": {
  "observed": "BUG: fills at open",
  "verified_at_sha": "..."
}
```

but never put that value under `expected.correct_behavior`.

## 10.3 Hermeticity

All tests use temporary roots and the A02 guard.

No network, live/testnet, H39 real store, Final Holdout, or operational database.
