# 5. Secondary major task — design a **large simplification / architecture convergence**

The repository has accumulated substantial research and infrastructure code across many versions. Full tests are now expensive: the latest P6 report records about 804 tests, full pytest taking roughly 6–7 minutes locally and coverage taking roughly 8 minutes. Earlier repository review also identified very large modules, duplicated execution/accounting/research utilities, historical research runners, and overlapping diagnostics.

The user explicitly wants a **major simplification and refactor**, potentially aggressive, because:

- active maintenance surface is too large relative to the number of qualified strategies (currently assumed zero unless you verify otherwise);
- research workflows have accumulated historical runners and duplicated semantics;
- test / coverage time is becoming expensive;
- future alpha research should build on one coherent kernel, not many custom paths;
- data collection / evidence preservation must stay reliable while the codebase becomes substantially smaller and easier to reason about.

However, simplification has a strict constraint:

> **Never trade fewer lines of code for weaker research validity.**

Do not recommend deleting or abstracting away controls whose purpose is PIT correctness, causal time, anti-p-hacking, evidence provenance, statistical validity, economic accounting, matched benchmarking, or fail-closed qualification.

The desired outcome is **less active code and fewer semantic implementations, with equal or stronger scientific rigor**.

# 6. Do not equate “complete refactor” with a blind rewrite

You must explicitly decide which migration strategy is safest:

- in-place semantic convergence;
- strangler-style replacement of legacy paths;
- modular extraction around frozen interfaces;
- partial rewrite of selected modules;
- or, only if strongly justified, a clean rewrite of a subsystem.

A repository-wide clean-slate rewrite should be recommended only if you can demonstrate that incremental convergence is materially riskier.

The preferred default is:

```text
freeze scientific contracts
-> build golden characterization tests
-> converge duplicated semantics
-> cut over incrementally
-> archive/delete old active implementations only after equivalence is proven
```

Do not propose one giant refactor commit.
